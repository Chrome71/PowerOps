# Finish checks, export and report requests

Read this file during Section 4 (Finish) of `powerops-implement`.

## 1. Export, .gitignore and flow tests (step 2)

Before you open a pull request, for each cloud flow the plan adds or changes, write or update its tests once the solution is exported and unpacked into the repo, and commit them with that export. To export, follow `dv-solution`, and use what the latest sign-in probe (section 3, step 3) found about `pac`; do not run `pac` again to find out, and export from the environment the person named there, never the active profile's. If `pac` isn't available, export with the Web API's `ExportSolution` and keep the zip, which `powerops analyze` and `powerops test` both read, and tell the user it isn't unpacked. Before you commit the export, check that the repo's `.gitignore` holds `*.msapp` and a line for each of the unmanaged zip, the managed zip, its settings file and the managed unpack folder, and add each that is missing: a canvas app's `.msapp` caches the URL of the environment it was made in, and the zips and that folder hold the same `.msapp` files. Then stage no `.msapp`, no zip and no settings file. A repository that keeps its deploy zips in Git on purpose, as PowerOps' ephemeral pull request recipe does, keeps that choice, and you add no zip line there. If `git ls-files` shows an `.msapp` or a settings file already tracked, tell the person and name `git rm --cached <file>`, which stops tracking it and keeps it on disk; running it stays theirs. Tests are `*.flowtest.json` files in the folder that the repo's PowerOps Action `tests` input names, else `flowtests/` at the repo root: one test for each path through the flow that the plan describes, with a mock for each connector action (see the PowerOps flow tests page, https://github.com/Chrome71/PowerOps/blob/main/docs/FLOW-TESTS.md). Use fake values in triggers and mocks; never paste a real run's raw outputs without replacing tenant URLs, ids, emails and names. Run `powerops test <solution> --tests <folder>` and report the result. A test that does not pass blocks the merge in CI: fix the flow or the test, and never delete or weaken a test to make it pass. If a test is `unsupported`, tell the user and let them decide. If the solution is not in the repo yet, say "not verified" and why.

## 2. Live Dev checks and design check (step 3)

For each cloud flow and app the plan adds or changes, check its final saved version in Dev, through Microsoft's skill for the product or by asking the user; never run `pac` or `az` for these checks. A read-only check needs no question. A check that runs a flow or writes data is covered by the sign-off with the test rows its Step's check names; other rows follow rule 7 of section 3. Fire each flow's real trigger once with a synthetic input and confirm that a run started and did what the plan says. For a canvas app, say who saves and who publishes, publish when a Step names it, load the published version fresh and check the planned controls in their states. If the published app shows an old-version banner, select Refresh on it: in one run the first load after a republish was still the old version. Confirm that each changed component is in the plan's solution, and report any other unmanaged solution it is in, apart from the system Default and Active solutions and sharing the plan allows. If a check can't run, say "not verified" and why. A later save or publish voids the checks it affects.

Then check the design of each screen the plan adds or changes, when the last `prototype:` line of `decisions.md` is `approved`. Get a screenshot of each built screen at the plan's form factor, and of each state you can reach without writing data: with a browser tool if you have one and the person is signed in, otherwise from the person. Compare each with the same screen in `mockups/prototype.html`, read its map `mockups/prototype.map.md` for the control or component each element is built with, and compare with `look.md` in the `references/` folder of `powerops-plan` (sections 2 to 4). Write `docs/plans/<name>/design-check.md`: `# Design check: <name>`, then for each screen its scores (the scale in `baseline.md` beside `look.md`) and one line per gap, `- <screen>: <what differs or fails>; <the control or theme setting that closes it>; fixed|open`. Fix each gap the plan's `Steps` allow by changing that control in place, and look again, at most three rounds. A gap that needs a plan change stops under rule 6 of section 3. A save or publish for a fix inside the Steps is covered by the sign-off (rule 7 of section 3). With no screenshot of a screen, write "not checked" for it and why; never grade a screen you haven't seen. After a fix, export and unpack the solution again and repeat steps 1 to 3 for what the fix changed, so that the two reports and the zip that is deployed hold the fix. An open gap, and a screen that is "not checked", is a remaining gap for step 4.

## 3. Report requests and deploy linking

The request names the plan, the current solution, the previous solution, the settings file, the test folder and any live evidence from step 3. The settings file is the one the deployment imports, `<zip name>.settings.json` beside the zip in the deploy folder, and both reports record its hash. When the deploy folder holds the managed zip that will be deployed, the request also names that zip, and the current solution is that zip unpacked into a new folder in the repo, outside the deploy folder and the source folder (such as `review/ContosoApp_managed`). Keep that folder out of Git like the two zips, because it holds the same `.msapp` files. The unpack command is exactly `pac solution unpack --zipfile <zip> --folder <folder> --packagetype Managed`, with no other option, and `dv-solution` or the person runs it: this skill never runs `pac` itself, apart from its sign-in probe. The previous solution is the last export before this plan, from the repo's history. Where one of these doesn't exist, the request says "no previous solution", "no settings file", "no test folder" or "no live evidence", and you invent none. Tell the Security reviewer that `pac` is signed in only if the user said so in this session.

Neither report changes the plan's status, but the import routes read them: the MCP tool `deploy_apply`, `deploy gate` and the Action import a zip only when both reports of this plan folder are ready, were written for the current plan, and are linked to that zip. A report is linked by the zip's SHA-256 in its `deploy-hash:` line, and the route checks that its `solution-hash:` is the digest of a fresh `pac solution unpack` of that zip. The routes also need both reports' `settings-hash:` to be the SHA-256 of that settings file. So commit the two reports, and a build that changes the zip needs both roles run again on its new unpack; a changed settings file, like a changed zip, needs both roles run again. Only as the fallback, when that check fails (another `pac` version or another unpack option can change the digest), run both roles again with the zip in the deploy folder as the current solution; that replaces both reports, and the new ones mark roles, tables, forms and views "not verified" because a role can't read files inside a zip. Or leave the import to the person, whose own `deploy apply` warns and goes on. A build that changes the solution after this runs `powerops-review-security` again before `powerops deploy plan`.
