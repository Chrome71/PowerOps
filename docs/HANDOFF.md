# Hand-off to Microsoft's skills

Microsoft's [power-platform-skills](https://github.com/microsoft/power-platform-skills) and [Dataverse-skills](https://github.com/microsoft/Dataverse-skills) build apps, flows, sites and tables. PowerOps plans the work, checks what they built, plans the import and imports it. When both are installed, an agent follows the steps below: Microsoft's skill builds in Dev, and PowerOps does everything after that. In a flow that PowerOps gates, `powerops deploy apply` is the import; with the hooks in [Gate Microsoft's imports](#gate-microsofts-imports), a Microsoft import tool runs only when its call is the reviewed plan's first import. `powerops settings apply` stays the one-solution import without a plan, for use outside such a flow.

## Set up

- Install the `powerops` CLI ([Install](../README.md#install)). The skills call it.
- Add the PowerOps skills to the repo with `powerops skills install` ([Planning skills](USE-WITH-AGENTS.md#planning-skills)). In a workspace whose own tooling rewrites `.claude/skills/`, for example a sync script that deletes and recreates the folder, run it in each child project, not at the workspace root, and start the agent there: the next rewrite removes skills installed at the root.
- Install Microsoft's skills as their READMEs say.
- Sign in `pac` with `pac auth create`. PowerOps is tested with `pac` 2.13.1, and the example workflows pin 2.14.1; older builds are untested (`pac` prints its version). `drift`, `deploy plan` and `deploy apply` also need the Azure CLI signed in with `az login` ([Command reference](COMMANDS.md#drift)).

## Per product

Microsoft's skill builds each product in Dev, and PowerOps takes over after it. Power BI is the exception: it has no Dataverse solution and moves by its own route.

| Product | Microsoft builds it with | Then PowerOps | To Test and Prod |
|---|---|---|---|
| Canvas app | `canvas-app` (canvas-apps) and the Canvas Authoring MCP server | `analyze`, `diff` and the import gate on the exported solution | `deploy apply` |
| Model-driven app | `app-builder` and `genpage` (model-apps), for forms, views, custom and generative pages | the same | `deploy apply` |
| Code component (PCF) | `pcf` (pcf). Its `pac pcf push` writes to Dev and needs a yes, and the gate always blocks it | the same | `deploy apply` |
| Power Pages site | `create-site`, `edit-site` and `setup-datamodel` (power-pages) | the same | `deploy apply` |
| Cloud flow | `build-flow` (power-automate) | `analyze`, `test`, `diff` and the import gate | `deploy apply`, then `manage-flows` for a flow that is off (step 10) |
| Code app | `create-code-app` (code-apps-preview, folder `code-apps`). Its baseline `pa app push` needs a yes, goes to Dev only and takes `--solution-id` | `analyze`, `diff` and the import gate | `deploy apply` |
| Dataverse tables | `dv-metadata` and `dv-solution` (dataverse) | `analyze`, `diff` and the import gate | `deploy apply` |

## The steps

The steps go from Dev to Test. For Prod, repeat steps 7 to 9 with Prod as the target, with its own plan and approval.

1. **Plan.** The `powerops-plan` skill turns the request into a plan in `docs/plans/<name>/`, `powerops-review-plan` reviews it in a fresh context, and `powerops plan sign-off docs/plans/<name>` signs it off. `powerops plan status` shows where each plan stands. Asked to build without a signed-off plan, the skills draft one and ask only the route, and the publisher prefix if the repo doesn't show it.
2. **Build in Dev.** `powerops-implement` does the plan's steps in order and hands the build work to the Microsoft skill for the product: `canvas-app` (canvas-apps), `app-builder` or `genpage` (model-apps), `pcf` (pcf), `build-flow` (power-automate), `create-site` (power-pages) or `create-code-app` (code-apps-preview). Tables, columns, publishers and solutions go to `dv-metadata` and `dv-solution` (dataverse). Build in Dev only, never in Test or Prod. `powerops-implement` never deletes in a tenant, journals each tenant write it attempts in the plan's `writes.md`, and names the route of each component in its commits. After the build and its final checks (step 4), `powerops-implement` starts `powerops-verify` and then `powerops-review-security`, each in a fresh context. Each writes a report in the plan folder, and neither gates anything.
3. **Export, and unpack into XML only.** Export the solution from Dev, unmanaged for the source and managed for Test, and unpack the unmanaged zip into an XML folder (`Other/Solution.xml`) that you commit:

   ```sh
   pac solution export --environment <dev> --name ContosoApp --path ContosoApp.zip
   pac solution export --environment <dev> --name ContosoApp --path deploy/ContosoApp_managed.zip --managed
   pac solution unpack --zipfile ContosoApp.zip --folder src/ContosoApp
   ```

   The folder holds each canvas app's `.msapp`, which caches the URL of the environment it was made in, so don't push that folder to a public repository. The two zips hold the same `.msapp` files, so keep `ContosoApp.zip` and `deploy/ContosoApp_managed.zip` out of a public repository too: if the repository is public or may become public, add those two paths to `.gitignore` yourself. The settings file of step 6 holds the target's connection ids and values, and stays out of Git in any repository. A commit you never push exposes nothing, but pushing the branch later publishes every commit on it, so keep these files out of commits from the start. A `.gitignore` entry does not stop Git tracking a file it already tracks (`git rm --cached <file>` stops it and keeps the file on disk), and a file once pushed stays in the history that was pushed.

   Never unpack into a folder in the YAML layout that Dataverse Git integration commits (`solutions/*/solution.yml`). `pac solution unpack` writes XML only, and pointed at a YAML folder with `--allowWrite --allowDelete` it added XML files beside the YAML and deleted others ([FOUNDATION section 8](FOUNDATION.md#8-research-topics-still-open)). Dataverse-skills' `dv-solution` unpacks with `pac` too, so the same rule applies to it. The managed zip can come from this export or from an export in CI, as in [docs/examples/](examples/README.md).
4. **Analyze and test.** `powerops analyze src/ContosoApp` reports what would break the import or a run, and `powerops test src/ContosoApp --tests flowtests` runs the flow tests that `powerops-implement` wrote or updated for each flow the plan changed. Fix errors and failing tests in Dev and export again. In CI, the Action's `tests` input runs the same tests as a required check ([Merge gate](GITHUB-ACTION.md#merge-gate-flow-tests)). Then `powerops-implement` checks the final saved version live in Dev: each flow's real trigger, a fresh load of each published canvas app, and each component's solution, with the user's go-ahead for anything that writes.
5. **Diff.** `powerops diff <old> src/ContosoApp --format markdown` compares the base branch's copy of the solution with the new one, for the pull request. The PowerOps Action puts this diff in its PR comment only when `target` is not set; with `target` (step 7) the comment holds the plan, so the diff then needs its own step.
6. **Settings.** One tool writes the deployment settings file: `powerops settings generate src/ContosoApp`, or model-apps' `solution-settings.js template`. Fill in each connection id and value, save it beside the managed zip as `deploy/ContosoApp_managed.settings.json` (the `<zip name>.settings.json` that `deploy plan` reads), and check it with `powerops settings validate src/ContosoApp --settings deploy/ContosoApp_managed.settings.json` (it checks that each connection reference has a `ConnectionId`, not that the connection exists). To keep a variable's default or current value, remove its entry instead of leaving `"Value": ""`, which `pac solution import` rejects. The file holds the target's connection ids and values, so keep it out of Git and build it in CI from repository variables, as [docs/examples/](examples/README.md) does.
7. **Plan the import in CI.** `powerops deploy plan deploy --target <test> --save deploy/powerops-plan.json` runs on the pull request (the Action's `deploy-folder` and `target` inputs write the same plan file), so the reviewer sees the import order, installs, upgrades, deletions, settings problems and flow states before approving. Run it after the two reports, and after any later build that changes the solution has run `powerops-review-security` again. The person promotes only what the reports name: each describes the folder or zip it names. `plan status` says when that solution changed since the report (`stale (solution)`), and `deploy plan` warns for each zip that no ready report names by its SHA-256 ([Use from an agent](USE-WITH-AGENTS.md#the-two-build-roles)).
8. **Import.** After approval, `powerops deploy apply deploy/powerops-plan.json --target <test> --apply`. It plans again and refuses when an input of the plan changed since the review: a zip, a settings file, the target environment, the target's solution state as `drift` reads it, or a dependency's version. An agent runs it only after the user said yes to that environment in the session; a pull request approval is not that yes. Don't import with a skill's or an MCP tool's import: pac's MCP server (`solution_import`), model-apps' `solution-settings.js import`, power-pages' `import-solution` or `deploy-pipeline`, or Dataverse-skills' `dv-solution`. None of them checks a reviewed plan. With the hooks in [Gate Microsoft's imports](#gate-microsofts-imports), pac's MCP `solution_import` and a plain `pac solution import` can run behind the gate, and the other Microsoft imports are always blocked there. After an apply that stops, times out or leaves a row `unknown`, follow [Recovery](RECOVERY.md): there is no rollback.
9. **Confirm.** `powerops drift --solution ContosoApp --env <dev> --env <test>` compares the solution in both environments.
10. **A flow is off.** `deploy apply` reports each cloud flow's state after the import, but it can't turn a flow on, because `pac` can't. Use power-automate's `debug-flow` to find out why and `manage-flows` to turn the flow on (its publish operation). That is a write in that environment, so ask first. Then run `drift` again.
11. **An agent was imported.** A solution doesn't carry some of a Copilot Studio agent's settings, so set them in the target after `deploy apply`: Application Insights, manual authentication (configure user authentication again), Direct Line and web channel security, the channels it is deployed to, and sharing with makers and users. Publish the agent before you share it. A published agent keeps the environment variable values it was published with, so publish it again after a value changes; a secret is read at run time and needs no republish. Each of these is a write in that environment, so ask first. PowerOps checks none of them, and its live checks for agents (the data policy, the publish state, the connection binding and evaluations) are waiting: no Copilot Studio environment has been available to build them on ([FOUNDATION section 8](FOUNDATION.md#8-research-topics-still-open)). Sources: [ALM guidance for Copilot Studio](https://learn.microsoft.com/microsoft-copilot-studio/guidance/alm), [Export and import agents using solutions](https://learn.microsoft.com/microsoft-copilot-studio/authoring-solutions-import-export) and [Variables overview](https://learn.microsoft.com/microsoft-copilot-studio/authoring-variables-about#environment-variables), checked 2026-11-04.

## Gate Microsoft's imports

The PowerOps skills import only with `deploy apply`, but that is an instruction to the agent: nothing in the client stops pac's MCP tool `solution_import` or the import script of a Microsoft skill. A `PreToolUse` hook can make those calls wait for PowerOps. Before each call, the hook runs [`powerops deploy gate`](COMMANDS.md#deploy-gate), which reads the call and runs the dry run of step 8. It exits 2 to block the call. Claude Code and Codex both block a call when a hook exits 2, and give its stderr (here the gate's reason) to the agent.

In Claude Code, add the hooks to the repo's `.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "mcp__pac-cli__solution_import|mcp__pac-cli__pages_upload|mcp__pac-cli__pages_upload-code-site|mcp__pac-cli__copilot_publish|mcp__pac-cli__model_genpage_upload",
        "hooks": [{ "type": "command", "onFailure": "block", "timeout": 600, "command": "powerops deploy gate \"$CLAUDE_PROJECT_DIR/deploy/powerops-plan.json\" || exit 2" }]
      },
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "onFailure": "block", "timeout": 600, "command": "powerops deploy gate \"$CLAUDE_PROJECT_DIR/deploy/powerops-plan.json\" || exit 2" }]
      },
      {
        "matcher": "Monitor",
        "hooks": [{ "type": "command", "onFailure": "block", "timeout": 600, "command": "powerops deploy gate \"$CLAUDE_PROJECT_DIR/deploy/powerops-plan.json\" || exit 2" }]
      },
      {
        "matcher": "PowerShell",
        "hooks": [{ "type": "command", "onFailure": "block", "timeout": 600, "command": "powerops deploy gate \"$CLAUDE_PROJECT_DIR/deploy/powerops-plan.json\" || exit 2" }]
      }
    ]
  }
}
```

- A pass means the call is the plan's first import: the zip and settings file are the bytes the plan holds, the environment is the one the plan was made for, no flag changes the import, and the dry run passes. It is not the user's yes: ask first, as for `deploy apply --apply`.
- The gate allows pac's MCP `solution_import` and one plain `pac solution import` with literal absolute paths. `--async`, `--max-async-wait-time` and `2>&1` are allowed; any other flag or redirection blocks. On Windows, quote `C:\...` paths ([`deploy gate`](COMMANDS.md#deploy-gate) lists the rest).
- Turn the hooks on when you start step 7 and off when you go back to building in Dev. With the hooks on, an import into Dev is blocked, because the plan is for the target, and so is create-site's template import. Import a plan of several solutions with `deploy apply`: the first import changes the target, so the next call fails the dry run.
- `Monitor` runs shell commands too, so it has a group like `Bash`.
- `$CLAUDE_PROJECT_DIR` is the folder Claude Code started in. A hook runs in the folder of the agent's last `cd`, so `$(git rev-parse --show-toplevel)` would let an agent that ran `git init` in a subfolder point the gate at a plan file of its own.
- The first matcher names five tools of pac's MCP server: `solution_import`, and the four that write a site, a page or an agent (`pages_upload`, `pages_upload-code-site`, `copilot_publish`, `model_genpage_upload`). Each name starts with the name you gave the server: `mcp__pac-cli__` for `pac-cli`, the name in Learn's `claude mcp add-json` example. For a server that a plugin provides, it is `mcp__plugin_<plugin>_<server>__`. A server with another name needs its name in all five, or its tools run unchecked. Claude Code reads a matcher of only letters, digits, `_`, `-` and `|` as a list of exact names.
- Hooks copied from an earlier version of this page match only `solution_import`. Replace that matcher with the one above, or the other four tools run unchecked. In Codex, trust the changed hook again afterwards (below).
- `onFailure: "block"` (Claude Code 2.1.295 or later) also blocks the call when the hook can't start or times out. Without it, both let the call through. `|| exit 2` blocks when `powerops` isn't on the `PATH`.

Codex reads the same hooks from `.codex/hooks.json` in the repo, or from `~/.codex/hooks.json`, with these changes. Its tool names turn every character of the server name and of the tool name other than a letter, a digit or `_` into `_`, so the first matcher is `mcp__pac_cli__solution_import|mcp__pac_cli__pages_upload|mcp__pac_cli__pages_upload_code_site|mcp__pac_cli__copilot_publish|mcp__pac_cli__model_genpage_upload`, which Codex also reads as a list of exact names. It has no `onFailure`, so leave it out: a hook that times out lets the call through. It has no `PowerShell` or `Monitor` tool, so leave those groups out. It sets no `CLAUDE_PROJECT_DIR`, so write the plan file's full path in its place: Codex runs hooks in the folder it started in, whatever folder the agent's command uses, and on Windows with `cmd.exe /C`, which expands no `$...`. A shell that can't parse the line (fish before 3.4, Windows PowerShell 5.1) lets the call through. Codex runs a new or changed hook only after you trust it in `/hooks`, and a repo's `.codex/` hooks only in a trusted project. Its trust covers the matcher, so after you replace the matcher the hook doesn't run until you trust it again, and until then `solution_import` runs unchecked too.

What the gate blocks always: model-apps' `solution-settings.js import`, power-pages' `import-solution` and `deploy-pipeline`, create-site's template import, `pac package deploy`, `pac solution upgrade`, `pac pcf push`, `pac application install`, `pac code push`, `pac catalog install`, `pac app-management install-application-package`, `Import-CrmSolution` and any import in PowerShell. So are the writes of a site, a page, an app or an agent that no plan holds: `pa app push` (also through `npx` or `node_modules/.bin`, and the retired `power-apps push`), `pac pages upload`, `upload-code-site` and `migrate-datamodel` (also as `pac powerpages` or `pac paportal`), `pac model genpage upload`, `pac copilot push`, `pac copilot publish` and `pac copilot init` (also without `--environment`: Learn calls that mode a local scaffold, but the flag's own description says it then defaults to the auth profile's environment, and the gate can't see the profile), the `copilot-studio` plugin's `manage-agent` push and publish (`node …/manage-agent.bundle.js push` or `publish`, which `run-eval` runs too: its other verbs pass when they are the word after the script, and any other call to the bundle is blocked as unreadable), and pac's MCP `pages_upload`, `pages_upload-code-site`, `copilot_publish` and `model_genpage_upload`. No plan check covers these, so the gate never lets them through: when one is needed with the hooks on, the user runs it, or turns the hooks off for that step after saying yes to it. So is a Bash command with a `$'...'` word that holds an escape, such as `$'\x70ac'`, because the escapes can spell any command. A mention of an import or of `manage-agent.bundle` in a command, such as `grep "pac solution import" docs` or a commit message, is blocked too: reword it. An input over 1 MB is blocked whatever the tool.

The control that stops an import is a deny rule, not the gate: `"permissions": { "deny": ["mcp__pac-cli__solution_import"] }` in Claude Code's settings, or `disabled_tools = ["solution_import"]` in the `[mcp_servers.pac-cli]` table of Codex's `config.toml`. Deny the four write tools the same way if you never use them. The gate is defence in depth for the routes you leave open.

What it doesn't do:

- It isn't an approval, and it doesn't prove anyone reviewed the plan file. An agent that can run `deploy plan --save` can write a new plan and pass the gate with an import that matches it. The yes to an import is held where the credential is: the form of the MCP tool `deploy_apply`, which the user answers in an interactive client, or the Action's apply job in a GitHub environment with required reviewers ([deploy apply](COMMANDS.md#deploy-apply)).
- It blocks the routes it knows. A new pac command or MCP tool that installs, imports, uploads or publishes passes until the gate gets a route for it. Other tenant writes have no route either: deletes and settings changes (`pac solution delete`, `pac env update-settings` and the like), `pac model genpage add` and `remove`, `pac copilot create` and `delete`, and pac's MCP admin, environment-settings and managed-identity tools. `powerops-implement` never runs a delete: it lists a stray object in the plan's `writes.md` for the person to remove, and asks the user before each other write.
- It has no route for Fabric writes (publish, refresh, delete), and it doesn't see a write that runs no shell command and no pac MCP tool: Apply in the Copilot Studio extension for VS Code and the Copilot Studio MCP server's `manage_agents`.
- It doesn't stop a file swap. The gate hashes the call's zip and settings file before the dry run and again just before it allows the call, and refuses anything but a regular file, but `pac` opens the file after the gate exits. An agent that can write the file can still swap it in that moment: the second hash is a speed bump against an agent that runs as the same user, not a guarantee.
- It doesn't see a script file that runs `pac` itself, a command built from variables (`$PAC $s import`, or `$PA push` when `PA` holds the retired `power-apps` CLI, or `node` running its script, or `node "$S" push` when `S` holds the `manage-agent` bundle's path, or a wildcard in its name) or by another program (`xargs -0`, a Python or Node argument list, `base64 -d | sh`, `printf` with escapes such as `\160ac` piped to `sh`, PowerShell string concatenation), another tool that runs commands (an MCP terminal server, Codex's `write_stdin` into a running shell), or a server whose name no matcher names. Both clients warn about this: Claude Code's Bash rules are not a security boundary, and Codex calls hooks "a useful guardrail, not a complete enforcement boundary". That is why the deny rules above come first.

## Sign-in state

pac's MCP server uses the same `pac` auth profiles, and its tools can select another environment or profile in the middle of a session. `drift`, `deploy plan` and `deploy apply` pass the environment on every `pac` call, so a changed selection doesn't move them. `plan facts` and `settings apply` read pac's current environment, and `settings apply` refuses when it no longer matches `--target`. A switched auth profile changes the identity of every `pac` call, and the `az` account that `drift`, `deploy plan` and `deploy apply` use can differ from it.
