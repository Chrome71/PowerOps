# Hand-off to Microsoft's skills

Microsoft's [power-platform-skills](https://github.com/microsoft/power-platform-skills) and [Dataverse-skills](https://github.com/microsoft/Dataverse-skills) build apps, flows, sites and tables. PowerOps plans the work, checks what they built, plans the import and imports it. When both are installed, an agent follows the steps below: Microsoft's skill builds in Dev, and PowerOps does everything after that. In a flow that PowerOps gates, `powerops deploy apply` is the import; with the hooks in [Gate Microsoft's imports](#gate-microsofts-imports), a Microsoft import tool runs only when its call is the reviewed plan's first import. `powerops settings apply` stays the one-solution import without a plan, for use outside such a flow.

## Set up

- Install the `powerops` CLI ([Install](../README.md#install)). The skills call it.
- Add the PowerOps skills to the repo with `powerops skills install` ([Planning skills](USE-WITH-AGENTS.md#planning-skills)). In a workspace whose own tooling rewrites `.claude/skills/`, for example a sync script that deletes and recreates the folder, run it in each child project, not at the workspace root, and start the agent there: the next rewrite removes skills installed at the root.
- Install Microsoft's skills as their READMEs say.
- Sign in `pac` with `pac auth create`. PowerOps is tested with `pac` 2.13.1, and the example workflows pin 2.14.1; older builds are untested (`pac` prints its version). `drift`, `deploy plan` and `deploy apply` also need the Azure CLI signed in with `az login` ([Command reference](COMMANDS.md#drift)).

## The steps

The steps go from Dev to Test. For Prod, repeat steps 7 to 9 with Prod as the target, with its own plan and approval. Keep Prod's sign-ins away from the agent: it can use every `pac` and `az` sign-in of the operating-system user it runs as ([Sign-in state](#sign-in-state)), so sign that user in to Dev and Test only, and import into Prod through an Action apply job whose GitHub environment has required reviewers (as [the example](examples/README.md) does for Test). Where your GitHub plan gives none, run the Prod import as an operating-system user no agent runs as.

1. **Plan.** The `powerops-plan` skill turns the request into a plan in `docs/plans/<name>/` (for a plan with screens, `powerops-prototype` writes three sketches in different design directions, and you pick one or skip with a reason), `powerops-review-plan` reviews it in a fresh context, and `powerops plan sign-off docs/plans/<name>` signs it off. `powerops plan status` shows where each plan stands. Asked to build without a signed-off plan, the skills draft one and ask only the route, and the publisher prefix if the repo doesn't show it.
2. **Build in Dev.** `powerops-implement` does the plan's steps in order and hands the build work to the Microsoft skill for the product: `canvas-app` (canvas-apps), `app-builder` or `genpage` (model-apps), `pcf` (pcf), `build-flow` (power-automate), `create-site` (power-pages) or `create-code-app` (code-apps-preview). Tables, columns, publishers and solutions go to `dv-metadata` and `dv-solution` (dataverse). Build in Dev only, never in Test or Prod. After one preflight question for anything missing, the build runs without a question under the sign-off, which covers each Dev write a Step names; it stops only for a stop-list item (a sign-in, anything outside the plan, a delete, a licence, a tenant-level write, a write outside Dev or to someone the plan doesn't name, a finding only a person accepts). `powerops-implement` never deletes in a tenant, journals each tenant write it attempts in the plan's `writes.md`, and names the route of each component in its commits. It builds by its build standard, so that the solution stays easy to change: each rule in one place, changes made in place, nothing left from a failed attempt. What the next maintainer must know goes in the plan's `build-notes.md`, and each built screen is compared with the picked sketch in `design-check.md`. After the build and its final checks (step 4), `powerops-implement` starts `powerops-verify` and then `powerops-review-security`, each in a fresh context. Each writes a report in the plan folder, and neither changes the plan's status.
3. **Export, and unpack into XML only.** Export the solution from Dev, unmanaged for the source and managed for Test, and unpack the unmanaged zip into an XML folder (`Other/Solution.xml`) that you commit:

   ```sh
   pac solution export --environment <dev> --name ContosoApp --path ContosoApp.zip
   pac solution export --environment <dev> --name ContosoApp --path deploy/ContosoApp_managed.zip --managed
   pac solution unpack --zipfile ContosoApp.zip --folder src/ContosoApp
   pac solution unpack --zipfile deploy/ContosoApp_managed.zip --folder review/ContosoApp_managed --packagetype Managed
   ```

   The second unpack is the managed zip's own folder, which the two review roles read ([step 7](#the-steps)). Run it with exactly that command and no other option, into a new or emptied folder outside `deploy/` and `src/ContosoApp`.

   Keep every canvas app's `.msapp` out of Git, in every repository: it caches the URL of the environment it was made in. The two zips and the managed unpack folder (`review/ContosoApp_managed`) hold the same `.msapp` files, and the settings file of step 6 holds the target's connection ids and values. So before the first commit, add these lines to `.gitignore`:

   ```gitignore
   *.msapp
   /ContosoApp.zip
   /deploy/*.zip
   /deploy/*.settings.json
   /review/
   ```

   `*.msapp` covers the `CanvasApps/` folder of this unpack and an `.msapp` at any other path; Learn names one under `canvasapps/<name>/` in a YAML-layout folder that is packed. The default is for this step's export route. A repository bound to Dataverse Git integration gets its commits from the service. In the commits this project has seen (`tests/fixtures/powerops-seed-yaml/`) the canvas app was an unpacked `<name>_DocumentUri/` folder with no `.msapp`, which is not what Learn describes; whether that folder caches the environment's address, and whether the service honours `.gitignore`, is unproven. Git holds the rest of the unpacked source, and the zips are the artifact: keep them where the review and the import run. The [ephemeral recipe](examples/README.md#example-an-ephemeral-environment-per-pull-request), which commits its deploy zips, is the exception, for a private repository only. In this XML layout `analyze` reads a canvas app's formulas (PO014, PO018, PO036) only from its `.msapp` (the YAML layout's are read from the folder), so on the folder from Git it reads none and prints no note: check the canvas app on the zip (step 4). Git alone doesn't hold the canvas app either. Learn says a pack of the YAML layout with a declared canvas app's `.msapp` missing still succeeds and leaves the app out, and says nothing for the XML layout, so a rebuild exports again from Dev and never packs from Git ([SolutionPackager tool](https://learn.microsoft.com/power-platform/alm/solution-packager-tool), checked 2026-11-12). Because the managed unpack folder stays out of Git, `plan status` in another checkout says the report's input isn't there, which is expected. A report whose input is the folder `src/ContosoApp` reads `stale (solution)` in a checkout without the `.msapp`, because the folder digest hashes each file, the `.msapp` too. A commit you never push exposes nothing, but pushing the branch later publishes every commit on it, so keep these files out of commits from the start. A `.gitignore` entry does not stop Git tracking a file it already tracks (`git rm --cached <file>` stops it and keeps the file on disk), and a file once pushed stays in the history that was pushed.

   Never unpack into a folder in the YAML layout that Dataverse Git integration commits (`solutions/*/solution.yml`). `pac solution unpack` writes XML only, and pointed at a YAML folder with `--allowWrite --allowDelete` it added XML files beside the YAML and deleted others ([FOUNDATION section 8](FOUNDATION.md#8-research-topics-still-open)). Dataverse-skills' `dv-solution` unpacks with `pac` too, so the same rule applies to it. The managed zip can come from this export or from an export in CI, as in [docs/examples/](examples/README.md).
4. **Analyze and test.** `powerops analyze src/ContosoApp` and `powerops analyze ContosoApp.zip` (or the managed zip in `deploy/`), which holds the canvas apps, report what would break the import or a run, and `powerops test src/ContosoApp --tests flowtests` runs the flow tests that `powerops-implement` wrote or updated for each flow the plan changed. Fix errors and failing tests in Dev and export again. In CI, the Action's `tests` input runs the same tests as a required check ([Merge gate](GITHUB-ACTION.md#merge-gate-flow-tests)). Then `powerops-implement` checks the final saved version live in Dev: each flow's real trigger, a fresh load of each published canvas app, and each component's solution, with no question for the test rows and runs a Step's check names, which the sign-off covers; any other write stops for the person.
5. **Diff.** `powerops diff <old> src/ContosoApp --format markdown` compares the base branch's copy of the solution with the new one, for the pull request. The PowerOps Action puts this diff in its PR comment only when `target` is not set; with `target` (step 7) the comment holds the plan, so the diff then needs its own step.
6. **Settings.** One tool writes the deployment settings file: `powerops settings generate src/ContosoApp`, or model-apps' `solution-settings.js template`. Fill in each connection id and value, save it beside the managed zip as `deploy/ContosoApp_managed.settings.json` (the `<zip name>.settings.json` that `deploy plan` reads), and check it with `powerops settings validate src/ContosoApp --settings deploy/ContosoApp_managed.settings.json` (it checks that each connection reference has a `ConnectionId`, not that the connection exists). To keep a variable's default or current value, remove its entry instead of leaving `"Value": ""`, which `pac solution import` rejects. The file holds the target's connection ids and values, so keep it out of Git and build it in CI from repository variables, as [docs/examples/](examples/README.md) does.
7. **Plan the import in CI.** `powerops deploy plan deploy --target <test> --save deploy/powerops-plan.json` runs on the pull request (the Action's `deploy-folder` and `target` inputs write the same plan file), so the reviewer sees the import order, installs, upgrades, deletions, settings problems, flow states and each Copilot Studio agent (an `agent` warning: the import may leave it published) before approving. Save the plan file in the deploy folder: `deploy apply` reads the zips and settings files from the plan file's own folder, and `deploy plan` warns when `--save` names another folder. Run it after the two reports, and after any later build that changes the solution has run `powerops-review-security` again. The person promotes only what the reports name: each describes the folder or zip it names. `plan status` says when that solution changed since the report (`stale (solution)`), and `deploy plan` warns for each imported zip that no plan folder's two ready reports cover and prints the evidence it has ([Use from an agent](USE-WITH-AGENTS.md#the-two-build-roles)). A report covers a zip when it records the zip's SHA-256 as its `solution-hash:`, or as its `deploy-hash:` with a `solution-hash:` that equals the digest of a fresh `pac solution unpack` of that zip, which `deploy plan` runs into a temp folder and deletes. The roles write `deploy-hash:` when the request names the managed zip and the current solution is its unpack from step 3. If the digest differs although the folder is the zip's, the cause is another `pac` version, another operating system (not checked), or another unpack option (`--localize`, `--map`, `--sourceLoc`, or what a skill adds). Unpack again into a new or emptied folder with exactly the step 3 command and the `pac` version that runs `deploy plan` (in the Action, the runner's), and run both roles again ([deploy plan](COMMANDS.md#deploy-plan)). With the zips out of Git (step 3), a CI checkout holds none, and a zip that CI exports again is not the reviewed zip: no report records the new export's hash. So make this step's plan file, and run the import that checks the reports, where the reviewed zip is (the deploy folder of step 3); a plan in CI needs an export in the job, or CI exports and imports with `require-reviews: 'false'` and a GitHub environment with required reviewers, as [promote-dev-to-test.yml](examples/promote-dev-to-test.yml) does.
8. **Import.** After approval, `powerops deploy apply deploy/powerops-plan.json --target <test> --apply` (Test's id or URL, not the plan file's `target`). It plans again and refuses when an input of the plan changed since the review: a zip, a settings file, the target environment, the target's solution state as `drift` reads it, or a dependency's version. An agent runs it as `deploy apply <plan file> --target <test> --apply --require-reviews`, and only after the user said yes to that environment in the session; a pull request approval is not that yes. One yes covers one deployment, one saved plan file to one target: its import with `deploy apply` and the plan's steps there. `settings apply --apply` checks no review, so it stays the person's own command, outside that yes. It ends once they are done, and earlier on a refusal, a declined, cancelled or failed form, a re-planned or changed plan file, a changed plan hash or a blocked report; the next deployment gets its own yes. When the plan, the dry run or the MCP form names a Copilot Studio agent, the agent quotes that line in full, word for word, before it asks for the yes; a plan that forbids a published agent in that environment waits until the person has said yes to that and the plan is amended. Don't import with a skill's or an MCP tool's import: pac's MCP server (`solution_import`), model-apps' `solution-settings.js import`, power-pages' `import-solution` or `deploy-pipeline`, or Dataverse-skills' `dv-solution`. None of them checks a reviewed plan. The MCP tool, the gate and the Action import a zip only when both reports of one plan folder cover it ([deploy apply](COMMANDS.md#deploy-apply)): both are `ready`, were written for the current plan, list no open High finding and are linked to the zip, by its SHA-256 as their `solution-hash:`, or as their `deploy-hash:` with a `solution-hash:` that is the digest of the zip's `pac solution unpack`, and the folder's plan has a valid sign-off. Reports of the managed zip's unpack (step 3) are linked that way. As the fallback when that check fails and the recovery in step 7 doesn't fix it, run both roles with the zip itself as the current solution. That overwrites the folder's two reports with ones that mark roles, tables, forms and views "not verified", because a role can't read files inside a zip, so commit the folder reports first. Otherwise the person runs `deploy apply` and reads the warnings. With the hooks in [Gate Microsoft's imports](#gate-microsofts-imports), pac's MCP `solution_import` and a plain `pac solution import` can run behind the gate, and the other Microsoft imports are always blocked there. After an apply that stops, times out or leaves a row `unknown`, follow [Recovery](RECOVERY.md): there is no rollback.
9. **Confirm.** `powerops drift --solution ContosoApp --env <dev> --env <test>` compares the solution in both environments.
10. **A flow is off.** `deploy apply` reports each cloud flow's state after the import, but it can't turn a flow on, because `pac` can't. Learn names the usual causes: a connection reference with no connection, connections the importing user has no permission on (share them with that user), and a flow that already existed, which keeps its state, so a flow that was off stays off. Such a flow has usually never run, and power-automate's `debug-flow` then reports no runs and stops; decline its offer to run or test the flow. Read the flow and its connections instead (FlowAgent's `get_flow` and `list_connections`), fix the connection, and turn the flow on with a publish alone: `publish_flow`, or `manage-flows`' batch publish. Not `manage-flows`' publish-and-test, which also runs the flow. Turning a flow on is a write in that environment, and the gate doesn't see `publish_flow`, so the user's yes is the only check: that deployment's yes covers it when the plan names the step; otherwise ask first. Then run `drift` again. Sources: [Import a solution](https://learn.microsoft.com/power-automate/import-flow-solution), checked 2026-11-05, and `debug-flow` and `manage-flows` at power-platform-skills [`4076781`](https://github.com/microsoft/power-platform-skills/tree/4076781a3c6862896ad98bd51f32e180d9ddd4fd/plugins/power-automate/skills).
11. **An agent was imported.** A solution doesn't carry some of a Copilot Studio agent's settings, so set them in the target after `deploy apply`: Application Insights, manual authentication (configure user authentication again), Direct Line and web channel security, the channels it is deployed to, and sharing with makers and users. The import may leave the agent published (one live run did; Learn describes publishing as a separate step), so `deploy plan` names each agent before the import and `deploy apply` reports each one back with whether its `publishedon` is set ([deploy apply](COMMANDS.md#deploy-apply)). Publish the agent before you share it. A published agent keeps the environment variable values it was published with, so publish it again after a value changes; a secret is read at run time and needs no republish. Also check these in the target. A secret environment variable reads its Azure Key Vault secret only when the secret carries a tag for the target, `AllowedEnvironments` with the environment id or a tag with the agent's `{envId}/{schemaName}` (Copilot Studio's page calls it `AllowedAgents`, the Power Apps page `AllowedBots`), and the Microsoft Copilot Studio Service has the Key Vault Secrets User role. The target's Authentication for agents setting (preview, in the Power Platform admin center) must allow the agent's authentication, or the agent can't publish updates and stops responding. A connected agent is shared on its own: access to the main agent doesn't grant it. When you export the agent again from Dev, first add the components made since the last export to the solution (Add required objects). Each of these is a write in that environment: that deployment's yes covers the ones the plan names, though a stop-list item still stops ([powerops-implement](../skills/powerops-implement/SKILL.md) rule 7); ask first for any other. PowerOps checks none of them, and its live checks for agents (the data policy, the connection binding and evaluations) are waiting: no Copilot Studio environment has been available to build them on ([FOUNDATION section 8](FOUNDATION.md#8-research-topics-still-open)). Sources: [ALM guidance for Copilot Studio](https://learn.microsoft.com/microsoft-copilot-studio/guidance/alm), [Export and import agents using solutions](https://learn.microsoft.com/microsoft-copilot-studio/authoring-solutions-import-export) and [Variables overview](https://learn.microsoft.com/microsoft-copilot-studio/authoring-variables-about#environment-variables), checked 2026-11-04; [Use variables](https://learn.microsoft.com/microsoft-copilot-studio/authoring-variables), [Use Azure Key Vault secrets](https://learn.microsoft.com/power-apps/maker/data-platform/environmentvariables-azure-key-vault-secrets), [Authentication for agents](https://learn.microsoft.com/power-platform/admin/security/configure-authentication-controls-for-agents), [Add a connected agent](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/add-agent-connected), [Add other agents](https://learn.microsoft.com/microsoft-copilot-studio/add-agent-copilot-studio-agent) and Export and import agents again, checked 2026-11-05; Export and import agents using solutions and Agent (bot) table/entity reference, read 2026-11-09 (the publication note).

## Gate Microsoft's imports

The PowerOps skills import only with `deploy apply`, but that is an instruction to the agent: nothing in the client stops pac's MCP tool `solution_import` or the import script of a Microsoft skill. A `PreToolUse` hook can make those calls wait for PowerOps. Before each call, the hook runs [`powerops deploy gate`](COMMANDS.md#deploy-gate), which reads the call and runs the dry run of step 8. It exits 2 to block the call. Claude Code and Codex both block a call when a hook exits 2, and give its stderr (here the gate's reason) to the agent.

In Claude Code, add the hooks to the repo's `.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "mcp__pac-cli__solution_import|mcp__pac-cli__pages_upload|mcp__pac-cli__pages_upload-code-site|mcp__pac-cli__copilot_publish|mcp__pac-cli__model_genpage_upload|mcp__pac-cli__app-management_install-application-package",
        "hooks": [{ "type": "command", "onFailure": "block", "timeout": 600, "command": "powerops deploy gate \"$CLAUDE_PROJECT_DIR/deploy/powerops-plan.json\" || exit 2" }]
      },
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "onFailure": "block", "timeout": 600, "command": "powerops deploy gate \"$CLAUDE_PROJECT_DIR/deploy/powerops-plan.json\" || exit 2" }]
      },
      {
        "matcher": "Monitor",
        "hooks": [{ "type": "command", "onFailure": "block", "timeout": 600, "command": "powerops deploy gate \"$CLAUDE_PROJECT_DIR/deploy/powerops-plan.json\" || exit 2" }]
      },
      {
        "matcher": "PowerShell",
        "hooks": [{ "type": "command", "onFailure": "block", "timeout": 600, "command": "powerops deploy gate \"$CLAUDE_PROJECT_DIR/deploy/powerops-plan.json\" || exit 2" }]
      }
    ]
  }
}
```

- A pass means the call is the plan's first import: the zip and settings file are the bytes the plan holds, the environment is the one the plan was made for, no flag changes the import, and the dry run passes. It is not the user's yes: ask first, as for `deploy apply --apply`.
- The gate allows pac's MCP `solution_import` and one plain `pac solution import` with literal absolute paths. `--async`, `--max-async-wait-time` and `2>&1` are allowed; any other flag or redirection blocks. On Windows, quote `C:\...` paths ([`deploy gate`](COMMANDS.md#deploy-gate) lists the rest).
- Put the hooks into `.claude/settings.json` before you start the session that runs steps 7 and 8. Every session in the repository shares that file. Build in Dev before the hooks go in or after they come out, never while that session runs. If the hooks were edited during it, run the probe again before the next import. In the first trial, hooks added during the session never ran, although Claude Code's settings page says hook edits are normally picked up while a session runs. So before the first import, run the [gate probe](examples/gate-probe/README.md), which shows whether the hook is active without calling a tenant. With the hooks on, an import into Dev is blocked, because the plan is for the target, and so is create-site's template import. Import a plan of several solutions with `deploy apply`: the first import changes the target, so the next call fails the dry run.
- `Monitor` runs shell commands too, so it has a group like `Bash`. From Claude Code 2.1.314 a `Bash` matcher also runs on the shell commands Monitor starts (Claude Code's hooks reference and changelog say so; PowerOps hasn't tested it), so on that build both groups match; the `Monitor` group keeps older builds covered.
- `$CLAUDE_PROJECT_DIR` is the folder Claude Code started in. A hook runs in the folder of the agent's last `cd`, so `$(git rev-parse --show-toplevel)` would let an agent that ran `git init` in a subfolder point the gate at a plan file of its own.
- The first matcher names six tools of pac's MCP server: `solution_import`, the four that write a site, a page or an agent (`pages_upload`, `pages_upload-code-site`, `copilot_publish`, `model_genpage_upload`), and `app-management_install-application-package`, which installs an application package. Each name starts with the name you gave the server: `mcp__pac-cli__` for `pac-cli`, the name in Learn's `claude mcp add-json` example. For a server that a plugin provides, it is `mcp__plugin_<plugin>_<server>__`. A server with another name needs its name in all six, or its tools run unchecked. Claude Code reads a matcher of only letters, digits, `_`, `-` and `|` as a list of exact names.
- Hooks copied from an earlier version of this page match only `solution_import`, or five MCP tools without `app-management_install-application-package`. Replace that matcher with the one above, or the tools it lacks run unchecked. In Codex, trust the changed hook again afterwards (below).
- `onFailure: "block"` (Claude Code 2.1.295 or later) also blocks the call when the hook can't start or times out. Without it, both let the call through. `|| exit 2` blocks when `powerops` isn't on the `PATH`.

Codex reads the same hooks from `.codex/hooks.json` in the repo, or from `~/.codex/hooks.json`, with these changes. Its tool names turn every character of the server name and of the tool name other than a letter, a digit or `_` into `_`, so the first matcher is `mcp__pac_cli__solution_import|mcp__pac_cli__pages_upload|mcp__pac_cli__pages_upload_code_site|mcp__pac_cli__copilot_publish|mcp__pac_cli__model_genpage_upload|mcp__pac_cli__app_management_install_application_package`, which Codex also reads as a list of exact names. It has no `onFailure`, so leave it out: a hook that times out lets the call through. It has no `PowerShell` or `Monitor` tool, so leave those groups out. It sets no `CLAUDE_PROJECT_DIR`, so write the plan file's full path in its place: Codex runs hooks in the folder it started in, whatever folder the agent's command uses, and on Windows with `cmd.exe /C`, which expands no `$...`. A shell that can't parse the line (fish before 3.4, Windows PowerShell 5.1) lets the call through. Codex runs a new or changed hook only after you trust it in `/hooks`, and a repo's `.codex/` hooks only in a trusted project. Its trust covers the matcher, so after you replace the matcher the hook doesn't run until you trust it again, and until then `solution_import` runs unchecked too.

The gate passes `deploy apply --apply --require-reviews` only as one plain `powerops` command in Bash with literal words, options the command has, no value after either switch, no option twice and no redirection but `2>&1` or `>&2`; it passes dry runs and `settings apply` without `--apply`. A call it can't read that way is blocked, and so is any command whose text holds `settings apply` or `deploy apply` other than as such a call: `dotnet`, `env`, `sh -c`, a variable, a `~` path or a wildcard, dry runs included, and a mention such as `git commit -m "... deploy apply"`, `ls deploy apply` or `terraform -chdir=deploy apply`: reword it. The program word must be literal too, so `~/.dotnet/tools/powerops`, `"$HOME/.dotnet/tools/powerops"` or a path with a Windows short name such as `RUNNER~1` is blocked whatever command it runs: call `powerops` from the `PATH`. In a `settings apply` or `deploy apply` call, a word with a `^`, a `#` or a `~` after its first character blocks the call, dry runs included, because zsh can read them as glob operators. Any `powerops` command that a `(` follows or a `)` precedes is blocked too, such as one with a process substitution `<(...)`, a function definition `powerops() {...}` or a `case` arm `a) powerops ...`. In the PowerShell tool every such command is blocked, the guarded form and dry runs too, so there an agent imports through the MCP tool `deploy_apply`, which has no `settings apply` dry run, or switches to Bash. So is a Bash command with a `$'...'` word that holds an escape, such as `$'\x70ac'`, because the escapes can spell any command. So is a call that holds an import or a route after `NAME=value` words, other than a `pa app push`, because the gate doesn't read it (such a word can change `PATH`); a call with no import or route in it, such as `X=1 pac org who`, passes as before. A mention of an import or of `manage-agent.bundle` in a command, such as `grep "pac solution import" docs` or a commit message, is blocked too: reword it. An input over 1 MB is blocked whatever the tool.

The control that stops an import is a deny rule, not the gate: `"permissions": { "deny": ["mcp__pac-cli__solution_import"] }` in Claude Code's settings, or `disabled_tools = ["solution_import"]` in the `[mcp_servers.pac-cli]` table of Codex's `config.toml`. Deny the five write tools the same way if you never use them. While the hooks are on, deny the write tools of other servers the same way, by the names the client shows (`mcp__<server>__<tool>`): FlowAgent's `copy_flow`, `publish_flow` and `update_flow`, and the Copilot Studio MCP server's `manage_agents` and `manage_workflows`, whose reads go with them. The Power BI Authoring MCP server creates, changes and deletes model objects, but Learn groups its tools by object type, not by read and write, and names no tool that only writes, so a deny rule can't keep its reads and refuse its edits. Its `--readonly` flag does: on v1.0.1 it refused each change to the model, refresh start, role or permission change and `DeployToFabric` that was tried, but it still writes TMDL and BIM exports to any path given, and it does not refuse `CancelRefreshWithAPI`, which failed offline only for lack of a workspace connection (tested on 2026-11-10 against a local model, with no workspace). Give the agent Build permission only on the model, which limits the server to DAX queries, or ask first for each edit; Learn also advises a backup of the model and work in PBIP under Git. The gate is defence in depth for the routes you leave open.

What it doesn't do:

- It sees only the agent's own tool calls that the hooks match, and only while the hooks are installed: not the person's terminal, the MCP tool `deploy_apply` (which always checks the reviews itself) or the Action.
- It isn't an approval, and it doesn't prove anyone reviewed the plan file. An agent that can run `deploy plan --save` can write a new plan and pass the gate with an import that matches it. The yes to an import is held where the credential is: the form of the MCP tool `deploy_apply`, which the user answers in an interactive client, or the Action's apply job in a GitHub environment with required reviewers ([deploy apply](COMMANDS.md#deploy-apply)).
- It blocks the routes it knows. A new pac command or MCP tool that installs, imports, uploads or publishes passes until the gate gets a route for it. Other tenant writes have no route either: deletes and settings changes (`pac solution delete`, `pac env update-settings` and the like), `pac model genpage add` and `remove`, `pac copilot create` and `delete`, `pac copilot quarantine` and `merge-translation` (which change an agent's quarantine status and its translated text), `pa app share` and `pa connection create` (which share a code app and create a connection), `pa app add data-source` (Microsoft's code-apps plugin says that from Power Apps CLI 1.3.0 it can create a connection when the connector has none, without asking first; Learn's CLI reference doesn't say so, and PowerOps hasn't tried it), pac's MCP admin and environment-settings tools, and the commands and MCP tools of pac's 16 preview groups, which pass the gate: `power-pages` (in a Bash or Monitor command, `pac power-pages upload-certificate` written plainly, with the two subcommand words second and third, no option before them and no `NAME=value` in front, passes too; the PowerShell tool blocks every `pac` call), `copilot-studio`, `environment-management`, `authorization`, `governance`, `licensing`, `dynamics`, `workflows-agent`, `analytics`, `user-management` and `managed-identity` hold writes (such as creating and deleting a website, deleting an agent, copying, resetting and deleting an environment, creating and deleting role assignments and data policies, billing policies, applying a Finance and Operations version, and giving a user the system administrator role); in `app-management` the install is routed above and its three reads pass; and `connectivity`, `power-apps`, `power-automate` and `resource-query` only read. `pac` 2.14.1 lists 222 preview MCP tools in these 16 groups, and the deny rules above are the control for them. `powerops-implement` never runs a delete: it lists a stray object in the plan's `writes.md` for the person to remove, and stops for each write outside the signed plan and for each delete, licence, tenant-level or admin write, even one a Step names.
- It has no route for Fabric writes (publish, refresh, delete), and it doesn't see a write that runs no shell command and no pac MCP tool: Apply in the Copilot Studio extension for VS Code, the Copilot Studio MCP server's `manage_agents` and `manage_workflows` (each action can read or write), the Power BI Authoring MCP server's model edits, and FlowAgent's `copy_flow` to another environment and its `publish_flow` and `update_flow` outside Dev. Those FlowAgent calls move or change a flow in Test or Prod with no reviewed plan, and Learn's page for the plugin gives copying a flow to the test environment as an example.
- It doesn't stop a file swap. The gate hashes the call's zip and settings file before the dry run and again just before it allows the call, and refuses anything but a regular file, but `pac` opens the file after the gate exits. An agent that can write the file can still swap it in that moment: the second hash is a speed bump against an agent that runs as the same user, not a guarantee.
- It doesn't see a script file or a shell function that runs `pac` or `powerops` itself, a quote inside a nested string, such as `bash -c '... settings ap""ply ...'`, words after a `#` comment that holds a quote (the gate doesn't read comments, so the quote runs on into the next line), a command built from variables (`$PAC $s import`, or `$PA push` when `PA` holds the retired `power-apps` CLI, or `node` running its script, or `node "$S" push` when `S` holds the `manage-agent` bundle's path, or a wildcard in its name) or by another program (`xargs -0`, a Python or Node argument list, `base64 -d | sh`, `printf` with escapes such as `\160ac` piped to `sh`, PowerShell string concatenation), another tool that runs commands (an MCP terminal server, Codex's `write_stdin` into a running shell), or a server whose name no matcher names. Both clients warn about this: Claude Code's Bash rules are not a security boundary, and Codex calls hooks "a useful guardrail, not a complete enforcement boundary". That is why the deny rules above come first.

## Sign-in state

pac's MCP server uses the same `pac` auth profiles, and its tools can select another environment or profile in the middle of a session. `drift`, `deploy plan` and `deploy apply` pass the environment on every `pac` call, so a changed selection doesn't move them. `plan facts` and `settings apply` read pac's current environment, and `settings apply` refuses when it no longer matches `--target`. A switched auth profile changes the identity of every `pac` call, and the `az` account that `drift`, `deploy plan` and `deploy apply` use can differ from it.
