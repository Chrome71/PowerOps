#### R1. The one app, a System Administrator in Test and Dev, can be used from the unprotected `test-plan` environment, so the `test` reviewers can be bypassed
- Area: 8. Security roles; 5. Dev to Test to Prod route
- Finding: The plan keeps M9's single Entra app, adds it as an application user with System Administrator in Test (M9) and in Dev (this plan), and gives it federated credentials for two GitHub environments: `test-plan` (no reviewers) and `test` (required reviewers). A `pull_request` run uses the workflow file from the PR, so anyone who can push a branch to the repository can put a step in the plan job, sign in as that app through `test-plan`, and run `pac solution import` into Test (or do anything else a System Administrator can do in Dev and Test) with no reviewer. The `test` gate then protects only the job that the PR author chose to put behind it. M9's README example says the opposite ("give the app registration of the plan job a read-only role in the target, not an administrator role") and M9 review R2 raised the same point; M10 makes the one app an importer and the plan names no second app. `test-plan` also holds the same value secrets (the connection id, the variable values) as `test`, so a branch pusher can read them too (log masking is exact-match; a step can encode a value). That last part cannot be removed while both jobs must build the same settings file bytes (R6), but it is not stated. The admin question about the minimum role (M9) is not repeated for the Dev export and the Test import. For the owner-only test repo this is an accepted risk; the example is the flagship docs for "a plan reviewed in the PR" and "required reviewers", and as written it teaches a gate that can be bypassed.
- Suggested fix: In the example and its README use two app registrations: a plan app (federated credential for `test-plan` only; application user in Dev with the role the export needs and in Test with a role that can read but has no import right, the minimum to be recorded in the live check) and an apply app (federated credential for `test` only; application user in Test only, with the role the import needs). If the live check keeps one app, say in Environments and route that this is test-only, and put the two-app setup in `docs/examples/README.md` with the reason. State that value secrets in `test-plan` are readable by anyone who can push a branch, so they must hold configuration (connection ids, URLs), never credentials; advise CODEOWNERS or a ruleset on `.github/workflows/`, and "Prevent self-review" on `test`. Add the minimum-role question to `Questions for your admin`.
- Resolution: fixed (the docs teach two app registrations, configuration-only secrets in `test-plan`, CODEOWNERS or a ruleset, Prevent self-review and a required plan check; the live check keeps one app in the owner-only test repo and says it is test-only; the minimum-role question added)

#### R10. Output channels and log hygiene of `deploy apply`

(e) The dry run shows the `pac` arguments; the paths in them must be file names, not the runner's folder path (M9: no folder path in output).
- Suggested fix: Prefix forwarded `pac` text with a fixed marker that cannot match `^error:`. Print one names-only progress line per import (before and after) to stdout and have `apply.sh` also print the report to the log, not only to the summary. Put the report in a code fence longer than any backtick run, and pass every name from the plan file through `TextReport.Clean` and the safe-name rule. Reuse the timeout text. Show file names in the arguments. Tests for each.
- Resolution: fixed (forwarded lines prefixed with two spaces and a bar; progress lines; the report in the log and in a long code fence; every name from the plan file through the safe-name rule and `TextReport.Clean`; the timeout text reused; file names in the dry-run arguments)
