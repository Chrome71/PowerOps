# Decisions: m24-mcp-inputs

## Round 1

### Q1. How is an unpaired surrogate in a tool's arguments refused as a tool error?
1. An incoming message filter in `McpCommand.Options` tries to write the `tools/call` parameters back as JSON text and, when that throws, answers the request with a tool error (`isError`, one `error:` line); the other rules stay in `Check` (recommended)
2. Leave the SDK's JSON-RPC error -32603 for this one input and say so in the docs; control characters, length and list caps stay in `Check`
3. In your own words
Answer: The filter. The row's mechanism, catching `InvalidOperationException` from `GetString()` in `Check`, never runs for a lone surrogate: the probe showed the SDK failing the request with -32603 before any handler, for a value, a list item and a key, at both revisions. The BUILD-PLAN row asks for a tool error, and a generic protocol error gives an agent nothing to act on. The filter is about 20 lines in the options every server is built from, so the tests cover it. Changed after review R1: a result sent from a filter bypasses the SDK's `resultType` stamp, and 2026-07-28 requires the key, so the filter stamps `"complete"` at 2026-07-28 or later and not before, reading the revision from `request.Context?.ProtocolVersion` as the SDK does, and a raw-pipe test asserts the key at 2026-07-28 and its absence at 2025-06-18.

### Q2. Does M24 stop the server from hanging on an unanswered form when its input closes?
1. Yes: `McpCommand.Serve` cancels the run when the transport's reader completes, and the `mcp` action uses it
2. No: M24 documents it as a residual, and the S-8 test covers the running-import case only (recommended)
3. In your own words
Answer: No, option 2 (changed after review R2: the row asks only for the test because the host waits; the fix would cancel every running call). The probe found the hang: under revision 2025-06-18 a form the client never answers kept the process running 12 s after stdin closed, until it was killed; under 2026-07-28 the form is a result and nothing hangs. Cancelling the run token at end of input ends it, but it cancels every handler still running, not only the form: a `deploy_plan` with `save` in flight would skip its save, and a `deploy_apply` between the yes and the import would be refused. The S-8 row asks only for a test of what the host does when stdin closes, and the host waits for a running handler, so the import case needs nothing. The hang is named as a residual in the MCP section of `docs/USE-WITH-AGENTS.md` and in the M24 row's Built bullet ("Accepted:"), with a line that a later change could end the form's wait alone at end of input.

### Q3. Does M24 narrow URL-shaped `target` and `envs` values, for S-3?
1. No: Learn says a token's audience is one URL and says nothing on whether Dataverse refuses it at another org, so the S-3 row's rule applies. The host suffix check stays, the answer and its sources go in the verification record, and the residual goes in the MCP section of `docs/USE-WITH-AGENTS.md` (recommended)
2. Yes: refuse, in the tool, a URL-shaped value whose host is not a documented Dataverse host, before `pac` is called
3. In your own words
Answer: No. Learn does not say such a token works at another org, so the stop condition of decision Q11 is not met. Option 2 would narrow tool inputs, which Q11 keeps for the user; it is not taken under the delegation below. If the user wants it, it is a later change of its own. What the checks do not show, and a live read would be needed for: what `pac org who --environment <value>` does with a URL on a host that is not Dataverse. This plan does not run it.
