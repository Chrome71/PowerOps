# M100: Secret-handling rules for Text environment variables and flow actions

## Goal

Practitioners report secrets kept in plain Text environment variables, and secrets passed through flow actions whose run history shows them; no `analyze` rule finds either. This milestone adds two Warning rules: PO041 (a Text environment variable whose schema name looks like it holds a secret) and PO042 (a flow action that reads a secret without secure outputs, or an HTTP action with an `authentication` block without secure inputs). PO042 needs four small fields on `FlowAction`, the per-action record M99 added. This is milestone M100 of the upgrade plan drawn from the practitioner research (its section "M100. Secret-handling rules").

### Won't build

- The literal key in a header or URL (the upgrade plan's PO050): it fires on the frozen eval's pilot case and belongs to M111. `FlowAction` gets no header names and no values.
- The no-failure-path rule (PO049): M111.
- Reading a secret through anything else: the Key Vault `DecryptData` actions, a custom connector, a legacy `ApiConnection` Key Vault action (no `operationId`), a child flow's output. The upgrade plan names the two reads below; the others are noted as not checked on PO042's page.
- A check of a Text variable's value (its default or current value). PO041 reads the type and the schema name only, and never prints a value. PO008 already reports a shipped current value.
- An exception for an `Http` action whose credentials come only from a secret read with secure outputs. Logic Apps hides the inputs of an action that uses secured outputs, so such an action's credentials may already be hidden; PO042 still fires there (a known, accepted false-positive class, accepted with `powerops baseline`), because Microsoft's own walkthrough turns on the HTTP action's secure inputs as well, and the rule can't tell what an expression reads.
- Narrowing PO042's `authentication` test by authentication type (for example a managed identity, which holds no secret). The upgrade plan says "an `authentication` block"; Power Automate's HTTP action rarely uses a managed identity, and a finding is accepted with `powerops baseline`.

## Users

- A maker or an agent who runs `powerops analyze` (or the MCP `analyze` tool) on an export before a deployment and reads a warning that names the variable, or the flow and the action, to change.
- A reviewer who fixes it as the rule page says, or accepts the finding with `powerops baseline`.
- The sessions that build M107 (`inventory`) and M111, which read `FlowDefinition.Actions` next.

## Assumptions

Each Microsoft claim was checked on 2026-11-12 by `powerops-researcher` (Opus, Learn only; Log has the details):

- Types. The Dataverse `type` column of `environmentvariabledefinition` has `100000000` String (Text in the maker UI) and `100000005` Secret (*environmentvariabledefinition table/entity reference*). That the export's `<type>` element holds the same numbers is not on Learn; it is observed in every fixture and eval case (`alm-sample`'s Secret variable holds `100000005`, `alm-makers`' Text variable `100000000`).
- Text is not for secrets. Learn says a Text variable used for a custom connector's client secret "isn't secure", its values not encrypted, and recommends Key Vault (*Use environment variables in solution custom connectors*); no page says so for Text variables in general. The Secret type reads its value from Azure Key Vault (*Use environment variables for Azure Key Vault secrets*). That an export holds a Text variable's default value as written is observed (`defaultvalue` elements in the fixtures), not stated on Learn. The table reference also lists a Dataverse secret store; PO041's `Fix` names Key Vault, the store the maker page documents.
- Secure inputs and outputs keep data out of run history (*Secure data used in cloud flows*, Power Automate). The definition records them as `runtimeConfiguration.secureData.properties`, an array of `inputs` and `outputs` (*Secure access and data for workflows in Azure Logic Apps*; *Schema reference guide for trigger and action types*); no Power Automate page shows the JSON, and the same key is observed in exports: `alm-makers` (public) and the eval cases. The same Logic Apps page says an `Authorization` header is not shown by default and an action that uses secured outputs as inputs has its inputs hidden; Learn does not say whether Power Automate's run history shows the fields of an `authentication` object, so PO042's second message states only that the block exists and secure inputs are off.
- Reads of a secret. The Dataverse action `RetrieveEnvironmentVariableSecretValue` returns a Secret variable's value (*RetrieveEnvironmentVariableSecretValue Action*); a flow calls it with the Dataverse connector's *Perform an unbound action*, operation `PerformUnboundAction` with parameter `actionName`, or `PerformUnboundActionWithOrganization` (*Microsoft Dataverse* connector reference); `shared_commondataserviceforapps` is observed in fixtures. The Key Vault connector's *Get secret* is `GetSecret` and *Get secret version* `GetSecretVersion`, whose outputs Learn calls secret and visible in run history (*Azure Key Vault* connector reference). The Key Vault connector's id is not on Learn (it shows the path `keyvault`); it is observed as `/providers/Microsoft.PowerApps/apis/shared_keyvault`, the `connectorid` of a connection reference in a public export (`pnp/powerplatform-samples`, `samples/varify-bot/sourcecode/VARify/src/Other/Customizations.xml`, commit `2956844`, read 2026-11-12). That sample has no flow that calls it, so the `inputs.host.apiId` of a Key Vault action is inferred from the observed rule that an action's `apiId` equals its connector's `connectorid` (every connector in `alm-makers`); a wrong inference costs a missed finding, never a false one, and a live export with a Key Vault action is a follow-up in the handover.
- Microsoft's own walkthrough turns on secure outputs on the action that reads the secret and secure inputs on the HTTP action that sends it (*Use environment variables for Azure Key Vault secrets*, steps 9 and 15), which is PO042's `Fix`.
- `docs/ecosystem/`: no `compatibility.md` row covers environment variables, Key Vault, secure data or the Dataverse connector; of the open `changes.md` entries only ECO-0009 mentions environment variables (model-apps creating them), not their type or secrets.
- The leak scan is `reports/leakscan.sh` in the main checkout (git-ignored), run from there as `bash reports/leakscan.sh origin/main claude/m100-secret-rules-842730`.
