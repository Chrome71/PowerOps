# M73: An agent in the import is named before every yes, and `deploy apply` reads the agents back

## Goal

Fix finding F41 of the PowerOps 1.0 trial (2026-11-08), as section 3 of the agreed 1.0 fix plan sets out (Fable and Astra, six rounds; amendments A1, A2, F-1, F-2):

| Id | Finding | This plan |
|---|---|---|
| F41 | `deploy plan` said "plan ok" for a zip that held a Copilot Studio agent, and the managed import left the agent with `publishedon` set in Test. No route named that effect before the yes: `DeployPlan.Build` ignores `Solution.Agents`, the MCP form (`McpCommand.cs:343`) names only the target, the hash and the zips, and `deploy apply` reads back flow states only. It returns before any read when the plan has no flows (`DeployCommand.cs:428-431`) and after a partial failure (`:419-425`) | `deploy plan` names each agent with a warning (row 1); the `deploy apply` dry run, the MCP form, `deploy gate` and `powerops-implement` step 7 show it before the yes (rows 6, 8, 9, 10); `deploy apply --apply` reads each imported agent back (rows 3 to 7) |

The person's answer to Q6 (Round 0 in `decisions.md`, "Keep no-publish") stands: in the second trial the agent-bearing import stays refused, so the trial exercises only the refusal path. The read-back is still built and tested offline here.

Done when:

1. `deploy plan` on a folder whose zip holds an agent and is installed or upgraded gives one `agent` item per agent, severity `warning`, with the item sentence of row 1 (`PlanKind.AgentEffect`), and `blocked` stays false; the summary line names the agents instead of a bare "plan ok". A skipped zip, or a zip with no agent, gives none. `deploy plan`'s JSON is at `schemaVersion` 2, and `deploy apply` reads only plan files of version 2.
2. The `deploy apply` dry run lists each agent of a zip it would import, in text and JSON. The MCP form's message names each agent with the form sentence of row 8 (`McpCommand.AgentFormNote`), and a declined form makes no import call. When `deploy gate` blocks a call after its dry run passed, its stderr carries one line per agent item.
3. `deploy apply --apply` reads the agents of every solution whose import went through (`ok`) with one `bot` read, also when the plan has no flows and after a partial failure. The report's `agents` gives each one `found`, `missing` or `not-read`, and `publishedOn` (whether `publishedon` is set) for a found one. The read-back never changes `status`, `message`, the solution rows or the exit code. A failed flow read keeps today's message and exit code, and the agents are still read.
4. `powerops-implement` step 7 tells the agent to quote the `agent` line to the user before asking for the yes, and to stop under rule 6 when the plan forbids a published agent in that environment.
5. `docs/COMMANDS.md`, `docs/HANDOFF.md`, `docs/FOUNDATION.md`, `docs/GITHUB-ACTION.md`, `docs/schemas/README.md`, `deploy-plan.schema.json` and `deploy-apply.schema.json` say what changed. The `deploy-plan-*` and `deploy-apply*` goldens and the plugin skill copies are updated by the recipe.
6. `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status docs/plans/m73-agent-import` and the leak scan are clean. The work is committed locally on the session's branch.

### Won't build

- A `block` severity, or a "publish allowed" flag. PowerOps can't tell a no-publish plan from another. Each route already stops for the person's yes, and the text makes that yes informed (fix plan, "Rejected").
- Reading `componentstate`, `ismanaged`, `publishedby` or any other `bot` column. `publishedOn` means only that `publishedon` is set (Assumptions).
- A read of the agents before the import. So for an upgrade, or an agent the target already held, `publishedOn: true` doesn't show what the import did (Assumptions; the docs say so).
- A message on a call `deploy gate` lets through. A hook that exits 0 shows nothing to the person; the plan, the dry run, the form and step 7 carry the agent line. A later milestone could have the gate answer Claude Code's `ask` decision with the line where the client supports it (not checked for Codex).
- Keeping the agent row in a Markdown report that hits its size cap. The items table follows the solutions table, which has one row per zip, so the cut reaches it only past hundreds of zips; the summary line (row 1) and the cut note still show.
- Reading flows back after a partial failure. Flows stay as today: no read after a failed import.
- Reading the agents of a solution whose import timed out (`unknown`). [Recovery](../../RECOVERY.md) covers that case.
- A Dataverse capture of the `bot` read. This milestone is offline: the sample response is made for this project from Learn's `bot` table page and is marked as made, not captured.
- Any change to `action/plan.sh` or `action/apply.sh`. The plan job copies the Markdown report, whose items table already holds every item, into the job summary and the PR comment. The apply job copies the text report, which gains the agent lines (row 7).
- Turning a published agent off, or unpublishing it. That is a tenant write.

## Users

- A maker or reviewer reading `deploy plan` (the PR comment, the job summary or the CLI) before approving an import into Test.
- The person answering the MCP form of `deploy_apply`, or an agent following `powerops-implement` step 7.
- Whoever reads the `deploy apply` report after an import, to see whether each agent landed and whether `publishedon` is set.

## Assumptions

- A solution import may leave an agent with `publishedon` set: observed once (2026-11-08, a managed import into Test), not stated by Learn. *Export and import agents using solutions* (read 2026-11-09) says to publish the imported agent before it can be shared, so it describes publishing as a separate step; *Configure and deploy agents from the Agent Library* (read 2026-11-09) says imported agents aren't published automatically, for Agent Library templates only. *Upgrade or update a solution* (read 2026-11-09) says managed customizations are always imported in a published state, which is the solution layer's state, not Copilot Studio's publish. So the message says "may" and cites both (claim a).
- `bot.publishedon` is "Date and time when the agent was last published", a DateTime column that can be read, created and updated (*Agent (bot) table/entity reference*, read 2026-11-09). Because it can be written, an import may carry it; so `publishedOn` means only that the column is set, not that someone published the agent in the target (claim b).
- The entity set is `bots` and `schemaname` is a string of at most 100 characters described as the unique name of the agent (same page). Learn gives no character set and lists no unique key, so a name outside letters, digits and underscores, or over 100 characters, is reported `not-read` without being sent, and two rows with one name reject the read (claim b).
- There is one read, after the import. For a first install `publishedOn: true` means the import carried a set `publishedon`; for an upgrade, or an agent the target already held, it may have been set before, so it doesn't show what the import did.
- The `bot` read has not run against a tenant: the query and the sample are built from Learn's `bot` page and read 8's live `in` query. If the read answered 200 with no rows for another reason than "no such agent", every agent would show `missing` and nothing would fail; the docs call `missing` a prompt to check. A first live capture (a read-only probe, or the first authorized import) is a follow-up outside this milestone; under Q6 trial 2 doesn't run it.
- System Administrator and System Customizer read all `bot` rows; Environment Maker reads only the agents it owns or that are shared with it (*Secure your Copilot Studio projects*, read 2026-11-09). So `missing` means the query returned no row for that name, which also happens when the reading account can't see that agent; the docs say so (claim b).
- No documented import option controls or prevents an agent's publication: `pac solution import`'s flags (*pac solution*, read 2026-11-09) name none, and `--publish-changes` is the generic publish of customizations. The full parameter lists of `ImportSolution` and `StageAndUpgrade` were not read (claim c; Q6 is why trial 2 tests only the refusal).
- The dry run's report is computed from the zips the plan hash covers, so the MCP form takes the agents from it rather than from the plan file, whose items the hash doesn't cover.
