# M81: Skill fixes that need no eval

## Goal

Fix three findings of the PowerOps 1.0 trial (2026-11-08) in the planning and build skills, as section 3 ("M81") of the agreed 1.0 fix plan sets out (Fable and Astra, six rounds; amendment A11 closed it):

| Id | Finding | This plan |
|---|---|---|
| F10 | `powerops-implement` forbids probing sign-ins: it asks the person about each of five sign-ins and says "you do not run `pac` or `az` to find out". In the trial the build session asked questions a status call would have answered | Before the first build step the skill probes each sign-in the plan's routes need with a read-only status call, reports each as available or missing with no account detail, and asks the person only for a missing one (rows 1 and 2) |
| F4 | The plan skill's engagement rule treats option-number answers as low engagement, so a person who answers through the choice tool is moved to a shallower depth | Answers picked from the options, by number or through the choice tool, no longer lower `depth`; only "just pick", "whatever you think" or a request to speed up do (row 4) |
| F35 | No step checks that a skill, CLI or MCP tool a plan step names can be called, so a plan can rest on a tool that isn't installed | The plan skill's `Steps` rule checks each named tool and names one that isn't callable in Assumptions; the `powerops-review-plan` checklist gets the same item (rows 5 and 6) |

Done when:

1. `skills/powerops-implement/SKILL.md` section 3 step 3 holds the probe of row 1 in place of the sign-in question, and section 4 step 2 refers to it (row 2).
2. `skills/powerops-plan/SKILL.md` holds the engagement rule of row 4 and the `Steps` rule of row 5, and stays within its word ceiling (row 7).
3. `skills/powerops-review-plan/SKILL.md` holds checklist item 12 of row 6.
4. `SkillsCommandTests` pins the new wording and fails on the old (row 7); the smoke script has the two new scenarios of row 8 and passes `bash -n`.
5. `docs/PLANNING-SKILLS.md` says what changed (row 9); the plugin copies are regenerated by the recipe "Update goldens" (row 10).
6. `dotnet build` (0 warnings), `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status docs/plans/m81-skill-fixes` and the leak scan are clean.

### Won't build

- A PowerOps command that probes sign-ins. The fix plan rejected it: the status calls already exist, and a new command would be one more thing to install and keep current.
- A probe that proves a sign-in still works. A status call reads a local cache; a token that has expired since shows up as a failure at the first real call, which the skill already stops on.
- Running the smoke script here. It calls the agent CLIs on every scenario and costs model credits; it runs weekly in CI (`.github/workflows/skills-smoke.yml`). M77 did the same.
- Any change to `powerops-verify`, `powerops-review-security`, their plugin copies or `tests/eval`. Those are frozen; M81 needs no eval (fix plan: "Frozen role. No.").

## Users

Makers who plan and build with the PowerOps skills in Claude Code or Codex. The build session reports its sign-ins without asking (F10); a person who answers by option number keeps the depth they had (F4); a plan names only tools the agent can call, or says which it couldn't (F35).

## Assumptions

- The fix plan's line numbers predate M73 to M78; the text above was found by content on `main` `278b136`.
- The probe's output enters the agent's context even though it is never repeated: `pac auth list` prints each profile's account and environment, which the design's "the agent should never see those" (PLANNING-SKILLS, Environment facts) was written to avoid. The fix plan accepted this when it chose `pac auth list` and rejected a PowerOps command; `az account show -o none` keeps `az`'s details out of the agent's context.
- Researcher, 2026-11-09 (Learn and Azure/azure-cli, details in `decisions.md`): `pac auth list` lists "the authentication profiles stored on this computer", with columns Index, Active, Kind, Name, Friendly Name, Url (the environment URL) and User (a UPN); Learn documents neither its output nor its exit code with no profile, so row 1 counts a probe that fails or lists nothing as missing. `az account show` reads only the local profile cache (`Profile.get_subscription`), and with no account raises "Please run 'az login' to setup account."; `-o none` prints "no output other than errors and warnings"; that the exit code survives `-o none` is inferred, not stated.
- A status call reads a local cache, so "available" means a profile or account exists, not that its token still works (refuted for `az`, not documented for `pac`).
- `command -v` is POSIX and `Get-Command` is PowerShell's; neither runs the tool it looks for.
- Smoke scenarios 7 and 8 build plans that say "No Microsoft skill, pac, az or Python is used", so the probe should run nothing and ask nothing there; on Claude `pac` and `az` are not allowed tools in them anyway. Both should pass in the same number of turns or fewer. Not run here.
- `pac auth list` exits 0 with no profile (observed in the M32 runbook, `docs/BUILD-PLAN.md`), so the probe reads its output rather than its exit code; that is why the output reaches the context.
