# M115: PowerOps's own imports leave the agent's yes, and the gate blocks the unguarded ones

## Goal

Carry out decision 3(a) of the review-enforcement audit (2026-11-13; `decisions.md` Q1) and its finding C-2. Today an agent's `powerops settings apply --apply`, which imports a zip with no review check at all, sits inside the person's one yes per deployment (decision 67), and both it and a `powerops deploy apply --apply` without `--require-reviews` pass `deploy gate` (the audit's reproductions G01 and G02 exit 0). After this milestone the text gives an agent no yes for `settings apply --apply` (it becomes the person's own command, as decision 16(c) already uses it outside a gated flow), an agent's `deploy apply --apply` always carries `--require-reviews`, and the gate's deny-list (decision 41's pattern in `ImportCall.cs`) blocks both unguarded forms in an agent's hooked shell call. Separately, the implement skill stops calling Power BI's missing solution checks "not applicable" and calls them "not covered by PowerOps", a gap the person accepts by name.

1. `deploy gate` exits 2 with the route line of Data row 1 for each blocked form of row 3 (a), and exits 0 without reading the plan or the target for each passing form of row 3 (b); the forms of row 3 (c) block as unreadable. `ImportCallTests` and `DeployGateCommandTests` hold a row for each.
