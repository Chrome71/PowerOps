# M59: A wider flow simulator set: float, the hour, minute and second adders, time-zone conversion, startOfDay and dayOfWeek

## Goal

Let `powerops test` run flows that use the date functions makers reach for after `addDays`, and `float`. This is M59 of the improvement plan written after the live test of 2026-11-04 (P1; it closes C-2, "the simulator's function set is narrow"). The plan and the person's answers to its decisions are kept outside the repo, because they quote a private test run. M58 added `formatDateTime`, `int` and `addDays`'s format, compared the simulator with one cloud run, and left the rest of the date set to this milestone (`docs/plans/m58-flow-conformance/plan.md`, "Won't build"). Today `addHours(utcNow(), 1)` and every function below make a flow test `unsupported` (`ExpressionFunctions.cs:22-76`, `docs/FLOW-TESTS.md:30`).

The rule from M14 and M58 holds: what Learn doesn't settle is `unsupported`, never a guessed value. The capture of 2026-11-05 (`tests/fixtures/flowtests/capture/`) holds no call to any of the eight functions, so every value here comes from Learn's function reference, from .NET's format and time-zone behaviour that the reference links to, or from what the capture showed about the service's timestamp reading (decisions Q1). Nothing is compared with a new cloud run: a capture needs the person's yes in Dev and is optional for this milestone (decisions Q13).

Done when:

1. `float`, `addHours`, `addMinutes`, `addSeconds` (each with its format argument), `startOfDay`, `dayOfWeek`, `convertFromUtc` and `convertTimeZone` are simulated where Learn's sections state a result, each tested with the examples of its section on Learn's expression functions reference (rows 1 to 6), and every form Learn leaves open is `unsupported`, as listed under "Not on Learn" and in `decisions.md`.
2. Time zones take Windows names, such as "Pacific Standard Time", and the conversion gives the same result on Windows and Linux: CI's Windows and Linux jobs run the same tests, which check Learn's examples, daylight-saving boundaries in a North American, a European and an Australian zone, and 16 zones at two instants of 2026, each against one fixed expected value (row 7). Names .NET reads on one platform only (IANA names such as `America/Los_Angeles`, other casing) are `unsupported` on both.
3. The pinned list test holds the 47 names; `docs/FLOW-TESTS.md` lists every supported function with every argument form it takes and the rules for the new ones; the test that compares that list with `ExpressionFunctions.Names` passes (rows 8, 9).
4. The tests that used `addHours` as their example of an unsupported function use `dayOfYear` instead, and the `test-failures.*` goldens change by the recipe; `CaptureTests` passes unchanged; the eval baselines in `tests/eval/roles/baseline/` are unchanged (row 8).
5. `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status .` and the leak scan are clean; the PR is green on all eight checks. Not merged by this session.

- A new capture in Dev: optional, needs the person's yes, skipped here (decisions Q13). Nothing in a tenant is created, changed or deleted.

### Not on Learn

The simulator's choices in this milestone, each a case for a later capture:

- `addHours`, `addMinutes` and `addSeconds` read a timestamp as `addDays` does: an offset converted and written `+00:00`, no zone kept (decisions Q1). The capture showed it for `addDays` only.
- `startOfDay` keeps no zone on a timestamp with none (decisions Q2), and `dayOfWeek` takes its date as written.
- A timestamp with no zone in `convertFromUtc` is UTC, and in `convertTimeZone` a time on the source zone's clock (row 5).
- The conversion's result format uses `en-us`, as `addDays`'s does (M58 decisions Q4, confirmed by the capture for `addDays`).
- Windows ids with punctuation (`W. Europe Standard Time`, `Central Standard Time (Mexico)`, `UTC-11`) are taken as Windows writes them. Learn's convertTimeZone section says "you might have to remove any punctuation from the time zone name"; the Default Time Zones page it links to writes the dots, and its own DISM example sets `W. Europe Standard Time` (decisions Q4).
- `float` with no locale reads like en-US; `float` of a number gives that number; a float with no fraction is written `14.0` and is not an integer anywhere one is needed; the double type stands for Learn's "float data type" (decisions Q10 to Q12).
- What this milestone makes `unsupported` and a capture could settle: an offset in `startOfDay`, `dayOfWeek` and both conversions; `Z` with a source other than `UTC`; a skipped or repeated clock time; an instant before 2007; the destination `UTC` with `o`; a time-zone name in another casing, an IANA name, `Türkiye Standard Time`; `float` with a space, an exponent, parentheses, `NaN`, infinity, a locale other than `en-US` and `de-DE`.
- Time-zone data: Windows' on Windows, the IANA database through ICU's mapping on Linux (decisions Q5). The service's data is not on Learn; the tests pin the 2026 rules of 16 zones on both CI platforms.

## Assumptions

- Learn's expression functions reference, read 2026-11-05 from its published source (the page's `ms.date` is 07/21/2026): `addHours`, `addMinutes`, `addSeconds('<timestamp>', <amount>, '<format>'?)`, the amount Integer, the format "either a single format specifier or a custom format pattern", default `o`, "If the format isn't a valid value, an error is generated"; examples `addHours('2018-03-15T00:00:00Z', 10)` gives `"2018-03-15T10:00:00.0000000Z"`, `addHours('2018-03-15T15:00:00Z', -5)` gives `"2018-03-15T10:00:00.0000000Z"`, `addMinutes('2018-03-15T00:10:00Z', 10)` gives `"2018-03-15T00:20:00.0000000Z"`, `addMinutes('2018-03-15T00:20:00Z', -5)` gives `"2018-03-15T00:15:00.0000000Z"`, `addSeconds('2018-03-15T00:00:00Z', 10)` gives `"2018-03-15T00:00:10.0000000Z"`, `addSeconds('2018-03-15T00:00:30Z', -5)` gives `"2018-03-15T00:00:25.0000000Z"`. `startOfDay('<timestamp>', '<format>'?)`, same format text, example `startOfDay('2018-03-15T13:30:30Z')` gives `"2018-03-15T00:00:00.0000000Z"`. `dayOfWeek('<timestamp>')`, an Integer "where Sunday is 0, Monday is 1, and so on", example `dayOfWeek('2018-03-15T13:27:36Z')` gives `4`. `convertFromUtc('<timestamp>', '<destinationTimeZone>', '<format>'?)`, names from "Microsoft Windows Default Time Zones", same format text, returns "The timestamp converted to the target time zone without the timezone UTC offset";
