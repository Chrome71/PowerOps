# M59: A wider flow simulator set: float, the hour, minute and second adders, time-zone conversion, startOfDay and dayOfWeek

## Goal

Let `powerops test` run flows that use the date functions makers reach for after `addDays`, and `float`. This is M59 of the improvement plan written after the live test of 2026-11-04 (P1; it closes C-2, "the simulator's function set is narrow"). The plan and the person's answers to its decisions are kept outside the repo, because they quote a private test run. M58 added `formatDateTime`, `int` and `addDays`'s format, compared the simulator with one cloud run, and left the rest of the date set to this milestone (`docs/plans/m58-flow-conformance/plan.md`, "Won't build"). Today `addHours(utcNow(), 1)` and every function below make a flow test `unsupported` (`ExpressionFunctions.cs:22-76`, `docs/FLOW-TESTS.md:30`).

The rule from M14 and M58 holds: what Learn doesn't settle is `unsupported`, never a guessed value. The capture of 2026-11-05 (`tests/fixtures/flowtests/capture/`) holds no call to any of the eight functions, so every value here comes from Learn's function reference, from .NET's format and time-zone behaviour that the reference links to, or from what the capture showed about the service's timestamp reading (decisions Q1). Nothing is compared with a new cloud run: a capture needs the person's yes in Dev and is optional for this milestone (decisions Q13).

Done when:

1. `float`, `addHours`, `addMinutes`, `addSeconds` (each with its format argument), `startOfDay`, `dayOfWeek`, `convertFromUtc` and `convertTimeZone` are simulated where Learn's sections state a result, each tested with the examples of its section on Learn's expression functions reference (rows 1 to 6; all of them but convertTimeZone's second, whose hour `80` is read as the typo it is, decisions Q12), and every form Learn leaves open is `unsupported`, as listed under "Not on Learn" and in `decisions.md`.
2. Time zones take Windows names, such as "Pacific Standard Time", and the conversion gives the same result on Windows and Linux: only the 24 zones of row 4 are taken, each only from the first year after its last rule change through 2030, and CI's Windows and Linux jobs run the same tests, which pin every one of those zones' January and July offsets in every year it is taken, the 2026 daylight-saving changes of four zones, and Learn's examples, each against one fixed value written in this plan (row 7). Any other name, an IANA name such as `America/Los_Angeles` and another casing included, is `unsupported` on both. The results don't depend on the computer's own time zone (row 7).
3. The pinned list test holds the 47 names; `docs/FLOW-TESTS.md` lists every supported function with every argument form it takes and the rules for the new ones; the test that compares that list with `ExpressionFunctions.Names` passes (rows 8, 9).
4. The tests that used `addHours` as their example of an unsupported function use `dayOfYear` instead, and the `test-failures.*` goldens change by the recipe; `CaptureTests` passes unchanged; the eval baselines in `tests/eval/roles/baseline/` are unchanged (row 8).
5. `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status .` and the leak scan are clean; the PR is green on all eight checks. Not merged by this session.

### Not on Learn

The simulator's choices in this milestone, each a case for a later capture. The first four are on the main path of a real flow (`startOfDay(convertFromUtc(utcNow(), '...'))`, `float(triggerBody()?['amount'])`), so a capture checks them first:

- `startOfDay` keeps no zone on a timestamp with none (decisions Q2); the capture showed this for `addDays` only.
- A timestamp with no zone in `convertFromUtc` is UTC, and in `convertTimeZone` a time on the source zone's clock (row 5).
- A float with no fraction is written `14.0`, is not an integer anywhere one is needed, and its text is `14.0` (decisions Q12).
- The double type stands for Learn's "float data type": a string with more digits than a single-precision float holds keeps them (decisions Q10).
- `addHours`, `addMinutes` and `addSeconds` read a timestamp as `addDays` does: an offset converted and written `+00:00`, no zone kept (decisions Q1). `dayOfWeek` takes its date as written.
- The conversion's result format uses `en-us`, as `addDays`'s does (M58 decisions Q4, confirmed by the capture for `addDays`).
- `convertFromUtc` takes Windows ids with punctuation (`W. Europe Standard Time`) as Windows and the Default Time Zones page write them; `convertTimeZone` refuses them, after its section's sentence on punctuation (decisions Q4).
- `float` with no locale reads like en-US; `float` of a number gives that number; `float` of a string that no number style reads is an error. Learn's sentence that `float` can be used "only when passing custom parameters to an app" is not modelled: the simulator runs `float` wherever an expression is.
- What this milestone makes `unsupported` and a capture could settle: an offset in `startOfDay`, `dayOfWeek` and both conversions; `Z` with a source other than `UTC`; a skipped or repeated clock time; a name with punctuation in `convertTimeZone`; an instant before a zone's first year or after 2030; the destination `UTC` with `o`; a zone outside row 4's 24, a time-zone name in another casing, an IANA name; `float` with a space, an exponent, parentheses, `NaN`, infinity, a locale other than `en-US` and `de-DE`.
- Time-zone data: Windows' registry on Windows, the IANA database through ICU on Linux (decisions Q5). The service's data is not on Learn. Within the 24 zones and their years, the tests pin January and July of every year and the 2026 changes on both platforms; the change times of other years are each database's own, and a country that changes its rules before 2030 makes a computer's result depend on whether its data has the change.
