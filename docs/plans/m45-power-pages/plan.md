# M45: Power Pages reader and boundary rules

## Goal

Read the Power Pages components of a solution in the enhanced data model, and warn in `analyze` about five Web API and table-permission settings that should be fixed before Production. This is M45 of Phase 7 ([plan](../phase7-power-platform/plan.md), build-order item 80, release label v0.28.0), with its "Stops if" rule, and decision 49 (D10) for inputs an export doesn't hold.

Done when:

- `Solution` has one new field, `PowerPageComponents`, read from every `powerpagecomponents/<id>/powerpagecomponent.xml` of an unpacked folder and of an exported zip, which use the same entry path (Assumptions, the packed copy). A file whose shape the reader doesn't know is an `InvalidDataException` whose message starts with the path. The existing rules give the same findings on every solution as before.
- Five warnings, PO019 to PO023, each message ending "before Production": the Web API `*` fields setting on an enabled table; an enabled table with neither a fields setting nor `UseFieldsFromView`; a table permission with no web role; a child permission with a role its parent lacks, or with an inactive parent; an anonymous role with create, write or delete. Each has firing and quiet tests in `WarningRuleTests`, with a disabled API, explicit fields and `UseFieldsFromView` among the quiet cases, a page with a dated Learn Sources line, and a row in `docs/rules/README.md`.
- Where a rule's input is outside the export (the view behind `UseFieldsFromView`, a parent permission or a web role not in the solution), `analyze` prints one `note:` line on stderr, with no finding and no exit-code change (D10).
- The gov-apptemplates `core-portal` solution is a fixture in `tests/fixtures/core-portal/`, recorded in `tests/fixtures/NOTICE.md`, quiet on the five rules. `analyze` has one CLI-level test on the fixture folder and one on its zip.
- The goldens change only as the Data section says. `RoleEvalTests` passes with no eval file changed, and `powerops-verify` and `powerops-review-security` keep their blob ids (`69208a2ed044a346bbae9877c8cd74d9e4794df9` and `6a6a6a1fdb71eb16d09cf3ed99406d04a0982a1f`).
- `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status .` and the leak scan are clean, and one `feat:` PR is open.

### Won't build

- The `.powerpages-site/` download layout, the `site/` folder of the fixture's repo, and any other root without a solution manifest: the Phase 7 plan leaves them to a later milestone.
- A wildcard Error, Global-scope checks, more than one anonymous or authenticated role, local login, bearer authentication, `*Secret` settings, header and encoding settings, page permissions, Liquid checks, a `diff` of the boundary, and the plugin's `analyze-performance` JSON (the Phase 7 plan's "Deliberately doesn't").
- Reading the "Power Pages Web API Columns" view, or any saved query: the note covers it, and no other rule needs a view.
- A `--json` or SARIF field for the notes, or a note in the MCP tool's result beyond the stderr lines it already passes on: the M45 section says "no schema change".
- A component type the rules don't read (pages, templates, files, snippets, links) as anything but a generic row.

## Users

- A maker or agent who runs `analyze` on an exported or unpacked solution that holds a site, before it goes to Test or Production.
- CI: the Action runs `analyze` with `--fail-on error` by default, so five new warnings change no exit code. A job set to `fail-on: warning`, as the examples README suggests with a baseline, fails on the new findings until they are fixed or baselined. A new `note:` line on stderr changes no exit code.
- An agent through the MCP `analyze` tool, which already passes on stderr `note:` lines (`McpCommand.cs:144`).
- Every command that loads a solution (`analyze`, `baseline`, `diff`, `test`, `settings`, `deploy` and their MCP tools) goes through the same parser, so it reads the new component files and a refused file stops it with exit 3 as any malformed file does today. To keep that to shapes the rules depend on, only types 9, 11 and 18 have their `content` parsed (rows 1 and 2).

## Assumptions

- Learn, checked 2026-11-03. The `powerpagecomponent` table reference lists `powerpagecomponenttype` 9 Site Setting, 11 Web Role and 18 Table Permission. The Web API overview: `Webapi/<table>/enabled` defaults to `False`, valid values `True` and `False`; `Webapi/<table>/fields` is a comma-separated list of logical names, required unless `Webapi/<table>/UseFieldsFromView` is `True` and the "Power Pages Web API Columns" view has at least one eligible column. The wildcard page and the deprecations page: a `fields` setting whose value is `*` is unsupported for all sites from 14 September 2026, requests to such a table fail, and a site can get a one-time 90-day exemption. The table permissions page: a permission takes effect only when it is associated with one or more web roles; a child's roles are inherited from its parent; the studio shows an error when a child has a role its parent lacks; a deactivated parent leaves its children active but not in effect. The security pages: anonymous users get access through the Anonymous Users role, and anonymous table permissions are public data access.
- Observed shapes, not documented: the fixture at `64dabc2` (component files with a `powerpagecomponentid` attribute, the type, name, site, state and `content` as a JSON object; web roles with `anonymoususersrole` and `authenticatedusersrole` booleans; site settings with `content` `{"value": …}` or none). microsoft/contoso-real-estate-power-platform at `dbd5f76d8098d838f8cbdd050134ea6094b68cf5` (MIT), `src/portal/solution/ContosoRealEstatePortal/src`, read for shape only: type 18 permissions with `entitylogicalname`, `scope`, boolean `read`, `write`, `create`, `delete`, `append` and `appendto`, `parententitypermission` `null`, and the role ids in `adx_entitypermission_webrole`, the same key pattern the fixture uses for `adx_websiteaccess_webrole` and `adx_webpageaccesscontrolrule_webrole`; `Webapi/*` settings with values `true` and `*`; four components with `statecode` 1. No public export with a child permission was read, so `parententitypermission` holding the parent's id is the Phase 7 research's reading and the key's name, not an observation; the reader doesn't refuse another kind there (decisions Q11).
- The packed copy: `pac solution pack --packagetype Unmanaged` (pac 2.14.1, local, no sign-in) of a copy of the fixture gives 137 entries: `solution.xml`, `customizations.xml`, `[Content_Types].xml`, `Assets/powerpagesites.xml`, `Assets/powerpagesitelanguages.xml`, 122 `powerpagecomponents/<id>/powerpagecomponent.xml` and 10 `powerpagecomponents/<id>/filecontent/<file>`. Every component file is byte-identical to the unpacked one, so the zip path is the unpacked path and nothing is guessed. Microsoft's own export in the same repo (`portals/core-portal/releases/MS-Gov-Core-Portal - 1.0.0.0.zip`) has the same 137 entry names; its component files differ from the unpacked ones only in CRLF line endings. `SolutionZip` moves only the two manifest files, which is the same mapping for every entry this fixture has; it doesn't add `[Content_Types].xml`, which the reader doesn't read.
- Learn says a deactivated table permission becomes ineffective, and doesn't say whether an inactive site setting or web role still applies. The rules count only active components (decisions Q3).
- Learn's wildcard examples are all a whole value of `*`; whether `*` as one entry of a list is a wildcard is not stated, so PO019 checks the whole value only (decisions Q4).
- The table permissions page also says a deactivated table permission becomes ineffective; the manage-exemptions page gives the exemption as a one-time 90-day extension per site; the Web API overview says `UseFieldsFromView` needs site version 9.8.8.x or later, which an export doesn't show (both rule pages say so).
- A real site export (F5) was not read; it is optional and not part of this build.
