# Decisions: m28-write-paths

## Round 1

### Q1. What exit code does a refused write give, and when is it found?
1. Exit 2 with an `error:` line, found by one rule in every command before it does its work: the helper's `Refusal` opens nothing, refuses a link at the target (except the names `/dev/stdout` and `/dev/stderr` as typed) and a target that is a named input, and for `skills install` a link on the way; the write runs it again, and a change found only then exits 3 through the commands' existing catch-alls (recommended)
2. Exit 3 at the write, through the existing catch-alls, with only `deploy apply` checking up front (it already has an up-front `--out` check)
3. In your own words
Answer: Exit 2 with an `error:` line, found by `Refusal` before the work, in every command; exit 3 only for a target that changed between the check and the write. AGENTS.md calls 2 a usage error and 3 unreadable input or an internal error, and a link or an input given as `--out` is the arguments being wrong. The neighbours already do this: `deploy` exits 2 for `--out` or `--save` naming a folder and `drift` for `--save` naming a file, while a write that fails for any other reason exits 3 and stays so. The up-front check keeps `deploy apply` from importing and then refusing to write its report, and keeps `drift --save` and `skills install` from writing some files before refusing. One rule for every command also means no new catch clause: the race case is an `InvalidDataException`, which each command already turns into exit 3. The price is an accepted narrowing of decision 35's "a target that resolves to a device or a pipe is written in place": `Refusal` opens nothing, so it cannot tell a link to a device from a link to a file (the name of a link's final target proves nothing: a planted link to `/proc/self/root<file>` is a regular file under a `/proc` name), and refuses every link. A device or FIFO named directly (`/dev/null`, `/dev/stdout`, `/dev/stderr`, a FIFO's own path) is still written in place; a link to one is refused (a FIFO elsewhere, `/proc/<pid>/fd/1`, and also `/dev/fd/<n>` and `/proc/self/fd/<n>`, which with `3<in.zip` would name an input), and the user names the device itself. The Phase 6 plan is signed off and is not edited; Step 6 of this plan edits BUILD-PLAN's decision 35 and the M28 row instead, and lists the narrowing under "Accepted:" in the row's Built bullet. The master session is told in the report on this plan so that it can raise it with the user. Option 2 is a smaller diff, but it makes the same mistake exit 2 in `deploy apply` and 3 elsewhere. `skills install` keeps its existing exit 1 for a directory in the way and a conflict; only the new link refusal is 2, so that command's old behavior is not changed.

### Q2. What counts as one of the command's inputs?
1. The files the user named on the command line (arguments and options that name a file), compared by full path, with a link on an input's last name resolved; not the files inside a folder they named (recommended)
2. Also every file the command finds and reads in a folder it was given: found zips, settings files, flow tests and snapshot files
3. In your own words
Answer: The files the user named. It closes the observed case (`settings generate <zip> --out <zip>`) and the plausible typos (`--out` set to an argument, a baseline, a snapshot or the plan file), and it keeps the common pattern working: a report or plan file written into the folder being analyzed or deployed, which the Action does (`--save` into the deploy folder). Option 2 needs `analyze`, `diff`, `test` and `deploy plan` to hand the helper what their scans found, and would refuse nothing a user types by accident, since nobody names a found zip as `--out` by mistake. The comparison is a guard for the common spellings (full path, a link on the last name, case on Windows and macOS); it does not see 8.3 names, `\\?\` paths, Unicode normalization or an alias through a link on a folder on the way, and the residual goes under Assumptions. Hard links are not compared: the move replaces the directory entry and leaves other names with their old bytes (observed), so a hard link to an input is no danger, and .NET 10 has no file id to compare anyway.

### Q3. How does the helper tell a device or a pipe from a regular file?
1. One probe, on an existing target that is not a link: open it once for write and set its length to the length it has; if that fails it is a device or pipe and is written in place on that same handle, otherwise it is a regular file, closed and replaced through a temp file and a move. The names `/dev/stdout` and `/dev/stderr`, exactly as typed, are written in place without a probe (recommended)
2. A path rule: a target whose resolved path is under `/dev/` or `/proc/` is written in place, and no file is opened
3. A P/Invoke of `stat` for the file type
Answer: The probe, with the typed names. The first draft of this answer was the path rule; the fresh review showed it unsafe, and the probe is the fix. A planted link `report.json -> /proc/self/root<abs path>` resolves to a `/proc/...` string and is a regular file, so the path rule wrote through it (reproduced: `File.WriteAllText` overwrote the file behind it; the same for `/proc/self/cwd/<file>` and `/dev/shm/<file>`). The probe classifies the thing that is opened and not its name, and links never reach it, because `Refusal` has refused them (Q1); so those three links are refused without touching what they point at. It opens the target once and writes on that same handle, so a reader of a FIFO that stops at end of file sees the text, where a probe that opened and closed first gave it an early end (observed with a prototype). .NET 10 has no file type call (observed), so option 3 would be a struct layout per platform and architecture for what ten lines of probe do. Only an exception from the length probe means a device or pipe; an exception from the open propagates, and a regular file directly under `/dev/` is refused and never replaced, a guard for a system not tried. The typed names are separate because `/dev/stdout` with stdout redirected to a regular file would be a link to a regular file and be refused, and it works today; they are matched as exact strings, so a planted link and `/dev/./stdout` do not match. `/dev/fd/<n>` and `/proc/self/fd/<n>` are not typed names: with `3<in.zip` they name an input, and opening them for write truncates it. The same probe should take `NUL` on Windows in place (the runtime source throws `NotSupportedException` for a handle that cannot seek, which Learn documents for `RandomAccess.SetLength`); a Windows-only test checks it, and until then it is inferred.
