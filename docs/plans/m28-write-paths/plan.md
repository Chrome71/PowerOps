# M28: Write paths

## Goal

Build BUILD-PLAN milestone M28 (build-order item 53, release label v0.20.6). The spec is fixed: the Phase 6 plan's R-9 row, its decisions Q2 and Q8, BUILD-PLAN decision 35 and the M28 row, whose done-when is the bar. R-9 observed four cases: `baseline --out` wrote through a link, `settings generate <zip> --out <zip>` overwrote its input, `plan sign-off` wrote through a linked `plan.md`, and `skills install` with a linked `.claude` wrote outside the repo. Every write truncates in place, so a crash leaves a cut-off file.

This plan settles what the row leaves open, with evidence: the recount of the write sites after M21 (Data), the helper's shape, its exit codes and messages, and the tests (Automation). Three choices are in `decisions.md`, answered with the recommended option under the user's delegation of 2026-10-22: the exit code of a refusal, what counts as an input, and how a device or pipe is told from a regular file.

**What .NET 10 gives, without P/Invoke** (observed this session on Linux, .NET 10.0.113, in a throwaway console project outside the repo):

- `FileInfo.LinkTarget` is non-null for a link to a file, a dangling link, a link loop and a link to a folder. `ResolveLinkTarget(true)` throws `IOException` on a loop. Learn says `LinkTarget` resolves symbolic links and junctions (https://learn.microsoft.com/dotnet/api/system.io.filesysteminfo.linktarget <!-- plan-status: allow -->).
- There is no file type and no file id: `FileInfo.Attributes` is `Normal` for `/dev/null`, a FIFO and a regular file, and `FileInfo`'s and `SafeFileHandle`'s properties, `RandomAccess`'s methods and the `File` methods whose names say link, id, type or stat hold no inode or type (listed by reflection). So a device cannot be told from a file by name or by a type call, and the name of a link's final target proves nothing: a link to `/proc/self/root<abs path>`, to `/proc/self/cwd/<file>` or to `/dev/shm/<file>` resolves to a `/proc` or `/dev` string and is a regular file. `File.WriteAllText` through the first overwrote the file behind it (reproduced, after a review found it).
- **The probe**, for an existing target that is not a link. Open it once with `File.OpenHandle(path, FileMode.Open, FileAccess.Write, FileShare.ReadWrite)`, which follows links, then `RandomAccess.SetLength(handle, RandomAccess.GetLength(handle))`. Only an exception from these two calls means a device or pipe; an exception from the open itself is an error. The calls succeed on a regular file, and fail on the others: `IOException` for `/dev/null` and `/dev/zero`, `NotSupportedException` for a pipe, a FIFO and a terminal (Learn documents the second for a handle that cannot seek: https://learn.microsoft.com/dotnet/api/system.io.randomaccess.setlength <!-- plan-status: allow -->). Opening a read-only file or a folder for write throws `UnauthorizedAccessException`, a missing file `FileNotFoundException`, a loop `IOException`. The same-length `SetLength` touched the file's modification time (observed), so "unchanged" in this plan means the bytes and the mode. A prototype that classified by this probe wrote `/dev/null` and a FIFO outside `/dev` in place through `new FileStream(handle, FileAccess.Write, 1)` on that same handle, with a reader that reads to end of file receiving the whole text. The same prototype followed links, so it needed the open to tell a link to a device from a link to a file; this plan refuses every link at the target before any open, which also refuses the three planted links above without touching what they point at (Automation).
- `File.Move(temp, target, overwrite: true)` over a link replaces the link and leaves the file behind it untouched; over a hard link it gives the target a new file and leaves the other name with the old bytes; over a read-only file it succeeds on Unix (a rename ignores the file's own permission), so the probe's open for write is what keeps a read-only target failing as it does today. `new FileStream(path, FileMode.CreateNew, ...)` fails on an existing link and a dangling link and creates nothing, so the MCP `save` already refuses both.
- A temp file made with `FileMode.CreateNew` gets the default mode (`0644` under a `022` umask), which can be wider than the target's. `FileStreamOptions.UnixCreateMode` creates it with the target's mode, narrowed by the umask (a `0666` target gave `0644`, a `0600` target `0600`); `File.SetUnixFileMode(temp, target's mode)` then restores the bits the umask cleared. Setting `UnixCreateMode` is for Unix only. `Flush(true)` works. A temp file in a read-only folder fails with `UnauthorizedAccessException` whose message holds the temp file's path (observed), so the helper has to rewrite it. Learn documents `File.Move`'s `overwrite` parameter (.NET Core 3.0 and later) but not that the replacement is atomic (https://learn.microsoft.com/dotnet/api/system.io.file.move <!-- plan-status: allow -->); on Linux it is a rename, which the link and hard-link observations are consistent with.
- **Windows, read from the source and not run.** `SafeFileHandle.Open` does not reject a handle whose file type is not a disk file, and `CanSeek` is false for one (https://github.com/dotnet/runtime/blob/main/src/libraries/System.Private.CoreLib/src/Microsoft/Win32/SafeHandles/SafeFileHandle.Windows.cs <!-- plan-status: allow -->). `GetLength` and `SetLength` both call `ValidateInput(..., allowUnseekableHandles: false)`, which throws `NotSupportedException` for such a handle (https://github.com/dotnet/runtime/blob/main/src/libraries/System.Private.CoreLib/src/System/IO/RandomAccess.cs <!-- plan-status: allow -->). So `NUL` and the other reserved names should take the same in-place branch as a pipe. Learn gave no sign that `SetLength` succeeds on them, so no reserved-name check is added; a Windows-only test runs `--out NUL` and CI is the check.

## Automation

**Files.**

- `src/PowerOps.Core/Output/SafeWrite.cs` (new, Core because `PlanSignOff` writes; `BoundedRead` is the read-side twin):
  - `record WriteRefusal(string Path, string Reason)`. The reasons: `is a symbolic link; symbolic links are not written.` (the twin of the read side's `is a symbolic link; symbolic links are not read.`) and `is an input of this command; it is not overwritten.`
  - `WriteRefusal? Refusal(string path, IEnumerable<string> inputs, string? root = null)`: opens and creates nothing. Every command calls it first, before its work.
  - `void WriteText(string path, string text, IEnumerable<string> inputs, string? root = null)`: UTF-8 without a byte order mark, which is what all twelve callers write today. It runs `Refusal` again, because the target can change between the check and the write, and throws `InvalidDataException` (message `<path>: <reason>`) when that finds something. Every other failure is an `IOException` or `UnauthorizedAccessException` as `File.WriteAllText` throws today; one from the temp file's creation, write or move is caught and rethrown as the same base type, with the original as its inner exception and the temp file's path in the message replaced by the target's, so no message holds `.powerops-<hex>.tmp`.
  - An `internal` overload takes a `beforeMove` callback (called with the temp file's path), for the tests of the failed move, the temp's mode and a link swapped in late; and `internal static bool IsDirectlyUnderDev(string fullPath)` for the guard below.
- Callers: the twelve sites of the table, each calling `Refusal` up front and `WriteText` at the write, with the files it was given as `inputs`. No catch clause is added: a refusal found up front returns exit 2 itself, and one found only at the write is an `InvalidDataException`, which each command's catch-all already turns into exit 3.
- `src/PowerOps.Cli/McpCommand.cs`: one comment above `TrySave` saying why it is not routed through `SafeWrite` (it must refuse an existing file or link, which `CreateNew` does). No code change.
- `tests/Shared/Links.cs` (new, compiled into both test projects like `Golden`): `Links.Create(link, target, folder: false)` creates a symbolic link. Where creating one fails, it skips on Windows (`Assert.Skip("Symbolic links are not available here.")`, the message the existing tests use) and fails on Linux and macOS, where a link can always be made and a skip would hide a missing check. M32's `Tools.Require` is the model.

**The helper.**

`Refusal(path, inputs, root)` runs in every command before its work, and refuses in this order. It opens and creates nothing.

1. **A typed process name** is never refused: on Unix a `path` that `string.Equals(path, "/dev/stdout", StringComparison.Ordinal)` or `"/dev/stderr"` matches, as typed and not resolved (so a planted link, and `/dev/./stdout`, do not match). `/dev/fd/<n>` and `/proc/self/fd/<n>` are not typed names: with `3<in.zip` they name a user's input, and opening them for write would truncate it. They are links, and are refused like any.
2. **A link at the target.** `new FileInfo(path).LinkTarget is not null` (the check `PlanChecker` and `DeployCommand` already use for reads, so OneDrive placeholders and other reparse points that are not links keep working). A dangling link, a loop and a link to a folder are links. Without an open the helper cannot tell a link to a device from a link to a file, and the name of a link's final target proves nothing (Data), so every link is refused.
3. **With `root`:** `root` and the target's folder are made full first, so `.`, `..` and a trailing separator in `root` do not matter, and every folder from below `root` down to the target's folder is checked with `new DirectoryInfo(folder).LinkTarget is not null`, and the first link is refused, named by its own path; `root` itself is not checked, because the user named it. Without `root`, links on the way are allowed, as the user typed `--out some/linked/dir/report.json`.
4. **An input.** The target and each input are made full (`Path.GetFullPath`), an input's last name is resolved if it is a link (`ResolveLinkTarget(true)`, so an input that is a link to the target matches; an `IOException` while resolving, such as a loop, counts as no match), and the paths are compared `Ordinal` on Linux and `OrdinalIgnoreCase` on Windows and macOS (a false refusal on a case-sensitive Mac volume is the safe direction). This guards the common spellings. It does not see 8.3 names, `\\?\` paths, Unicode normalization or an alias through a link on a folder on the way. Hard links are not compared and need not be: the move never writes into the target's file, it replaces the directory entry, so a hard link to an input keeps the input's bytes (observed). Only the same entry can destroy an input.

`WriteText(path, text, inputs, root)`:

1. A typed process name is opened and written in place with `File.WriteAllText`, with no probe, as today. Stdout redirected to a regular file therefore still works.
2. Otherwise `Refusal` runs again.
3. **The open.** An existing target (it is not a link now) is opened once with `File.OpenHandle(path, FileMode.Open, FileAccess.Write, FileShare.ReadWrite)`. `FileNotFoundException` or `DirectoryNotFoundException` means a missing target (step 5). Any other exception from the open propagates, exit 3: a read-only file or a folder (`UnauthorizedAccessException`), a loop, a sharing violation. None of them is read as a device.
4. **The probe**, on that handle: `SetLength(handle, GetLength(handle))`. Only an exception from it (`IOException` or `NotSupportedException`) means a device or a pipe; the text is then written in place on the same handle, so a FIFO is opened once and a reader that reads to end of file sees the text before the close. Nothing is replaced. If the probe succeeds, the handle is closed and the file is replaced as in step 5. One guard against a wrong answer on a system not tried: a target whose given full path is directly under `/dev/` (`Path.GetDirectoryName` is `/dev`) that the probe calls regular is refused with `InvalidDataException` (exit 3), never replaced; `/dev/shm/x` is not directly under `/dev/`.
5. **The temp file.** A missing target or a regular file. The temp stream is created before the `try` that guards the rest, `.powerops-<8 hex digits>.tmp` in the target's folder, with `FileStreamOptions { Mode = FileMode.CreateNew, Access = FileAccess.Write, Share = FileShare.None }` and, on Unix for an existing target, `UnixCreateMode` set to the target's mode, so it is never wider than the target (`CreateNew` fails on a planted link or an existing file, and `finally` deletes only a file this call made). In the `try`: write, flush to disk, close, on Unix for an existing target `File.SetUnixFileMode(temp, target's mode)`, then `File.Move(temp, target, overwrite: true)`. A missing folder gives `DirectoryNotFoundException` as today. The temp-path rewrite of the messages is described under Files.

The guarantee against a link swapped in after the check covers the replacing branch: a rename replaces a link instead of following it (observed), so nothing is written through it, and the re-run of `Refusal` catches most swaps first (exit 3). In the in-place branch a link swapped in between the re-run and the open is followed, because .NET has no `O_NOFOLLOW`; it is then a link to a device or pipe or one the probe calls regular (and replaced, not followed). A folder on the way swapped for a link between the re-run and the creation of the temp file would take the temp and the move with it; .NET has no `openat`. Both windows need a racing writer to the folder, who can already replace the file; they are residuals.

**Windows.** The probe applies as on Unix: `NUL` should take the in-place branch (Data), which the Windows-only `--out NUL` test checks, including that no temp file is left; that `Refusal` (`LinkTarget`, `GetFullPath`) accepts a device name is checked by the same test. Rename is `File.Move(..., overwrite: true)`; Learn says the OS can fail to get exclusive access to the destination (`UnauthorizedAccessException`), so a target held open elsewhere fails and the temp is deleted. A read-only existing file fails at the open for write, as today. `LinkTarget` handles symbolic links and junctions. Modes: none; the new file takes the folder's inherited ACL, so an explicit ACL on the old file is not kept. Not run on Windows by this plan (no machine, as in M32); the CI run is the check.

**Compatibility** (what a CI user or an agent can see; the PR description lists it). A write through a link to a file, over a named input, or through a link on the way for `skills install`, exits 2. **Accepted narrowing:** a link to any device or pipe other than the typed names is refused too (a FIFO elsewhere, `/proc/<pid>/fd/1`, `/dev/fd/<n>`, `/proc/self/fd/<n>`). The spec says "a target that resolves to a device or a pipe is written in place"; telling a link to a device from a link to a file needs an open that the up-front check must not make, and the name of a link's target proves nothing. Name the device itself: `/dev/null`, `/dev/stdout`, `/dev/stderr`, a FIFO's own path. Step 6 edits decision 35 and the M28 row of BUILD-PLAN to say so, and lists it under "Accepted:"; the signed-off Phase 6 plan is not edited. A replaced file is a new file: its mode is kept, its owner, ACL, extended attributes and hard-link count are not. Known limits, listed in `docs/COMMANDS.md` ("Writing files"), with no fallback: a single file bind-mounted into a container as `--out`, a folder that allows writing the file but not creating a file, and a sticky world-writable folder such as `/tmp` where a rename over another user's file is refused (inferred); each now fails with exit 3 where an in-place write worked.

## Assumptions

Observed this session (Linux, .NET 10.0.113) is in Data. Inferred, not run:

- **macOS.** `/dev/null` and `/dev/stdout` work as on Linux (the probe, the typed names and the `/dev` guard); the macOS CI run is the check. The probe's result on a FIFO there is not known; only the FIFO test depends on it.
- **Windows.** The `NUL` branch, the rename, the junction handling and the ACL paragraph are from Learn and the runtime source, not from a run. Whether the `windows-latest` runner may create symbolic links is not known (M32 saw link tests skipped there); the run records whether the link tests ran or skipped, as M32 records its counts.
- **Hard links** are not detected and need not be (Automation). Ownership, extended attributes and the hard-link count of a replaced file are not kept; a shared folder's file owned by another user becomes the writer's.
- **A killed process** can leave a `.powerops-*.tmp` in the target's folder; the target itself is whole. The MCP `save` is not atomic (it keeps `CreateNew`, so a retry after a crash fails because the file exists); R-9 and decision 35 accept it.
- **A bind-mounted single file** as `--out` (a container mount) fails in the move with `IOException` (EBUSY on Linux is the expected error), and a folder where the file is writable but no file can be created fails creating the temp; in a sticky world-writable folder such as `/tmp` a rename over another user's file is refused (EPERM). All worked before. No fallback to an in-place write is added: it would give back the cut-off file and the window the helper closes, in the cases no test reaches. If someone reports the mount case, a fallback is a later `fix:`.
- **Typed inputs only.** `analyze exports/ --out exports/Demo.zip` overwrites a zip it just read; a report written into an analyzed folder is the common case and stays allowed (Q2). `--out` over a file `drift --save` writes in the same run is allowed too.
- **Culture and encoding.** The helper writes `new UTF8Encoding(false)` like the callers; it does not change what a lone surrogate becomes.
