# M54: The implement and plan skills never delete, keep a write journal and mark who answered

## Goal

Make the build skills' tenant writes traceable and keep the person's authority with the person. This is M54 of the improvement plan written after the live test of 2026-11-04 (P0 block). That plan, its reviews and the person's answers D1 to D9 are kept outside the repo, because they quote a private test run. The run found that the implement child deleted two draft app modules it had made in Dev without asking (claim 19 of the run's record; findings A-1 and C-3), that the record presented an orchestrating agent's answers, sign-off and risk acceptances as the plan owner's (A-2, A-3), that an environment-wide setting change and stray objects missed the cleanup list (A-4), and that the record did not say which route built each component (A-6). `docs/HANDOFF.md:103` claims `powerops-implement` asks before each delete; the skill has no such rule.

D3 is answered by the person: "Draft split (Recommended)". An orchestrating agent may answer product choices within the brief by delegation. It may never sign off a plan, accept a High finding or accept a security gap. Every answer is marked person or agent.

Done when:

1. `skills/powerops-implement/SKILL.md` section 3 says: never delete in a tenant, not even an object of this run and not when asked; a stray object goes into the journal with an open cleanup obligation, and work goes on only where the next step is safe and independent of it, otherwise it stops with one question; every tenant write attempt, failed ones too, gets a row in `docs/plans/<name>/writes.md` (actor, authority, operation with its route, outcome, cleanup obligation, no tenant details), committed with the step; each commit message names the route of each component it built.
2. Both skills record each answer and acceptance in `decisions.md` with `(answered by: person)` or `(answered by: agent <session>)`. A delegated product choice stays valid. An agent's answer never signs off, never accepts a High finding and never accepts a security gap: the skill stops and says a person must answer.
3. `powerops plan status` lists `writes.md` (entries and open cleanup obligations, text and JSON) and warns on each Log line of `decisions.md` where a sign-off or an acceptance is answered by an agent, with the text `sign-off answered by an agent` or `acceptance answered by an agent`.
4. `docs/HANDOFF.md`, `docs/USE-WITH-AGENTS.md`, `docs/COMMANDS.md` and `docs/PLANNING-SKILLS.md` say the same; `HandoffDocTests` asserts that the skill text carries the rule HANDOFF claims; `tests/smoke/skills-smoke.sh` has a scenario with an instrumented fake tenant tool where the agent's own stray object blocks a step, which passes only with zero delete calls and the stray recorded in `writes.md`.
5. `SkillsCommandTests.Plan_skill_stays_under_its_word_ceiling` passes without raising the ceiling; the plugin copies are regenerated by "Update goldens" and `git diff plugins` shows only the skill edits; the pinned roles `powerops-verify` and `powerops-review-security`, their plugin copies and `tests/eval` are unchanged.
6. `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status .` (no violation) and the leak scan (0 hits) are clean; the PR is green on all eight checks.

### Won't build

- A violation (non-zero exit) for an agent's sign-off or acceptance: the joint plan says warn, and this repository's own milestone plans are signed off by agents under the person's standing delegation of 2026-10-22 (decisions Q4).
- A check that the `answered by` marker is true, or a warning for a sign-off with no marker: the marker is written by the agent, like M52's `executor`, and plans before M54 have none (decisions Q4).
- A parse of severity or report in an acceptance line: every acceptance answered by an agent warns, whatever it accepted (decisions Q5).
- A timestamp column in `writes.md`: the commit that carries each row dates it (decisions Q2).
- Any change to `deploy apply`, `deploy gate` or the MCP tools: M52 holds the yes to an import. No new command or option.
- Changes to `powerops-review-plan`, `powerops-verify` or `powerops-review-security`: M55 changes the pinned roles.

## Users

- The person who owns a plan and answers its questions, alone or through an orchestrating agent.
- An orchestrating agent that runs `powerops-plan` or `powerops-implement` as a child and answers its questions under the person's brief.
- A reviewer or auditor who reads the plan folder afterwards: who answered what, which writes ran, and what is left in the tenant.

## Assumptions

- The marker is self-reported, like M52's `executor`: an agent that writes `person` where an agent answered is not caught. The warning is a tripwire for honest marking, not a control; the docs say so.
- A sign-off or an acceptance is always a Log line in `decisions.md`: section 5 of the plan skill already says so for the sign-off, and this milestone adds acceptances in both skills. The check reads only Log lines, because an `Answer:` line of a product choice may discuss acceptance in its reasons.
- Learn, checked 2026-11-04 with the Learn MCP tools: Recommendations for identity and access management (Power Platform Well-Architected, SE:05), the joint plan's source for M54, says that any action must be traceable to prevent repudiation attacks, that write access to developer environments should be gated, and asks of each role whether the identity needs permission to delete resources.
- The run's own plan folder, which the joint plan names for the acceptance check, was in a scratch folder that is gone. A synthetic folder of the same shape (an orchestrator's sign-off and acceptances, marked) stands in for it in the tests.
