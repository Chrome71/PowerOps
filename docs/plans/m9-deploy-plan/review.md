#### R3. Folder listing and file-name matching differ by operating system, and file names go into the hash text
- Area: 9. Testability (hash determinism across operating systems)
- Finding: "Every `*.zip` directly in the folder" is not defined for case. I checked: on Linux `Directory.EnumerateFiles(folder, "*.zip")` skips `B.ZIP`, while `SolutionLoader` treats `.zip` case-insensitively, so one folder gives different zip sets (and different hashes) on Linux and on Windows or macOS. The same holds for the settings file: `Seed.zip` with `seed.settings.json` matches on a case-insensitive file system and is an "orphan settings file" (exit 2) on Linux; the plan does not say which comparison applies. The hash text puts `<file name>` between spaces and ends the line at `\n`; a Linux file name can hold a space or a newline and can forge or merge lines, and a non-ASCII name can be NFC on one system and NFD on another (a git checkout on macOS). The test list has one hash test per input line but none for listing order or case.
- Suggested fix: List with `EnumerateFiles(folder)` and filter by extension with `OrdinalIgnoreCase`; match the settings file by exact (ordinal) name and report a near match (same name ignoring case) as exit 2 with both names; restrict zip and settings file names to a safe set (for example letters, digits, `.`, `_`, `-`) and exit 2 otherwise, which also removes the line-forging case; hash file names as written. Add tests: files created in reverse order give the same hash; an upper-case `.ZIP` is read; a settings file differing only in case is a usage error; a name with a space or a newline is refused.
- Resolution: fixed (extension compared ignoring case, settings matched by exact name with a case-only near match as exit 2, a safe file-name set, symbolic links refused; tests for order, `.ZIP`, case and bad names)
