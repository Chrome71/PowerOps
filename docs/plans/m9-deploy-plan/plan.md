# M9: deploy plan and the PR comment

## Goal

`powerops deploy plan <folder> --target <environment>` says, before anything is imported, what importing the exported solution zips in `<folder>` into the target would do: the import order, an action per solution (install, upgrade or skip), the components a managed upgrade deletes (where the plan can tell, Q2), the unmanaged layers the import leaves on top (when the target's layers were read), the settings files' problems and the cloud flow states after the import. It reads the target only, through M8's live reader, and writes nothing to it. It writes a plan file (JSON) with a hash over its inputs, which M10's `deploy apply` checks before it imports. The GitHub Action posts one pull-request comment and updates it on each run: the plan when a target is configured, else the offline `diff` of the PR's base and head solution (BUILD-PLAN decision 11). This is the BUILD-PLAN M9 row (release v0.10.0, build-order tasks 25 to 27).

Done when:

- Offline: the tests under Steps pass on zips built in the tests from `tests/fixtures/powerops-seed/` and small inline solutions, and on recorded snapshots (`tests/fixtures/drift/` and ones built in the tests), through a fake target read (no tenant, no network). Each case of the BUILD-PLAN row has a test: dependency order, a cycle, a missing dependency, install, upgrade, skip (same and lower version), managed over unmanaged and unmanaged over managed, a deleted component, an unmanaged layer, a settings error. The same inputs give the same plan hash, and a change to any one input (a zip byte, a settings byte, the target id, a snapshot field, a dependency's version) changes it. The Action's comment script passes its tests with a stub `gh`. The JSON goldens validate against `docs/schemas/deploy-plan.schema.json`. `dotnet build`, `dotnet test` and `dotnet format --verify-no-changes` are clean.
- Live (BUILD-PLAN M9 done-when), in the test repo `Chrome71/powerops-action-test` against the user's Test (BUILD-PLAN decision 9), read-only towards Test:
  1. A PR that changes the seed solution (a new managed export from Dev, one version higher) gets one plan comment against Test, which shows the upgrade, the settings check and the flow states.
  2. A second push to that PR edits that comment; the PR still has one PowerOps comment.
  3. A PR from a fork in the test org `chrome71-test` gets the offline `diff` in its job summary (the fork's token cannot comment and the fork run gets no secrets and no sign-in), and its run passes.
  4. A push whose sign-in is broken on purpose (a wrong secret) replaces the comment with "the plan could not run" and fails the job (R7).

## Users

- Agents in the user's Claude Code or Codex that run `powerops deploy plan ... --format json` to answer "what will this deployment do to Test?" before they ask the user to approve it.
- Reviewers of a pull request who read the plan comment, and M10's apply job, which runs only the plan file that was reviewed.

## Data

**Inputs.** `<folder>` holds exported solution zips: every file directly in the folder (not in subfolders) whose name ends in `.zip`, compared ignoring case so the same folder gives the same set on every operating system, is one solution, loaded with the existing `SolutionLoader`. Beside a zip, `<zip file name without the .zip extension>.settings.json`, matched by exact (ordinal) name, is its deployment settings file (pac's format, as in M7), optional, at most 1 MB. Other files are ignored. `--target` is an environment, passed unchanged to `pac` as `--environment` (an id or URL, as M8's `--env`), and never printed (it may be a URL). Output names the target by its friendly name.

**Target read** (all read-only), through M8's `DriftLiveReader` with one `pac org who` and one `az` token for the whole run:

1. `pac org who --environment <target>`: the friendly name and the environment URL (both read and checked as M8 does) and the `Environment ID:` line (read with the same `SettingsCommand.Field` helper; observed in `tests/fixtures/pac/org-who.txt`, not documented on Learn). The value must parse as a GUID; that check is new. The id goes only into the plan hash; it is never printed or saved. No `Environment ID:` line, or one that is not a GUID, exits 3.
2. The token: `az account get-access-token`, exactly as M8.
3. For each solution in the folder: M8's reads 2 to 6, giving its `Snapshot` (installed or not, version, managed, layers read, components, variables, references, flows). Layers stay as M8 reads them: today M8's reader reads no layers, so a managed target solution has `layersRead: false` and `unmanaged-layer` can fire only on a snapshot that holds layers (R13). A solution whose reads return more than one page (5,000 rows) exits 3, as in M8 (R15).
4. For each other solution a zip depends on (below), only M8's read 2 (`solution` by unique name): installed or not, and its version. Its components are not read.

**Dependencies.** Each zip's `<MissingDependencies>` (the existing `Solution.MissingDependencies`) names, on each `<Required>` node, the solution that holds the required component in the source environment. Exports show it as `solution="<unique name> (<version>)"`; the trailing ` (<version>)` is removed. Learn shows the element and the `solution` attribute in troubleshooting pages but documents no schema, so the format is observed (fixtures `coe-auditlogs`, `alm-makers`). A zip depends on each named solution other than itself. A `<Required>` with no `solution` attribute, or a name that fails M8's unique-name pattern, cannot be checked: it is not read and gives a `dependency-not-checked` warning (R5).

**Order.** A topological sort of the zips on their dependencies on other zips in the folder (Kahn's algorithm; among the zips that are ready, unique names in ordinal order ignoring case, so the order is stable). Zips left over because they are in a cycle, or depend on one, come last in name order and each gets a `cycle` item.

**Per solution.** The action, from the zip and the target snapshot:

| Target | Zip version | Action |
|---|---|---|
| not installed | any | `install` |
| installed | higher than the target's | `upgrade` |
| installed | the same or lower | `skip` (as `pac solution import --skip-lower-version`, which skips the same or a lower version) |

Versions must be four numeric parts (major.minor.build.revision, as Dataverse writes them) and are compared part by part; any other version, in a zip or in the target, exits 3 naming the zip (R12). For an `install` or `upgrade` only (a `skip` imports nothing, R4): the settings file is checked with `DeploymentSettings.Validate` (M7); a zip without one is checked as if its file were `{}`, so a connection reference, or a variable with no default or current value, is a problem, because `pac solution import` binds references only from a settings file (the README says the file is required for such solutions); the dependencies are checked; and each of the zip's cloud flows (`FlowState.CloudFlows`) gets M7's prediction (`FlowState.Plan`), where the state before is the target snapshot's state of the flow with that id (parsed as a GUID; a cloud flow whose id is not a GUID exits 3 naming the zip, R12), or `missing`.

**Items.** Each item has the solution, a kind, a severity (`block`, `warning`, `info`), a subject and a message. Any `block` item blocks the plan.

| Kind | Severity | Actions | When |
|---|---|---|---|
| `cycle` | block | any | the zip is in a dependency cycle among the zips, or depends on one; the message names the zips left over |
| `missing-dependency` | block | install, upgrade | a solution it depends on is neither installed in the target nor in a zip earlier in the order |
| `dependency-not-checked` | warning | install, upgrade | a `<Required>` with no `solution` attribute, or one whose name fails the pattern (subject: the required component's `<type>:<schema name or id>`) |
| `managed-conflict` | block | any | the solution is installed in the target, and the zip is managed and the target unmanaged, or the other way round |
| `settings` | block | install, upgrade | one item per M7 settings problem (subject: the variable or reference name; message: the M7 component type, kind and message) |
| `deletes` | warning | upgrade of a managed zip | a component of the target's solution that the zip no longer has, which the upgrade deletes. Matched where both sides name it: workflows (component type 29) by id against the zip's workflows; environment variables by schema name and connection references by logical name, both ignoring case. Subject: the flow's name for a cloud flow, else the name, else `<type> <id>`. For tables (type 1) and canvas apps (type 300), which the zip names by schema name and the target by id, the counts are compared instead: when the target's solution holds more components of the type than the zip's root components, one item says the upgrade deletes at least the difference (subject `<n> table(s)` or `<n> canvas app(s)`; the message says a deleted table loses its data, Q2, R6) |
| `unmanaged-layer` | warning | upgrade | the target solution is managed and a target component has an unmanaged layer, which the import does not override (subject as in M8) |
| `layers-not-read` | info | upgrade | the target solution is managed and its layers were not read |
| `components-not-checked` | info | upgrade of a managed zip | the target's solution has components outside the checked set (the checked set: type 29, types 380 and 381, the ids of the snapshot's connection references, and types 1 and 300 by count); the subject is their count, the message lists their type numbers, so their deletion is not checked |

Items are sorted by plan order, then by the kind order of the table, then by subject (ordinal).

**File names.** A zip or settings file name may hold only letters, digits, `.`, `_` and `-` (R3). Any other name, a settings file whose name differs from a zip's only in case, and a symbolic link among the folder's zip and settings files are usage errors (exit 2) that name the file through `TextReport.Clean`.

**Plan hash.** SHA-256, in lowercase hex, of the UTF-8 text built from these lines, each ending in `\n`:

```
powerops deploy plan 1
target <environment id, lowercase, D format>
zip <file name> <SHA-256 of the zip's bytes>
settings <file name> <SHA-256 of its bytes>        (or: settings none)
snapshot <SHA-256 of SnapshotFile.Write of the target snapshot>
dependency <unique name, lowercase> <version>      (or: dependency <name> none)
```

The `zip`, `settings` and `snapshot` lines repeat per zip, in ordinal order of the zip's file name; the `dependency` lines follow, one per distinct name read under Target read item 4 (zips of the folder are covered by their `snapshot` line, not here), in ordinal order of the lowercase name. The file names are safe by the rule above, so no name can add or merge a line. The settings file's raw bytes are hashed, because they are what `pac` reads: a change of line endings or a byte-order mark is a change (R17). `SnapshotFile.Write` sorts its lists, so two reads of an unchanged target give the same text. The hash covers the inputs, not the plan's findings: M10 re-plans with the same rules and refuses on any difference (BUILD-PLAN decision 14).

**Plan file.** The JSON report (below) is the plan file. It holds no environment id or URL, no folder path, no connection id and no variable value: only the target's friendly name, the tool version, file names, solution names, versions, flow names, component ids, hashes and the items. It lists its inputs (R10): per zip the zip's and the settings file's SHA-256 and the snapshot's SHA-256, and the dependency lines, so M10 can say which input changed when it refuses. Plan and apply must run the same powerops version: `tool` records it, and M10 decides how it uses it.

## Automation

`powerops deploy plan <folder> --target <environment> [--save <plan file>] [--format text|json|markdown] [--out <file>]`

1. **Usage** (before any read): the folder is missing or not a folder; it holds no zip; a file name breaks the rule above; a symbolic link; two zips have the same unique name (ignoring case); a `*.settings.json` has no zip of that exact name (a typo would leave a zip without its settings) or differs from one only in case; `--target` is missing; `--save` or `--out` names an existing folder: exit 2. A zip that does not load, whose unique name fails M8's pattern or whose version is not four numeric parts, a settings file over 1 MB, not JSON or of the wrong shape, and a cloud flow whose id is not a GUID exit 3, naming the file (through `TextReport.Clean`) and the reason, as `settings validate` does (R12).
2. **Read** the target (Data). The first failed read stops the run with exit 3 (exit 2 for a non-Dataverse host), with M8's messages prefixed by `--target:` (as `drift` prefixes `--env N:`), never the value; forwarded `pac`, `az` and Web API text goes to stderr only, as in `drift`. No report and no file are written.
3. **Plan**: order, actions, items, flows and the hash, all in Core.
4. **Report**: `--format` to stdout or `--out`. `--save <file>` also writes the JSON report to that file, whatever `--format` is, so one run (one read of the target) gives both the Markdown for the PR and the plan file for M10. Exit 0 when nothing blocks, 1 when anything blocks (the report and the plan file are still written, so the block can be reviewed).

Exit codes: `0` plan ok, `1` blocked, `2` usage error or a target URL that is not on a documented Dataverse host, `3` an unreadable zip, settings file, version or flow id, or a failed, timed-out or unreadable `pac`, `az` or Web API read, or `pac` or `az` not found.

`--format json` follows the M4 contract: `schemaVersion` first (`JsonOutput.SchemaVersion`), `docs/schemas/deploy-plan.schema.json`, its row in `docs/schemas/README.md`, a `Map` entry in `OutputSchemaTests` (prefix `deploy-plan`) and goldens. It holds `tool` (the version `powerops --version` prints), `target` (the friendly name), `hash`, `blocked`, `inputs` (`zips`: `zip`, `zipSha256`, `settings`, `settingsSha256`, `snapshotSha256`; `dependencies`: `name`, `version` or null), `solutions` (in plan order: `order`, `solution`, `zip`, `settings` (file name or null), `version`, `managed`, `action`, `installed` (`version`, `managed`, `layersRead`, or null when not installed), `dependsOn` (sorted names) and `flows` (`name`, `exportState`, `exists`, `stateBefore`, `expectedState`)) and `items` (`solution`, `kind`, `severity`, `subject`, `message`). The text report writes every name through `TextReport.Clean`, so a name cannot forge a workflow command line (R11). The Markdown report escapes names with `MarkdownReport.Escape` and, like `diff`, stops at whole rows before `DiffReport.MarkdownLimit` characters with a line that says how many rows were left out (R17). `MarkdownReport.Escape` leaves `@` mentions and `#` references as they are; names come from a same-repository PR, whose author can mention anyone anyway (R11, accepted).

The model, the order, the items, the hash and the reports live in Core (`src/PowerOps.Core/Deploy/DeployPlan.cs` and `src/PowerOps.Core/Output/DeployPlanReport.cs`). `src/PowerOps.Cli/DeployCommand.cs` holds `deploy plan` (M10 adds `apply`), lists the folder, loads the files, hashes their bytes and writes the reports; the target read is a function passed to it (`Program.Run`'s new `deployTarget` seam: target and the solution and dependency names to a `DeployTarget` record in Core with the name, id, snapshots and dependency versions), so command tests use a fake, and reader tests use `DriftLiveReader` with fake `pac`, `az` and web functions as M8's do. `DriftLiveReader` gains `ReadTarget(target, solutions, dependencies)`: one `Who` (which now also returns the `Environment ID:` line, null when absent; `drift` ignores it) and one `Token`, then the reads. Its existing `Read(solution, env)` keeps its behaviour and its tests, and shares the per-solution reads with `ReadTarget` (the body moves into one private method). `DriftReadException` is reused as it is.

**The GitHub Action** (`action.yml`), three new inputs and one output. The analyze steps do not change. The comment and diff logic lives in two scripts in the repo, `action/diff.sh` and `action/comment.sh`, called from `action.yml`, so tests can run them (R9).

- `comment` (default `'false'`, Q3): on a `pull_request` event, post one PR comment and update it on later runs. Opt-in, so existing workflows do not start needing `pull-requests: write`.
- `deploy-folder` and `target` (default empty): when `target` is set and the PR is not from a fork, a step checks that `deploy-folder` is set (else it fails with a clear message, R17) and runs `powerops deploy plan "$deploy-folder" --target "$target" --save "$deploy-folder/powerops-plan.json" --format markdown --out <comment file>`. The plan file goes into the deploy folder, so the folder (zips and plan file) is what M10's apply job needs (R10); the workflow uploads it without the settings files (README). `pac` and `az` must be signed in by earlier steps (the action signs in to nothing). The step does not fail on its own: it records the exit code in a step output, and the last step fails the job (R17). powerops' stderr is captured: only lines that start with `error:` (powerops' own text, which never holds the target value) reach the log, and the forwarded tool text only when the runner is in debug mode (`RUNNER_DEBUG`), because `az` and Web API errors can name tenant ids and the URL in a public log (R1). For exit 2 or 3 the comment file holds a fixed text: the plan could not run, the exit code, and "see the job log" (R7). The plan's Markdown, or that text, always goes to the job summary too. The output `plan-file` is set only when the plan file exists (R17).
- On a fork PR with `target` set, the plan is skipped (forks get no secrets and no sign-in) and the diff path below runs instead (R17).
- Without a `target` (or on a fork), when `comment` is on: `diff.sh` compares the first parent of the checked-out commit with the workspace. `actions/checkout` checks out the PR's merge commit by default, and its first parent is the base branch's tip it was merged onto, so the pair is exactly the PR's change (R8). The script reads the parent's id from the commit (`git cat-file -p HEAD`, which works in a shallow clone), fetches it (`git fetch --no-tags --depth=1 origin <id>`, with the checkout's credentials), checks it out in a worktree under `$RUNNER_TEMP`, and runs `powerops diff <worktree>/<path> <path> --format markdown`; `path` must name one solution, relative to the repository root. If the fetch fails, or the diff exits 2 or 3 (the solution is new in the PR, `path` holds several solutions), the comment holds a fixed text: the diff could not run, which step failed and the exit code, without the tool's text. The README requires the default checkout of the merge commit and the default `persist-credentials`.
- `comment.sh`, only for `pull_request` events when `comment` is on: on a fork PR (the head repository is not the base repository) it writes the Markdown to the job summary and stops. Else it finds its earlier comment with `gh api --paginate` on the PR's issue comments (the first whose author is `github-actions[bot]` and whose body starts with the marker `<!-- powerops -->`) and updates it (`PATCH`), or creates one (`POST`). The body is the marker and the Markdown, sent as a file (`-F body=@file`), never through a shell string. A body over 65,000 bytes is replaced by a short note that the report is in the job summary, and the full Markdown goes to the job summary. GitHub documents no comment size limit, so the cap is a cautious guess (shortcut: an undocumented limit, raise it if GitHub documents one); the Markdown's own row cut keeps most plans under it. If the API call fails (a read-only token, for example a Dependabot run), the script writes a warning annotation and the job summary instead, and does not fail the job. `GH_TOKEN` is `github.token`.
- A last step fails the job when `deploy plan` exited non-zero (blocked, usage or read failure), after the comment is written. The analyze `fail-on` step is unchanged.
- Inputs reach the steps and scripts only through `env:`, never inside `run:` text, as the analyze steps do. `gh` and `git` are preinstalled on GitHub-hosted runners (actions/runner-images); a self-hosted runner needs them, and the README says so.

The README's example workflow (R1, R17): `permissions: contents: read, pull-requests: write, id-token: write`; a `concurrency` group per PR, so two quick pushes do not both create a comment; the plan job runs in a GitHub environment (`test-plan`) whose environment secrets hold the Test URL, the tenant id and the app id, and the values the settings file needs, one secret per value; the settings file is built at run time with `jq` from those secrets in the deploy folder under `$RUNNER_TEMP`, never printed, and left out of any artifact; the steps install `pac` (`dotnet tool install --global Microsoft.PowerApps.CLI.Tool`), sign in `az` with `azure/login` (OIDC, `allow-no-subscriptions: true`) and `pac` with `pac auth create --githubFederated --tenant --applicationId --environment`, all actions pinned by a full commit SHA; the sign-in and plan steps run only for same-repository PRs; `pull_request_target` is not supported.

Out of scope (not asked for): an offline `--target` that takes snapshot files (the plan hash needs the target id, which snapshots do not hold), reading table or canvas app names from the target (Q2), version checks on dependencies, a way to waive a block (the README says to fix the input, or import with `pac` directly outside PowerOps when a block is wrong, R5), linters for the scripts, a `--comment-id` for several PowerOps comments on one PR, `pull_request_target` support, Prod (out of scope until M10, R16), and any write to an environment.

## Constraints

- `deploy plan` is read-only towards every environment: the target read is M8's (`pac org who`, `az account get-access-token`, Web API GETs). Its only file writes are `--out` and `--save`, both explicit. The Action posts or edits one PR comment with the workflow's own token.
- No new package. SHA-256 comes from the base library. The Action uses `gh` and `git` from the runner and no new action.
- Tests never call a real `pac` or `az`, the network or GitHub (the script tests put a stub `gh` first on `PATH`; they run where `bash` is found and are skipped on Windows).
- Fixtures and goldens hold fake values only. The goldens scrub the hash and `tool` (the hash depends on zip bytes built at test time, `tool` on the build); hash tests compare hashes of the same inputs instead.
- The plan file and the comment show the target's friendly name, solution, file and flow names, never a setting's value or a connection id. In a public repository the comment is public; the README says so.
- Licensing: reading needs no licence beyond access to Test; the seed's flow runs in managed environments, which need premium licences (BUILD-PLAN research basis). GitHub-hosted runners are free for the public test repo.
- Sources, checked on 2026-10-22 by powerops-researcher (Sonnet) on Microsoft Learn, docs.github.com and open repos only (no tenant contacted):
  - "pac solution" (learn.microsoft.com/power-platform/developer/cli/reference/solution): `--skip-lower-version` skips the import when the same or a higher version is installed; `--stage-and-upgrade`, `--settings-file` and `--force-overwrite` (overwrite unmanaged customizations) exist.

Managed over an unmanaged install elsewhere is not documented in general; the plan blocks both ways, as the BUILD-PLAN row says.

## Assumptions

- The `<Required solution="<name> (<version>)">` form of exports (observed, not documented) holds the providing solution's unique name before ` (`. If a live export shows another form, the parser is fixed before the build is reported.
- A dependency is met when a solution of that name is installed in the target or comes earlier in the order; the plan does not check the required component itself, so a component that moved to another solution in the target blocks here although the import would pass (R5; the README says how to proceed).
- The `Environment ID:` line of `pac org who --environment` names the environment the reads go to (the M7 capture shows it for the current environment). The live check compares it with the id the admin center shows.
- Two reads of an unchanged target give the same snapshot text (M8 sorts every list). The live check plans twice in a row and compares the hashes.
