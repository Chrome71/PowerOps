#### R1. "Each of the 36 functions against the examples in its section" cannot be met as worded
- Area: 9 Testability (Goal done-when, Automation)
- Finding: The plan says every function is written from its section of Learn's function reference and tested against that section's examples. I read the sections. `triggerOutputs` and `triggerBody` have no example. `decodeBase64` (51 calls in the fixtures, and ReadEnvironmentVariable depends on it) is a stub marked deprecated, with no description or example; it points to `base64ToString`. The only `guid` example is `guid('P')`, which needs a format argument applied to the test's fixed GUID. The `utcNow` examples all use format strings (`'u'`, `'d'`, `'ddd, d MMM yyyy'` and so on) with results in en-US style for one sample timestamp, and `addDays` takes an optional format too. Two of `json`'s four examples need `xml()`, which is not on the list. The plan is silent on all these argument forms, so an implementer must either build .NET format-string support that nobody listed (and pick a culture, which Learn does not give) or skip examples without saying so. A lenient implementation of an unlisted form would also pass where the rule is "never a pass"; today only unknown function names are `unsupported`.

Name the `base64ToString` section as the source for `decodeBase64`, and say `triggerOutputs` and `triggerBody` are tested from their descriptions. State that `utcNow`, `addDays` and `guid` with a format argument, and `json(xml(...))`, are `unsupported` (fixtures use none of them), with one test each, or list the formats you do want and the culture. Pin the list test to argument forms as well as names.
- Resolution: fixed (done-when: each example that uses only the listed functions and plain arguments; `decodeBase64` from the `base64ToString` section; `triggerOutputs` and `triggerBody` from their descriptions; a format argument to `utcNow`, `addDays` or `guid` is `unsupported` with a test each, and `json(xml(...))` is through `xml`; the pinned list covers these argument forms; conversions use the invariant culture)

#### R3. Mock rules: built-in actions have no defined behaviour, and `TimedOut` cannot be mocked
- Area: 9 Testability (Data, Automation)
- Finding: "Any action can take a mock except Scope, If, Switch, Foreach and Until." Only the four connector-like types (`OpenApiConnection`, `OpenApiConnectionWebhook`, `Http`, `Workflow`) have a stated effect: inputs evaluated and recorded, then the mock supplies status, outputs and error. For Compose, the variable actions, Response, Terminate, ParseJson, Query and Wait the plan does not say what a mock replaces. Does a mocked SetVariable still set the variable? Does a mocked Response count as "the first Response action that ran"? Does a mocked Terminate still end the run? Are its inputs still evaluated? The BUILD-PLAN asks for mocks on the never-run types and for static results; the only stated need for the wider rule is an action of any type with a static result enabled, and no fixture has one. Separately, a mock's `status` is `Succeeded` or `Failed` only, yet `actionStatus` accepts `TimedOut` and flows use `runAfter` with `TimedOut` (the 409 Response in ReadEnvironmentVariable lists Skipped, Failed and TimedOut), so that path can never be exercised and the `TimedOut` assertion value is dead.
- Suggested fix: Limit mocks to the four connector-like types and to actions with an enabled static result, and make a mock on any other type fail the test with a message; or specify per type what the mock replaces. Either allow `TimedOut` as a mock status or say it is not testable and drop it from `actionStatus`.
- Resolution: fixed (only the four never-run types take a mock, plus any action whose static result is on; a mock on any other action fails the test; `TimedOut` is dropped from `actionStatus`, with the reason: no simulated run times out and mocks are `Succeeded` or `Failed`, the static-result statuses)

#### R4. Which never-run actions get a `Skipped` record is not defined for nested actions
- Area: 9 Testability (Data assertions, Automation outputs and records)
- Finding: Both fixture tests assert `Skipped` (`List_records` after the Terminate; the 409 Response). The plan says every call of every action is recorded, and an action with no call fails an assertion with "did not run", so what gets a `Skipped` record decides whether such an assertion passes. The plan covers actions whose `runAfter` is not met, the branch not taken, and actions not started when Terminate runs. It does not say what happens to actions nested inside those: `Delete_Environment` inside an `If` whose branch was not taken, actions inside a Scope that was skipped, actions inside a Foreach over an empty array (zero calls). The natural test, "no environment id, so `Delete_Environment` is not called", depends on it. Learn says actions in the branch that does not run are `Skipped`; it says nothing about a skipped Scope.
- Suggested fix: Add a rule: actions nested in any `Skipped` container get one `Skipped` record each (or none, and the test author asserts the container instead), and say which. State that a Foreach with zero iterations leaves its inner actions with no calls. Add one Core test for each case.
- Resolution: fixed (a "What gets a Skipped record" rule: every action nested at any depth in a skipped container, a branch not taken or what Terminate leaves unstarted gets one `Skipped` record; an empty Foreach leaves its actions with no call; both are listed under Not on Learn and have Core tests in Step 3)

#### R5. When an `unsupported` action type or function is detected is not stated, and some structural cases are undefined
- Area: 9 Testability (Automation: Expressions, Simulator)
- Finding: Expressions are parsed "when they are evaluated", and a function name is checked then. The action-type rule ("any other type ... is `unsupported`") does not say whether the whole definition is scanned before the run or the type is checked when the action is reached. This decides how strong the gate is, and BUILD-PLAN says "never a pass". Reached-only means a test that avoids a `Select`, a `Table` or an `addHours` call passes although the flow holds something PowerOps cannot simulate. A pre-scan means nearly any real flow with one `Select` anywhere is `unsupported` for every test, including tests of other paths. Both are defensible and opposite. Also undefined: a `runAfter` that names an action not in the same block, a `runAfter` cycle (the loop stalls or never ends; the 100 000-call cap covers loops, not a stall), a `runAfter` status that is not one of the four, a definition with more than one trigger (an Assumption only), and two cloud flows with the same name inside one solution (only a match in more than one solution is covered).
- Suggested fix: State the rule and put it in the README limits (suggest: types and `operationOptions` are checked when reached, like expressions, and say a skipped branch is not checked). Add: an unresolvable `runAfter`, a cycle or an unknown status is `unsupported`; more than one trigger is `unsupported`; two flows with the name in one solution fail the test as ambiguous. One test each.
- Resolution: fixed (types, `operationOptions` and functions are checked when reached, and the README says a path the run does not take is not checked; an unresolvable `runAfter`, an unknown status, a cycle and more than one trigger are `unsupported`; more than one matching flow, in one solution or several, fails the test; tests in Steps 3 and 4)

#### R8. Expression text rules are narrower than Learn's, and culture is not pinned

- Finding: The plan says "`@@` at the start is a literal `@`". A lone `@` mid-string that is not followed by `{` or `@` (an email-like literal) is not discussed. How the end of `@{...}` is found when a string literal inside it holds `}` or `'` is not stated. Text conversions (`string()`, `@{...}` of numbers, decimals, booleans, and `utcNow`/`addDays` default format) are not tied to the invariant culture, so goldens could depend on the machine's locale.
- Suggested fix: State: `@@` is an escape anywhere in a string; a lone `@` is literal; the `@{` scanner honours single-quoted literals; all conversions use the invariant culture. Add a test case for each.
- Resolution: fixed (`@@` is a literal `@` anywhere, listed under Not on Learn beyond Learn's two positions; a lone `@` is literal; the `@{` scanner skips single-quoted literals; invariant culture for every text conversion; Step 2 tests both)
