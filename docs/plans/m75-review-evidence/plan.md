# M75: Review evidence for the deployed zip, and a review check on the promotion routes

## Goal

Fix the evidence half of finding F39 of the PowerOps 1.0 trial (2026-11-08) and Codex's fix 1, as section 3 of the agreed 1.0 fix plan sets out (Fable and Astra, six rounds; amendments A3, A4, F-3, F-4), under the person's answers to Q2 (Round 0 in `decisions.md`) and to the two questions of Round 1:

| Id | Finding | This plan |
|---|---|---|
| F39 (evidence) | `deploy plan` links a zip to a report only by SHA-256. The roles hashed the unpacked unmanaged folder and the zip is the managed export, so the two never match, and the warning said nothing about what the reports did cover | For a zip that no report records, `deploy plan` prints a `note:` line per reviewed input of the same solution: that the input is still the one reviewed, and how many changes `diff` finds between it and the zip besides the managed flag (rows 3 and 4). It is evidence, never a link |
| Codex fix 1 | Only `deploy plan` warned. `deploy apply`, the MCP tool `deploy_apply`, `deploy gate` and the Action checked no report, and the warning accepted any one `ready` report | `deploy apply --require-reviews` refuses unless both reports of one plan folder are `ready`, written for the current plan, and record the zip's SHA-256 (rows 2 and 5). Done when:

1. `deploy plan` and `deploy apply` name, on stderr, each zip the plan imports that has no plan folder under `docs/plans` whose `verify.md` and `security-solution.md` are both `ready`, both carry the plan's current hash, and both record that zip's SHA-256 as their `solution-hash` (the warning texts of row 2). Neither changes its report or exit code for it. The Action's job log shows these lines for the plan and for the apply.
2. For a zip that no report records, `deploy plan` also prints the evidence of row 3: one note per reviewed input of a solution with the same unique name whose digest is still the reviewed one, or, when there is none, one line that counts the reviews whose input changed since. An input that is missing, is or passes through a symbolic link, leaves the repository root or can't be read gives no note and no error.
3. `deploy apply --require-reviews` (dry run and `--apply`) refuses with exit code 1 and status `refused`, before any import, when a zip the plan imports fails the check of item 1, when no `docs/plans` is found, or when it can't be read. Without the option the same run prints the warnings and goes on as today.
4. The MCP tool `deploy_apply` passes `--require-reviews` on every call, so a report that turns `blocked` between the form's dry run and the apply stops the apply with no import. `deploy gate` runs its dry run with the check on. The Action's `apply.sh` passes the option unless the new input `require-reviews` is exactly `false`; both example workflows set it to `'false'` and say why.
5. `docs/COMMANDS.md`, `docs/GITHUB-ACTION.md`, `docs/HANDOFF.md`, `docs/RECOVERY.md`, `docs/USE-WITH-AGENTS.md`, `docs/PLANNING-SKILLS.md`, `docs/examples/`, `docs/schemas/deploy-apply.schema.json` (one description) and `skills/powerops-implement/SKILL.md` say what changed. The `mcp-tools.txt` golden and the plugin skill copies are updated by the recipe.
6. `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status docs/plans/m75-review-evidence` and the leak scan are clean. The work is committed locally on the session's branch.

### Won't build

- Letting a clean `diff` satisfy `--require-reviews`. Both reviewers rejected it (F-3), and the person kept "zip hash only" (Round 1, Q2): `diff` doesn't compare security roles, tables, columns, forms, views or app modules and their role maps.
- The `deploy-hash:` line and the unpack provenance check. That is M83, the first 1.0.x milestone (the person's answer to the fix plan's Q1).
- Proof that a role wrote a report. The check reads what the two files say; whoever can write to the repository, the gated agent included, can write files that pass. It guards against importing an unreviewed or changed zip by mistake, and the form, the person's yes and the GitHub environment's approval stay the authorization (row 9 says so in the docs).
- A gate rule for an agent's own shell call of `powerops deploy apply --apply` or `powerops settings apply --apply`. The gate matches Microsoft's import tools, not powerops' own commands, so that call gets the warnings only; it stays under the instruction never to run it without the person's yes (AGENTS.md, `powerops-implement` step 7). Blocking it would be a new gate rule, outside this milestone.
- A way to turn the check off for the MCP tool or the gate. Only the Action has one (Round 1, Q1), in the workflow file.
- A warning from `deploy plan` or a bare `deploy apply` when no `docs/plans` exists at or above the folder. `deploy plan` is silent there today, for repositories that don't use the planning skills; `--require-reviews` refuses there.
- A comparison of the report's `input:` with its recorded digest inside the rule. The zip's own SHA-256 equal to the recorded hash already says the reviewed bytes are the ones imported, wherever the input is now.
- The evidence note in `deploy apply`. It needs a second solution load and a `diff`; the apply prints the warnings only.
- A check of the plan's `status`. The roles write a report only for a signed-off plan, and a report must carry the plan's current hash.
- A rework of the example workflows so that they deploy a zip a role reviewed, and a move of their action pin. Their zip is built in CI, so they set `require-reviews: 'false'`; the pin they use predates the input (the old commit ignores it with GitHub's unknown-input warning) and moves in a follow-up after the merge, as the earlier pin changes did.
- Any change to the kept roles (`powerops-verify`, `powerops-review-security`), their plugin copies or `tests/eval`.
- A new field in `deploy apply`'s JSON. A refusal uses the existing `refused` status and `message`; only the schema's description of `refused` gains the new reason.

## Users

- A maker or reviewer reading `deploy plan`'s stderr (the CLI, the MCP tool's result or the Action's job log) before approving an import.
- An agent that imports through the MCP tool or a gated Microsoft import tool, which is refused until both reports cover the zip. Its own `powerops deploy apply` call only warns (Won't build).
- A person who runs `deploy apply` themself, who sees the warnings and decides.
- A workflow author who sets or leaves the Action's `require-reviews` input.

## Assumptions

- A managed and an unmanaged export of one version differ under `diff` only in the managed flag: checked 2026-11-09 on the one such pair in `tests/fixtures/zips` (`ColumnLevelSecuritySampleSolution.zip` against `ColumnLevelSecuritySampleSolution_managed.zip`): `1 change`, `solution managed: unmanaged → managed`. That pair holds one table with masking rules and no flow, canvas app, connection reference, environment variable or agent, so the claim is unchecked for those. The note doesn't depend on it: it prints whatever count `diff` finds.
- Until M83, a report covers a zip only when the role ran with that zip as its current solution, because `powerops manifest <zip>` gives the SHA-256 of the zip's bytes (`Manifest.cs:46`) and a folder's digest is another value. The roles can't read files inside a zip, so such a report marks roles, tables, forms and views "not verified" (`skills/powerops-verify/SKILL.md:48`). The person chose this over a `diff`-based pass (Round 1, Q2).
- Nobody has yet seen the kept roles write `state: ready` for a managed zip. A role that can't run a required check writes `failed`, and one with an open High finding writes `blocked`; if a zip review usually ends that way, the agent and CI routes refuse every import until M83 and the person's CLI is the route. The second trial is the first check of it.
- So a review of the unpacked folder, as in the first trial, never passes `--require-reviews`. In the second trial the "passes with both ready" case of the fix plan's re-trial check needs both roles run on the managed zip, or it is exercised through the person's CLI; the hand-over note says so for the trial's brief.
- A zip built in a workflow (the promotion example exports it on the pull request) is other bytes than any zip a role read, and that example's plan file sits under the runner's temp folder, outside the checkout that holds `docs/plans`.
