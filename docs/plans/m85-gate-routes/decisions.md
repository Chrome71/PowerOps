# Decisions: m85-gate-routes

Q1 is the owner's. Every other decision below was made by the planner (Opus, a planning subagent of the orchestrating session) inside Q1, and none needed the owner.

## Round 1 (planning)

### Q1. How should the gate treat pac's preview groups?
1. Keep the gate's scope and add deny rules: the gate keeps its job (installs, imports, uploads and publishes of content no plan holds), gains one route, the MCP tool `install-application-package`, and the two misread commands get fixed (a certificate upload and a prefixed `pa app push`); the preview groups stay unrouted, and the docs list them and give deny rules to copy
2. Block whole preview groups by name, reads included
3. Block preview writes by name

Decided: 1, by the owner, in chat on 2026-11-10, in the words above as they were offered. The reason given: the docs already say that deny rules are the control and that the gate is defence in depth (`docs/HANDOFF.md:103`, decision 41 in `docs/BUILD-PLAN.md`).

### Q2. `pac power-pages upload-certificate`: a narrow pass or a block with a correct message?
1. A narrow pass: the one subcommand pair `power-pages upload-certificate`, read as the second and third literal words of a `pac` call in a Bash or Monitor command, passes when no word after it holds a marker; every other spelling keeps today's reading (recommended)
2. A block with its own route line
3. A change to the marker regex so that `pages upload` no longer matches inside `power-pages upload-certificate`

Decided: 1, the orchestrator's lean, confirmed. A certificate upload is a site-settings write of the preview group `pac power-pages`, like `create-website`, `enable-waf` or `add-ssl-binding-by-portal`, which pass today; under Q1 the group is unrouted, so a block (2) would single out one of its 40 commands by an accident of spelling and would be a route the owner did not choose. Option 3 changes what every text scan matches (`grep`, commit messages, the leftover check), and needs a variable-length lookbehind for `power-` to keep `pac pages upload-certificate` blocked; a `case` in the existing `pac` switch is one line beside its neighbours and touches nothing else. The pass copies the rule the `node` passes already follow ("a pass must hold no marker", `ImportCall.cs:336`): a backtick or `$(...)` inside a quoted argument runs a command, so a marker in any later word sends the call to the default branch, which blocks it as unreadable. The switch lowercases, so `pac Power-Pages Upload-Certificate` passes like the lowercase form; mixed case of a blocked form (`pac PAGES Upload`) still blocks with its route. The `case` also needs `words.Length > 2` (Fable's round-1 finding 2): the switch key joins `words.Skip(1).Take(2)`, so `pac "power-pages upload-certificate"`, one quoted word with nothing after it, would match the key while the guard saw no later word; with the length check it falls to the default branch and stays unreadable, as today (run on 2026-11-10). The `PowerShell` branch blocks every `pac` call and is unchanged, so the pass is for Bash and Monitor only, and the docs say so. Checked on 2026-11-10: of the 222 commands that `pac help` lists in the 16 preview groups (`pac` 2.14.1, no sign-in), only `power-pages upload-certificate` hits a marker; of the 284 MCP tool names turned into `pac <words>`, the only marker hits are this one and the routes the gate already has.

### Q3. A `pa app push` led by an assignment: what rule?
1. A word is an assignment when its raw text, with backslash-newline pairs removed, matches `^[A-Za-z_][A-Za-z0-9_]*\+?=`; the program is never taken from an assignment word; leading assignments are skipped only to find a `pa`, `power-apps` or `npx` call, and only when every such word is literal; a segment led by an assignment is never read as `pac` or `node` (recommended)
2. Skip leading assignments for every program
3. Skip them only for `pa`, and leave `pac` and `node` as they are

Decided: 1. The `pa app push` route always blocks, so reading through the assignments can only change its message. Option 2 would let `X=1 pac solution import ...` reach the import check and pass, though an assignment can change `PATH` or what `pac` loads; the owner's constraint and the existing test (`ImportCallTests.cs:300`) keep it blocked. Option 3 leaves a misparse found while planning: today the program is the file name of the first word, so `PATH=/tmp/x/pac solution import --path <zip> --environment <env>` is read as a `pac` import (run on 2026-11-10 with the gate built from `d755cf1`: it reached the zip check), although the shell runs a program named `solution`; and `X=a/node <bundle> pull` passes as a `node` call. Under option 1 both block as unreadable.

The shape (Fable's round-1 finding 1): the first version tested `^[A-Za-z_][A-Za-z0-9_]*=` on the raw text, which misses two shell assignments, and each of these still reached the zip check on the gate built from `d755cf1` (rerun by the planner on 2026-11-10): `PATH+=/tmp/x/pac solution import ...` (bash and zsh read `NAME+=value` as an assignment), and `PATH\` newline `=/tmp/x/pac solution import ...` and `PA\` newline `TH=/tmp/x/pac ...` (the shell joins the lines first; the raw text keeps the backslash and newline while the value is `PATH=/tmp/x/pac`). So the test is on the raw text with backslash-newline pairs removed, and accepts `\+?=`. It stays on the raw text, not the value, because a quoted or escaped name (`"PA_CLI_ORIGIN=x" pa app push`) is not an assignment to the shell, which runs it as a command name; that keeps today's reading. A non-literal value (`$`, a backtick, `$(...)` in quotes) is skipped for no `pa` call and stays unreadable, because the gate does not read what it expands to.

What this changes (Fable's round-1 finding 2): taking the program never from an assignment word also turns some blocks into passes. Today the program of `X="$HOME"/pac org who`, `PATH=/x/pac $A $B` and `X=/a/pac model genpage $Y` is `pac`, and a non-literal word among its first three blocks it as unreadable; `PATH=/x/pac org who 'abc` blocks on its unclosed quote because the `pac` call set `candidate`; and `X=a/power-apps.cmd push` gets the `pa app push` route (each run on 2026-11-10 against `d755cf1`: exit 2). Under option 1 each of these five segments is unrecognized and none holds a marker (in the last, `.cmd` sits between `apps` and `push`), so each passes. The orchestrating session decided, following the reviewer's pick, that the new reading is the right one, because the shell runs the next word, not `pac` (or `power-apps.cmd`): the plan restates its invariant as the exact list of reading changes (Constraints) and pins each with a test (row 4 (e), (f)). The `.cmd` form is accepted under the same rule: the shell runs `push`. Two other forms change their message only and still block: `X=a/pa app push` and `X=a/power-apps push` go from the route to unreadable, because the marker `apps?…push` stays in the unread segment (in the second it matches `apps push` after the `-` of `power-apps`). The revision after round 1 listed `X=a/power-apps push` as a new pass; Fable's round-2 finding 1 showed it holds the marker (on `d755cf1`, `echo a/power-apps push` exits 2 "can't read", and in the reviewer's scratch copy with rows 1 to 3 applied it does too), so it moved to the unreadable list and the `.cmd` form took its place among the passes. `X=1 pac org who` passes today and still will: only an import or route marker in such a segment is blocked, and the docs say exactly that (round-1 finding 6).

### Q4. Does the gate read `env NAME=value pa app push`?
1. No: it stays unreadable, exit 2 (recommended)
2. Yes: skip `env` and its assignments too

Decided: 1. `env` takes options with their own grammar (`-S` splits a string into words, `-i`, `-u`, `-C`), so reading it is a new program to model, not a narrow fix; the call already blocks. Microsoft's code-apps hook tests list `env PA_CLI_ORIGIN=custom npx --no-install pa app list` among the forms it does not rewrite (`plugins/code-apps/scripts/tests/cli-origin.test.js:84` at power-platform-skills `4076781`).

### Q5. What deny-rule form do the docs give?
1. Claude Code: one `permissions.deny` list to copy, with the six gated MCP tools by exact name and one glob per write-holding preview group (`mcp__pac-cli__<group>_*`); Codex: an `enabled_tools` allow-list of the tools the session uses, with exact names (recommended)
2. Exact names of every write tool of the preview groups, for both clients
3. Advice to run pac's MCP server only with the tools you need, no list

Decided: 1. Verified on 2026-11-10:
- Claude Code: the permissions page (code.claude.com/docs/en/permissions, section "Tool name wildcards") says deny and ask rules accept glob patterns in the tool-name position, the pattern must match the full tool name, and a tool matched by a glob deny rule is removed from Claude's context; allow rules take a glob only after a literal `mcp__<server>__` prefix, with `mcp__github__get_*` as its example. Claude Code's changelog (github.com/anthropics/claude-code `CHANGELOG.md`, read 2026-11-10) dates the feature to 2.1.166: "Added glob pattern support in deny rule tool-name position". The smoke pin is 2.1.303, so every build the docs record has it. So `mcp__pac-cli__power-pages_*` is a documented deny rule. Evidence: documented, not tested.
- Codex: its MCP page (learn.chatgpt.com/docs/extend/mcp) calls `enabled_tools` a "Tool allow list" and `disabled_tools` a "Tool deny list (applied after `enabled_tools`)", and does not say whether they take patterns. Codex's code answers it: `ToolFilter::allows` in `codex-rs/codex-mcp/src/tools.rs` tests `HashSet::contains` on the server's raw tool name (`tool.tool.name`), the same at `rust-v0.163.0`, `rust-v0.167.0` and `main` (`3f797555cd`, read 2026-11-10), and `codex-rs/config/src/mcp_types.rs` at `rust-v0.167.0` documents the two fields as "Explicit allow-list" and "Explicit deny-list". So both take exact, raw names (`pages_upload-code-site`, with its `-`), and no pattern. A `disabled_tools` list of the preview writes would hold about 100 names (102 preview tools whose verb is not get, list, search, show, verify, download, retrieve or query, by the planner's count), so the allow-list is the shorter honest recipe.
A group glob also hides that group's reads; the docs say so, and say to list a group's write tools by exact name instead when its reads are needed. Option 2 is about 100 lines to copy and goes stale with each `pac` release; option 3 gives the reader nothing to copy, which Q1 asks for.

Tested or documented (Fable's round-1 finding 3): the first version planned no probe. Claude Code 2.1.322, Codex 0.167.0 and `pac` 2.14.1 are on this machine, and pac's server lists its tools with no sign-in, so a no-tenant probe of the Claude Code list costs one headless session. Step 3 runs it before the docs step: a control run and a deny run in a scratch folder outside the repo, `--setting-sources project` and `--strict-mcp-config` so only the probe's settings and server count, one prompt that needs no tool, and only the `init` event read (row 12). The docs, `changes.md` and compatibility line 32 say what its outcome supports, and "tested on <build>" only for the list that ran (review R2: step 3 logs the deny array it ran with, and step 4 checks the published fence is the same set). The outcomes (Fable's round-2 finding 2, review R3, the orchestrating session's decision): first, (i) the probe can't see (`pac-cli` not connected, or the control's `init` list holds no `mcp__pac-cli__` tool, as when tool search defers MCP tools), which gets one retry of both runs with `ENABLE_TOOL_SEARCH=false` before it is recorded; then the six exact names act as the control inside the deny run: (a) the six and the group tools are gone, so tested; (b) the six are gone and group tools stay, so globs don't apply on that build; (c) any of the six stays, so the probe can't tell (settings not loaded, or `init` doesn't reflect deny rules), which keeps "documented, not tested". For (b), the planner's choice of the smallest recipe that still holds: the docs say so with the build and don't offer the globs as working; the fence is cut to the six exact names, which the probe did test; and for the preview groups the text gives `mcp__pac-cli`, the documented whole-server rule (not a glob), for sessions that don't use pac's MCP server, or each write tool by exact name. An allow-list is no answer in Claude Code, because an allow rule does not hide a tool. The Log names the outcome. Both runs may use `--model haiku`, since the prompt needs no reasoning.

What the list covers (review R1, the orchestrating session's decision): the fence stays the six gated tools and the preview groups, which is what the owner chose, and does not grow. The docs stop calling it the control without limit: one sentence beside the fence says it covers those only, names pac's non-preview MCP writes that the page already lists as unrouted (`admin_self-elevate`, `admin_update-tenant-settings` and the other `admin` writes, `env_update-settings`, `model_create`, `model_genpage_add`, `model_genpage_remove`, all in the `tools/list` reply), and tells the reader to add them by exact name if unused; `HandoffDocTests` holds that sentence's names. Codex stays documented: its `ToolFilter::allows` is a `HashSet::contains` on the raw name, so a client run would add little.
