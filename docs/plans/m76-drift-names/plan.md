# M76: `drift` keys dynamic component types by definition name and matches agent components by schema name

## Goal

Fix finding F40 of the PowerOps 1.0 trial (2026-11-08), as section 3 of the agreed 1.0 fix plan sets out (Fable and Astra, six rounds; amendments A6 and F-7):

| Id | Finding | This plan |
|---|---|---|
| F40 / D5 | `drift` compares components by `(componenttype, objectid)`. Type numbers of 10000 and above come from each environment's component definitions (the agent was type 10226 in Dev and 10229 in Test, its components 10227 and 10230), and an imported agent and its components get new ids. After the trial's import `drift` reported 53 items and exit `1`: 48 were the agent's parts (bot, botcomponent, botcomponent_connectionreference) under other numbers and ids, 4 extra type-10090 components in Test (AppSetting there, SettingDefinition in Dev) were unexplained, and 1 was real | A live read now also reads the names of the dynamic types, the solution's agents and its agent components, when the solution holds them. Components of types 10000 and above are keyed by their definition name; agent components by schema name; agents are compared as agents (rows 3 to 6). The kinds of component whose rows can get new ids on import, `appsetting` and the agent link tables (`bot_botcomponent` and every `botcomponent_*`), are left out by name and counted under "not compared" (row 6). That explains the record's type-10090 items as information instead of drift |

Done when:

1. A live `drift` of a solution that holds a component of type 10000 or above that is not one of its connection references reads that environment's component definitions, and, when the solution holds an agent or agent components, its agents (`bot`) and agent components (`botcomponent`), each in one read of one page (rows 2 to 4). A solution whose only types of 10000 and above are connection references, or that has none, makes none of these reads, so its cost and the role it needs are as today.
2. Two environments that hold the same agent under other type numbers and other ids give no item and exit `0`; an agent on one side only gives `agent-missing` (drift); an agent component on one side only gives `component-missing` or `component-extra` named `botcomponent <schema name>`; two components that share a number but have different definition names never match; equal counts with one changed schema name still give items; an agent or agent component the read did not return is compared by id and counted under "not compared" (row 6). An agent published on one side only gives `agent-published` (information).
3. A snapshot with names is written at version 2 with the new fields; a snapshot without names (not installed, or a deploy target) is still written as the version-1 text, byte for byte, so `deploy plan`'s target digests and plan hashes don't move and plan files made before this change still match. A version-1 file still loads. A pair where one side has no names is compared by today's keys, and "not compared" says so when that pair keys a component of type 10000 or above (rows 5 and 6). Both orders are tested.
4. `drift --format json` is at `schemaVersion` 2 (`JsonOutput.DriftSchemaVersion`), with the two new kinds in `drift.schema.json`, and a test holds the schema's `kind` list equal to `DriftKind.Order`; `snapshot.schema.json` accepts versions 1 and 2 (row 7).
5. `docs/COMMANDS.md`, `docs/schemas/README.md` and `tests/fixtures/NOTICE.md` say what changed; goldens are regenerated by the recipe, and only `drift-*.json` (the version) and `snapshot-seed.json` change (rows 7 and 8).
6. `dotnet build` (0 warnings), `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status docs/plans/m76-drift-names` and the leak scan are clean; the work is committed on the session's branch.

### Won't build

- One read per agent or per agent component. One FetchXML per table, linked to the solution, gives the whole set in one page (A6; the fix plan rejected per-component reads).
- The new reads in `deploy plan`'s and `deploy apply`'s target read. `DriftLiveReader.ReadTarget` keeps today's reads. The fix plan's line on `DeployPlan.cs` `AddUpgrade` (the `components-not-checked` inventory) is left out, a deviation the PR body names: it needs names from the target, and a definitions read there would make `deploy plan` need read on `solutioncomponentdefinition`, which the read-only role documented in `docs/examples/README.md` and tested live on 2026-11-04 doesn't list. The inventory is information only and stays by number (`decisions.md`, Log).
- Matching by count. Counts are printed for the kinds left out by name, as information, never as identity (A6).
- A check that each kind left out by name really gets new ids on import. `appsetting` follows M12's manual run (10087 was AppSetting); `botcomponent_connectionreference` follows the trial record (matched only by count); the other agent link tables follow Learn's `botcomponent` page, which lists them, and are not shown to change ids (Not checked). A kind not left out by name whose ids change shows as drift, and the second trial verifies those items one by one.
- Names on the `unmanaged-layer` and `also-in-solution` subjects. They keep `<componenttype> <id>`.
- A change to `deploy apply`'s agent read-back (M73), the MCP `drift` tool's text, the kept roles, their plugin copies or `tests/eval`.
- A changelog entry.

## Users

- A maker or reviewer reading `drift` after a promotion of a solution that holds a Copilot Studio agent, who needs exit `1` to mean drift.
- A CI job that saves snapshots and compares them later, which must keep loading the version-1 files it already has.

## Assumptions

- Types of 10000 and above are per environment and defined in `solutioncomponentdefinition`. Learn has no page for that table, and its `solutioncomponent` page lists no `componenttype` above 432. Microsoft's open-source `microsoft/power-platform-skills` (MIT, `plugins/model-apps/scripts/lib/app-theme.js:210-219` at `da8ea7a`, 2026-11-03) says "The appsetting solution component type differs per environment, so it is read" and reads `solutioncomponentdefinitions` with `$select=solutioncomponenttype,primaryentityname`. The trial record observed it too (10226/10229, 10227/10230). The entity set and both column names of read 9 come from that code, not from Learn.
- An imported agent and its components get new ids. The trial record observed it; Learn's *Export and import agents using solutions* lists "CDS Bot ID" among the agent properties that don't transfer, and is silent on agent components.
- `bot` (`bots`: `botid`, `schemaname` "Unique name identifying the agent", 100 characters, `publishedon`) and `botcomponent` (`botcomponents`: `botcomponentid`, `schemaname`, 100 characters, solution-aware) are on Learn's table references. Learn doesn't say `botcomponent.schemaname` is unique.
- Learn's `botcomponent` page lists its link tables `bot_botcomponent`, `botcomponent_aipluginoperation`, `botcomponent_botcomponent`, `botcomponent_connectionreference`, `botcomponent_dvtablesearch`, `botcomponent_environmentvariabledefinition`, `botcomponent_msdyn_aimodel` and `botcomponent_workflow`; `botcomponent_connectionreference` has its own page (entity set `botcomponent_connectionreferenceset`) with the solution-aware columns. Learn's settings page says settings "are solution components"; it has no reference page for `appsetting` or `settingdefinition`, and the logical name `appsetting` comes from the `power-platform-skills` code above.
- Read rights: Learn's *Secure your Copilot Studio projects* gives System Administrator and System Customizer organization read on `bot` and `botcomponent`, and Environment Maker user level (its own agents only). An agent another maker owns is then not returned: it is compared by id and counted under "not compared" (row 6), or, when one side returns it and the other doesn't, shows as `agent-missing`. Nothing on Learn covers read rights on `solutioncomponentdefinition`.
- Each read returns one page of at most 5,000 rows (Learn, *Page results by using FetchXML*); a second page is refused as today.
