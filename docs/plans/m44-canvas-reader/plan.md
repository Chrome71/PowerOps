# M44: Canvas reader

## Goal

Read the canvas formulas of each `.msapp` in an unpacked XML folder and in an exported zip, so PO014 covers the layouts that `docs/HANDOFF.md` commits, and warn about `ForAll` around `Patch` and `ForAll` inside `ForAll` in every layout. This is M44 of Phase 7 ([plan](../phase7-power-platform/plan.md), build-order item 79, release label v0.27.0), with its "Stops if" rule, decision 49 (D10) for inputs an export doesn't hold, and the F1 fact read from Dev on 2026-11-03 (Assumptions).

Done when:

1. `SolutionParser` opens each `CanvasApps/*.msapp` of a folder or zip read-only as a zip, in memory, and reads every `.pa.yaml` entry under `Src/` (either path separator, any case) through the same YAML conversion and formula walk the YAML layout uses, into `Solution.CanvasFormulas`. The reads stay under the solution's `ReadBudget`: the `.msapp` up to the outer zip's size cap, its entry count before it is parsed, each `Src` entry's declared and actual bytes, the solution total, and the YAML conversion's nodes; no entry is written to disk. A `.msapp` that starts with the zip signature but can't be read, or a `.pa.yaml` that can't be, is an `InvalidDataException` whose message starts with the `.msapp`'s path.
2. A canvas app whose `.msapp` gives no `Src/*.pa.yaml` (an older app, or a file that isn't a zip, such as an empty file or a Git LFS pointer, which is not opened) gives one `note:` line on stderr through `analyze`, `baseline` and the MCP tool, with no finding and no exit-code change (D10).
3. PO014 fires on a hard-coded URL in an `.msapp` formula with the same message as in the YAML layout, and in both XML layouts the same finding.
4. PO018, warning: a formula that calls `Patch` inside `ForAll`, or `ForAll` inside `ForAll`, with firing and quiet tests in `WarningRuleTests`, a page with a dated Learn Sources line, and a row in `docs/rules/README.md`. It reads `CanvasFormulas`, so it covers the YAML layout too.
5. Tests build their `.msapp` in code (`SolutionZip`); no `.msapp` file is added to the repo. The hostile-input cases (too many entries, an oversized entry, too many YAML nodes, deep YAML, a broken zip) are refused with the path, in the reader tests and at the command level in `ReaderLimitsTests`, and `MutationTests` flips `.msapp` bytes.
6. The goldens change only as the Data section says. `RoleEvalTests` passes with no eval file changed: no eval case's `analyze` output changes (decisions Q3), and `powerops-verify` and `powerops-review-security` keep their blob ids (`69208a2ed044a346bbae9877c8cd74d9e4794df9` and `6a6a6a1fdb71eb16d09cf3ed99406d04a0982a1f`).
7. `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status .` and the leak scan are clean, and one `feat:` PR is open.

### Won't build

- A Power Fx parser: a token scan with a `shortcut:` note finds the two call shapes PO018 needs (the Phase 7 plan's "Deliberately doesn't").
- Reading `AppCheckerResult.sarif`: F1 shows it is still in a fresh `.msapp`, but its format inside the package is undocumented; a later milestone can read it (Phase 7 plan).
- Rules for 256,000 characters, more than 2 dependent screens, `TabIndex`, `FluentV8/*`, control counts, library size or delegation (the Phase 7 plan's "Deliberately doesn't" and "Won't build").
- The retired `*.fx.yaml` layout of `pac canvas unpack` or `--processCanvasApps` (`CanvasApps/src/<app>/`): Learn calls the format retired, and the `.msapp` beside it is what the import uses.
- Any JSON file of the `.msapp` (`Controls/`, `References/`, `Properties.json`): Learn says only `Src/*.pa.yaml` is source and the JSON isn't stable between saves.
- A change to PO005 (decisions Q2).
- A note for a canvas app whose metadata names a `.msapp` the solution doesn't hold (decisions Q3): all seven eval solution cases name a scrubbed `.msapp`, so the note would change every eval baseline. The PO014 and PO018 pages say such an app isn't read.
- A note for a YAML-layout app with no `Src`: Git integration writes `Src` for every app, and the YAML reader is unchanged.
- A count or formula field in `--json`, SARIF or the baseline: findings only, no schema change.

## Users

- A maker or agent who runs `analyze` on an export or an unpacked folder before review: PO014 and PO018 now see the app's formulas, which before this milestone only the YAML layout gave.
- CI: the Action runs `analyze` with `--fail-on error` by default, so the new findings change no exit code there. A job set to `fail-on: warning` fails on new PO014 findings in XML-layout apps and on PO018 until they are fixed or baselined. New `note:` lines on stderr change no exit code.
- An agent through the MCP `analyze` tool, which already passes on stderr `note:` lines (`McpCommand.cs:152`).
- Every command that loads a solution (`analyze`, `baseline`, `diff`, `test`, `settings`, `deploy` and their MCP tools) goes through the same parser, so it now opens each `.msapp` and parses its `Src/*.pa.yaml`. A `.msapp` that starts with the zip signature but can't be read, one over the 100 MB zip cap, or a `.pa.yaml` the YAML conversion refuses (anchors, too deep, too many nodes), stops it with exit 3, as a malformed YAML-layout file does today. A `.msapp` without the signature (an empty file, a Git LFS pointer) is not opened and gives the note, as a `*.zip` without it is skipped by discovery today. Entries outside `Src/` are never opened.
