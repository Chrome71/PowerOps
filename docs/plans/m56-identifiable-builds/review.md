### High

#### R1. The release tag is not `v<version>`; the version derivation and the download URL would fail on the first release
- Area: Done when 1, 2 and 3; rows 3 and 4; Assumptions ("`include-v-in-tag` is true, so the tag is `v<version>`")
- Finding: The plan, `release.yml`'s `Check the version` ("the tag without its `v`"), `install.sh` ("the release `v<version>`") and the tests all assume the tag is `v0.1.0`. `release-please-config.json` sets `package-name: PowerOps` and no `include-component-in-tag`. In release-please that option defaults to true and the component defaults to the package name, so the tag is built as `<component>-v<version>`: `PowerOps-v0.1.0`. The evidence is in this repository: release PR #4 is titled "chore(main): release PowerOps 0.1.0" and its branch is `release-please--branches--main--components--PowerOps`; the title pattern only carries the component when it is included in the tag. In the source, `TagName.toString()` returns `${component}${separator}v${version}` when a component is set, and `getComponent()` returns it unless `includeComponentInTag` is false. Then `${TAG#v}` leaves `PowerOps-v0.1.0`, the step looks for `artifacts/PowerOps.PowerOps-v0.1.0.nupkg` and fails, so the first release gets no assets; and the Action's download of `.../download/v0.1.0/...` would 404 even if the assets were attached by hand under the real tag. Every test the plan lists passes with this bug, because they read YAML text or stub `curl`.
- Suggested fix: Decide one of two, record it in `decisions.md`, and test it. (a) Add `"include-component-in-tag": false` to the package in `release-please-config.json` (a config edit, not a version edit; release-please regenerates PR #4's title itself, nobody edits it), and extend the `BuildPropsTests` case of row 7 to assert it and `include-v-in-tag: true`. (b) Keep the tag as it is and use the real name everywhere: derive `<v>` as `${TAG##*-v}`, or better take the `version` output of the release-please step (the action exposes `version` beside `tag_name`) and pass it to `publish` as a job output, and have `install.sh` build the URL from a tag value that the pin stores (add a third pin value, or store the full tag in `PO_RELEASE`). Whichever is chosen, fix the Goal/Done-when wording ("its tag without the `v`"), the first-release steps, and the `pin-drift` message.
- Resolution: fixed (option b): release-please's tag stays as configured (`PowerOps-v<version>`); `publish` takes `tag_name` and `version` from release-please's outputs and never parses the tag; `install.sh` and `pin-drift` use `PowerOps-v<version>`. Goal, Done when 1 and 2, rows 3 to 5, Assumptions and decisions Q14 changed; the config is not touched, so PR #4 is not either
