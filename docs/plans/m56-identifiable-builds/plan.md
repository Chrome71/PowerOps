# M56: Identifiable builds

## Goal

Make every PowerOps build say which build it is, and ship releases as files a reader can check. This is M56 of the improvement plan written after the live test of 2026-11-04 (requirement R1), part of its P0 block. That plan, its reviews and the person's answers to its decisions are kept outside the repo, because they quote a private test run. The live test found that the installed tool and a rebuilt one report the same version (`Directory.Build.props:11-12` turns the commit off and holds `0.0.0`), so a plan file's `tool` (`tool: 0.0.0`) cannot name the build that made it (CX-7), and the `tool` check that `deploy apply` runs passes between any two commits (the M10 review said the same). It also found that the apply report's tool version is all an auditor has to tell builds apart (C-5, B-4's tool half).

D4 is answered by the person: "GitHub Releases only (Recommended)". The channel is GitHub Releases, with no NuGet. release-please stamps the version, the release workflow attaches the tool package and a checksum, and the Action downloads a pinned, checksummed release.

Done when:

1. A build from a git checkout prints `<version>+<full commit>` for `powerops --version`, and the same text is the `tool` of its plan and apply files and the MCP server's version. So does the Action's source build of a commit it is pinned to, though the runner unpacks it without `.git`. A release build prints the plain version, release-please's version for that release.
2. The release workflow, on the release that release-please creates, packs at the tag, refuses to go on unless the packed tool's `--version` prints release-please's version, writes `SHA256SUMS`, attests the package's provenance, and attaches `PowerOps.<version>.nupkg` and `SHA256SUMS` to that GitHub Release. Nothing goes to NuGet. A failed `publish` has a written recovery that needs no re-run (row 6).
3. `action.yml` holds a release pin (a version and the SHA-256 of its package). With a pin it downloads that release's package, refuses it unless the SHA-256 matches, and runs it. With an empty pin, as now, before the first release, it builds from source in locked mode as before.
4. `pin-drift.yml` warns when the release pin is not the latest release that `.release-please-manifest.json` records, and when the Action's scripts changed after the pinned release.
5. The version files keep changing only through a release: a test holds the props version and the manifest equal and stamped by release-please, beside the existing `plugin.json` test.
6. The docs say how to install a release and check it, what the Action runs, that a plan is valid only for the build that made it, and how a maintainer cuts a release, recovers a failed attach and moves the pin. `DocsDriftTests` stays green.
7. `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status .` and the leak scan are clean; the PR is green on all eight checks.

### Won't build

- A NuGet package, a NuGet push or Trusted Publishing setup (D4). The NuGet steps of `release.yml` are removed.
- A tag, a release or a pre-release made by this milestone, a merge or edit of release PR #4, a change to how release-please names tags or titles PR #4, or any version edit by hand. The first release is the person's step (decisions Q8).
- A workflow that moves the Action's pin by itself after a release (decisions Q5), or a `workflow_dispatch` route that publishes for an existing release (decisions Q13).
- A check, in the Action, of the release's attestation: the pinned SHA-256 binds the bytes (decisions Q4).
- A self-contained or single-file build, or builds per operating system: the package is the framework-dependent tool that `dotnet tool install` takes.
- Draft releases for GitHub's immutable releases, which are off in this repository (decisions Q7).
- A `dirty` mark for a build with uncommitted changes (decisions Q2).
- A Windows leg of ci's `action` job (decisions Q15).

## Users

- A person who installs PowerOps and wants to know, and check, which build they run.
- A reviewer or auditor who reads a plan file or an apply report and wants to know which build made it.
- A workflow author who pins the Action by commit and wants the commit to fix the bytes it runs.
- The maintainer who cuts a release and moves the pin.

## Environments and route

No tenant. Every test runs offline: the release download against a stub `curl` and a zip the test makes, the release check against a stub `dotnet`, the release workflow by reading its YAML. No tag, release or pre-release is created, and nothing is published.

The first release is the person's step, after this PR is merged (decisions Q8):

1. Merge release PR #4, which release-please keeps up to date. release-please tags the release and creates the GitHub Release, and the `publish` job attaches the package and `SHA256SUMS`. If `publish` fails, CONTRIBUTING gives the recovery.
2. Check it: download both files, `sha256sum -c SHA256SUMS`, `gh attestation verify` on the package.
3. Move the pin: one PR that sets `PO_RELEASE` and `PO_RELEASE_SHA256` in `action.yml` to the release's version and the hash on its package's line of `SHA256SUMS` (the first 64 characters, not the whole line). CI's `action` job then runs the downloaded release, and `pin-drift` stops warning.

## Assumptions

- Learn, checked 2026-11-04 with the Learn MCP tools. "Source Link included in the .NET SDK" (.NET 8 breaking changes): from .NET 8, `InformationalVersion` includes `SourceRevisionId`, and setting `IncludeSourceRevisionInInformationalVersion` to `false` turns it off. "MSBuild reference for .NET SDK projects": the property defaults to `true`; the SDK fills `SourceRevisionId` with the commit hash when Source Link is present; "When set, its value is appended". Observed here with the SDK of `global.json`: a build with the property on prints `0.0.0+b8ad9049cc52d8dcb2284f581d6f470384e0120e`, the full `HEAD`; in a `git archive` copy (no `.git`) it prints `0.0.0`, and with `-p:SourceRevisionId=<that commit>` it prints the version and the commit.
- Learn, checked 2026-11-04 with the Learn MCP tools. Power Platform Well-Architected, "Recommendations for safe deployment practices" (OE:10), the source the improvement plan cites for R1, general recommendation 1: "Implement versioning across your build artifacts to help ensure that you can roll back and roll forward when necessary." "Recommendations for securing a development lifecycle", "Keep versioned artifacts": keep a catalog of all deployed assets and their versions.
- GitHub, checked 2026-11-04: immutable releases are off in this repository (`GET /repos/Chrome71/PowerOps/immutable-releases` gives `enabled: false`). With them on, assets can't be added to a published release, which is when `publish` uploads (decisions Q7). The repository is public, so a release asset downloads without a token. "Re-run workflows and jobs" (read 2026-11-04): a re-run uses the run's commit and ref, works up to 30 days after the run and at most 50 times. It does not say that a re-run of failed jobs reuses the outputs of the jobs that passed; that is observed behaviour that many workflows rely on, not a documented one, so the recovery does not depend on it (decisions Q13).
- release-please, checked 2026-11-04 (its config schema, and the review's read of its source): `include-component-in-tag` defaults to `true`, and the component defaults to the package name, so with `package-name: PowerOps` the tag is `PowerOps-v<version>`; release PR #4's title ("release PowerOps 0.1.0") and branch carry the component. The action's `version` output is the release's version. The `generic` updater rewrites the line marked `x-release-please-version`, and the two `json` updaters the `plugin.json` versions. Release PR #4 changes the manifest, the changelog, `Directory.Build.props` and both `plugin.json` files.
- The runner unpacks an action used as `<owner>/<repo>@<ref>` into `_actions/<owner>/<repo>/<ref>` with no `.git`; this is the runner's layout, not a documented contract. If it changes, the source build prints the plain version again, which is the current behaviour, not a failure.
- Git for Windows ships `unzip` (not `zip`), `sha256sum` and `curl`, so Git Bash on the Windows runner has the three tools `install.sh` needs; the review found `unzip` in its installer's file list. This was not run on a Windows runner.
