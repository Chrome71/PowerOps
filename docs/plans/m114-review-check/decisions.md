### Q2. Which plan states count as validly signed off?
1. Status `signed-off`, `implementing` or `done`, with `signed-off` and `signed-off-hash` set and the hash equal to the body hash: the conditions `plan status` already holds for those statuses. `draft`, `approved`, a malformed or unreadable header, a null sign-off and a changed body refuse.
2. The same, plus the plan's `review:` header and `review.md` (pending, missing, blocked).

Decided: 1. A plan is deployed while `implementing` and after `done`, so both must pass with their hash. The brief limits the change to "status and `signed-off-hash` against the body hash"; `plan sign-off` already refuses a pending review, and a `review:` edited after sign-off sits in the header, outside the hash, like every other header edit (packet E-8). `plan status` still reports review problems as violations.

### Q3. Does a superseded plan's folder still cover?
1. Yes, when its own plan is validly signed off.
2. No: a folder that a newer plan's `supersedes:` names covers nothing.

Decided: 1. The audit's `[R-A2]` case is a zip reviewed under plan `m`, deployed after plan `n` names `m` in `supersedes:`. A new version is "left as it is" by the planning skill (`docs/PLANNING-SKILLS.md`, Versions), so the old plan stays the signed record of what its zip was built from, and the zip's SHA-256 binds the reports to those bytes. Refusing it would block promoting an already reviewed zip (Test to Prod) as soon as a v2 draft exists, and a draft names `supersedes:` before anyone has approved it. The deployment yes stays the person's (decision 67). Recorded in the BUILD-PLAN decision as what stays unread.

### Q4. How is an open High read?
Decided: the format both kept roles prescribe (`## Findings`, `### High`, `#### <id>.` entries, `- Resolution: open`), as plan Data row 2 gives it: the first `- Resolution:` line of a High entry decides, and the entry is closed only when that value's first word is one of `fixed`, `resolved`, `answered`, `accepted`, `closed`, `withdrawn`, `kept`, `done`; anything else is open, including no `Resolution:` line, an empty value, `open`, `reopened`, `not done` and any unknown wording (fail-closed). The closing words are those of the 1,112 `- Resolution:` lines under `docs/plans/` on 2026-11-13 (first words: fixed 816, resolved 119, answered 86, accepted 44, open 21, closed 16, withdrawn 5, and one each of reopened, not, no, kept, `(a`). Fail-closed costs a refusal (or a sign-off warning) that a person clears by writing a closing word; fail-open would let a High with an odd wording cover a zip. The 122 role reports parse the same under either rule (plan Assumptions). `done` is on the list though no line under `docs/plans/` uses it: the kept roles and the plan skill use `done` for a finished check or step, so a person closing a finding may write it (round 3 R8). A missing `### High` section reads as no open High, so reports without a findings block, as written by the test fixtures and by hand, cover as before (the brief's compatibility contract). Fenced code is skipped so a quoted template is not read as a finding. History: round 1's Fable finding 5 added the empty value and `reopened`; round 2's `powerops-review-plan` R6 (`Not done`) moved the rule to a closed list.

### Q5. Where do the new reasons appear?
Decided: in the existing refusal sentence (`no review covers <zip>: docs/plans/<plan>: plan.md has no valid sign-off (<reason>); ...; nothing was imported.`), the plan's reason first (the phrase "has no valid sign-off" fits all six reasons; Fable round 1, finding 6), then the report faults, so `deploy plan`'s and a bare `deploy apply`'s `warning:` lines name them too. No new status, field or exit code (the brief's contracts).


### Q6. What does `plan sign-off` warn on?
1. A `state: blocked` or `state: failed` line in `review.md`, as the brief words it.
2. An open High finding in `review.md`, read with Q4's rule.

Decided: 2. `review.md` has no `state:` line: `skills/powerops-review-plan/SKILL.md` section 4 prescribes `plan-hash:`, `model:` and `fresh-context:` only, `docs/COMMANDS.md` says `review.md` has none, and none of the 88 `review.md` under `docs/plans/` has one; the packet's E-7 reproduction used a hand-made file. So option 1 would never fire on a real review. The role defines a blocking review by an open High, which is what the brief's "a current `blocked` review with an open High signs off with no warning" means. Raised by both plan reviews in round 1 (Fable finding 1, `powerops-review-plan` R2). The warning is in `plan sign-off` only; `plan status` output stays byte-identical. A warning, not a refusal (packet E-7): only a person accepts a High.
