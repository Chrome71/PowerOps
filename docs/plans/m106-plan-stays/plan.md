# M106: `deploy plan` says what an unmanaged import leaves

## Goal

For an unmanaged zip over an installed solution, `deploy plan` says nothing about the components the target holds that the zip no longer has (`DeployPlan.AddUpgrade` returns at `if (!solution.Managed)`). Practitioners report that an unmanaged import removes nothing, so a flow, environment variable or connection reference dropped from the source stays in the target unnoticed. This is milestone M106 of the upgrade plan drawn from the practitioner research (candidate 21, part); the plan's M106 section is the authority for the change.

Done when:

1. When a zip is unmanaged, its action is `upgrade` and the target's solution is installed unmanaged, the plan has one `stays` item, severity `info`, for each target component that a managed zip with the same contents would get a name-level `deletes` item for: each type-29 component of the target's solution whose id is not a workflow id of the zip (subject: the flow's name from the target read, else `29 <id>`, as `deletes` does), each target environment variable whose schema name the zip lacks, and each target connection reference whose logical name the zip lacks (both ignoring case). The message of every `stays` item is `An unmanaged import does not delete this from the target; the zip no longer has it.` (decisions Q4). An unmanaged zip over a managed install gets no `stays`: that import fails, and `managed-conflict` already blocks it (decisions Q1). Tables, canvas apps and other component types get no `stays` item and no count (Won't build).
2. `stays` never blocks: `blocked`, the exit code, the summary line and the plan hash are what they would be without it. A managed upgrade keeps exactly today's `deletes`, `unmanaged-layer`, `layers-not-read` and `components-not-checked` items and gets no `stays`; an `install` and a `skip` (lower or equal version) get none; a same-version skip keeps `same-version-differs` only.
3. `stays` is the last value of `PlanKind.Order` and of the schema's `kind` enum; its severity is `info` through `SeverityOf`'s `_` arm.
4. `JsonOutput.DeployPlanSchemaVersion` is `3`, so `deploy plan`'s JSON and the saved plan file say `3`, and `deploy apply` (CLI, MCP `deploy_apply`, the Action's apply job) refuses a plan file of version 2 with today's message (`... plan again with this version`), status `refused`, exit `1`: a plan saved before the upgrade is planned again. `deploy-plan.schema.json`: `schemaVersion` `const` 3, `stays` in the enum, and the `items` description names the kind.
5. Docs: `docs/COMMANDS.md`'s `deploy plan` section lists `stays` among the information kinds, says what it names and that it comes from the read the plan already makes, and its version sentence says 3; the `diff` section's aside ("`deploy plan` and `drift` are at 2") says `deploy plan` is at 3. `docs/schemas/README.md`: the "Each output's version" line, and a paragraph "`deploy plan` from 2 to 3" in the form of the "from 1 to 2" one. A new decision in `docs/BUILD-PLAN.md`, numbered at merge (66 if nothing lands first), says what `stays` is, that it never blocks, that the version goes to 3 under decision 48's rule, and that `deploy apply` refuses a plan file saved by the older build, so a plan saved before the upgrade is planned again.
6. The tests of Data row 4 are written first and seen to fail on their assertions, then pass. The `deploy-plan*` goldens are regenerated by the "Update goldens" recipe; their diff holds only the `schemaVersion` line of each existing `deploy-plan*` golden and the new `deploy-plan-stays.json`.
7. `dotnet build` (0 warnings), `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status docs/plans/m106-plan-stays` and the leak scan are clean; `tests/eval/`, `skills/powerops-verify`, `skills/powerops-review-security` and their plugin copies are byte-for-byte unchanged and `RoleEvalTests` passes.

### Won't build

- `stays` for tables, canvas apps or other component types, or a count of them (the target names them by id, the zip by schema name; `deletes` checks them by count only, and a count for an unmanaged import would add a guess to an information item).
- A change to `deploy apply`'s logic, the plan hash, the plan file reader, the report writers, the MCP tools' descriptions, the Action scripts, any skill, specialist or plugin file, or `docs/RECOVERY.md`.
- A new tenant read: `stays` uses the snapshot the plan already reads.
- A way to remove what stays (that is a person's step in the target, or a managed upgrade).

## Users

- An agent or person that reads `deploy plan`'s report (JSON, text or the Action's Markdown comment) before an import and needs to know what will still be in the target afterwards.
- A consumer that validates `deploy plan`'s JSON against the published schema, or keeps saved plan files for `deploy apply`.

## Assumptions

- An unmanaged import over an installed unmanaged solution deletes nothing from the environment: Learn's *Upgrade or update a solution* (an update's missing components are not deleted) and *Solution concepts* (only an upgrade deletes), read 2026-11-12; `decisions.md` has the sources. The message claims only this.
- unproven: whether the target solution's component list still holds such a component after the import (no Learn page says; probe: import v1 unmanaged, then v2 without one flow, read the solution's components). No build step and no message depends on it: `stays` says the component is left in the target, not in the solution.
- The target read already returns, for an installed unmanaged solution, its components, flows, variables and references (`Snapshot`), as it does for a managed one: the same `DriftLiveReader.ReadTarget` path, checked in the code at `e185b56`.
- The leak scan is `reports/leakscan.sh`, an untracked local tool of the main checkout; it runs from there against the committed branch (`bash reports/leakscan.sh origin/main <branch>`).
- The installed `powerops` may be stale; `plan status` and `plan sign-off` run with this worktree's build (`dotnet run --project src/PowerOps.Cli --`).
