## Round 1 (planning)

### Q1. How should the `environment:` line alternative treat case?
1. Widen only its last word to `[Ee]nvironment`, keeping the key `environment:` case-sensitive (recommended)
2. Wrap the whole alternative in `(?i:...)`
3. Leave it unchanged, as the fix plan's M90 section says

Decided: 1, by the building session. The fix plan calls the line alternative "unchanged and still case-insensitive on that line", but on `b065f23` it is case-sensitive: it matches only a lower-case `environment` after `'s`, and `environment: jane doe's Environment` was caught only by the prose alternative. Once the prose alternative goes quiet after a lower-case word, option 3 would let that header line through. Option 2 (the first draft) also made the key case-insensitive, so a prose line starting `Environment: the customer's environment` would fire where it is quiet today (Fable's round-1 finding 3); the header key is always lower case. Data row 2 pins both cases. <!-- plan-status: allow -->

### Q2. Which form does the prose alternative take?
1. An exclusion: today's pattern behind `(?<!\b\p{Ll}[\p{L}\p{M}.-]*)`, quiet only when the word before `'s` starts with a lower-case letter (recommended)
2. The fix plan's positive form, `\b\p{Lu}[\p{L}\p{M}.-]*` before `'s`

Decided: 1, by the building session, on Fable's round-1 finding 1. Run in .NET 10, the positive form goes quiet on names `b065f23` catches: one ending in a bracket (`Jane Doe (Contoso)'s Environment`), one ending in a digit (`Test User 1's`, `Doe2's`), and names in scripts with no case (Chinese, Arabic). The check is the net that keeps people's names out of Git, so it must not lose them; the exclusion removes only the false positive the trial hit, a lower-case possessive before a capitalised UI word. Both forms test the word right before `'s`, not the whole name, so the code comment and `docs/COMMANDS.md` say exactly that (Fable's finding 2; the fresh review's R1). <!-- plan-status: allow -->
