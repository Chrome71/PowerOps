# M99: Flow rules for a catch that tells no one, static results, the 90-day turn-off and long approvals

## Goal

Practitioners rank a flow that fails silently as the top flow defect, and no `analyze` rule reads `runAfter`, Terminate status, static results, recurrence or action timeouts: `FlowDefinition` keeps none of them. This milestone gives `FlowDefinition` a per-action reader, `Actions`, and gives `FlowTrigger` its type and a Recurrence's frequency and interval. Four Warning rules use them: PO037 (a flow catches a failure, tells no one and ends as succeeded), PO038 (an action has its static result turned on), PO039 (a flow's schedule is about every 90 days or rarer) and PO040 (an approval's explicit timeout is 30 days or more). M100 (secret rules), M107 (`inventory`) and M111 build on `Actions`, so its shape is part of the deliverable. This is milestone M99 of the upgrade plan drawn from the practitioner research (its section "M99. Flow rules").

- A list of nested action names, a parent link, header or input values on `FlowAction`: an action's descendants are the next `Descendants` entries of `Actions` (Data row 1), and with `Depth` a reader finds an action's parent (siblings in different blocks of one parent, such as a Condition's `actions` and `else`, are not told apart); M100 and M111 add the fields they need when they need them.
- A replacement of `ActionCount`, `Depth`, `NestedLoops` or `DataverseActions` by `Actions`. They stay as they are; the new list is built in the same walk.
- A change to the simulator's own static-result check (`FlowSimulator.StaticResultOn`).

## Assumptions

Each Microsoft claim was checked on 2026-11-12 by `powerops-researcher` (Opus, Learn only; Log has the details):

- Run status. A Terminate action with `runStatus` `Failed` ends the run Failed (*Schema reference guide for trigger and action types in Azure Logic Apps*; *Employ robust error handling* for Power Automate). A failure that a later action handles leaves the run Succeeded, and an unhandled one makes it Failed (*Check workflow status, view run history, and set up alerts in Azure Logic Apps*). Learn states this rule for Logic Apps only; applying it to cloud flows is an inference from the shared engine, and PO037's page says so. A Response action shapes the HTTP reply, not the run status (by implication only); PO037 still treats a Response as telling the caller, as the upgrade plan says. Terminate also takes `Cancelled`, which does not end as succeeded either, so PO037 is quiet on it (a narrowing of the upgrade plan's condition; it changes no count).
- Static results. An action with its static result on is treated as successful without running (*Test cloud flows*); the definition holds `runtimeConfiguration.staticResult` with `name` and `staticResultOptions`, pointing at `staticResults` (*Schema reference guide for the Workflow Definition Language*). Learn shows only the value `Enabled`, never `Disabled`; the rule fires on `Enabled` only, as the simulator does. That an export keeps it is not on Learn: observed in the m58 capture's second export (`docs/plans/m58-flow-conformance/capture.md`).
- The 90-day turn-off. "A cloud flow that isn't triggered within a 90 day period might be turned off"; owners with premium or capacity licences (Process, per flow) are exempt; owners are told 30 days before (*Limits of automated, scheduled, and instant flows*). The condition is no trigger at all, not "no successful trigger". A schedule rarer than 90 days is never triggered within some 90-day window, so the rule's condition follows from the page. The page is the manual ecosystem source `docs-flow-limits` (ECO-0002, done), `lastChecked` 2026-11-10, inside its 30 days.
- The run limit. A run lasts at most 30 days, pending approvals included, after which pending steps time out (the limits page). The approvals *Known issues* page says an approval flow can wait 28 days. The rule keeps the upgrade plan's 30 days, the limits page's figure; PO040's page names both and advises staying under 28. The two-flow pattern (*Create an approval (v2)*, then a second flow on the response) is on *Create and test an approval workflow with Power Automate*.
- Approval operations. `StartAndWaitForAnApproval`, `WaitForAnApproval`, `StartAndWaitForATextSuggestionApproval` and the deprecated `approvalSubscribe` and `approvalSubscribeV2` wait; `CreateAnApproval` does not (*Standard approvals*, connector reference). The api id `shared_approvals` is not on that page; it is observed in the `alm-makers` exports. `limit.timeout` as an ISO 8601 duration is documented for the Logic Apps types (`ApiConnectionWebhook` among them), not for `OpenApiConnectionWebhook`, the type exported cloud flows use; Power Automate's error reference says to set the action's Timeout setting as an ISO 8601 duration. So the key on an exported approval is an inference: no public fixture holds a timed approval. unproven: an exported approval with a Timeout setting holds it as `limit.timeout`; probed by step 5, which needs a tenant and so runs after this milestone. Accepted for the build by the building session (decisions, Log): PO040 is quiet when the key is absent, so a wrong key costs a missed finding, never a false one, and the rule page says the key rests on Logic Apps' documentation. A GitHub code search on 2026-11-12 found no public export with an approval and a timeout.
- `XmlConvert.ToTimeSpan`, run by the fresh plan review on 2026-11-12: `P30D`, `PT720H` and `PT2592000S` read as 30 days, `P1M` as 30 days, `P2M` 60, `P1Y` 365, `-P60D` minus 60; `P1W`, `P4W`, `p30d` and `P30DT` throw `FormatException`, `P99999999D` throws `OverflowException`. Row 8 pins each.
- `docs/ecosystem/`: no `compatibility.md` row covers flow definitions; ECO-0002 is done and its source is `docs-flow-limits`; the open entries do not touch flow JSON.
