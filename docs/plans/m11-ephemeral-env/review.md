#### R1. `deploy plan` blocks every solution that has a connection reference, so the recipe cannot deploy what the plan says it can
- Area: 2. Connection references and environment variables; 9. Testability
- Finding: Data says a solution "with references the solution's flows can do without while they are off" can use the recipe, and Assumptions say such a solution deploys "with no settings file and nothing to bind". M9's code says otherwise. `DeployPlan.AddSettings` runs `DeploymentSettings.Validate` for every install and upgrade, with an empty `{}` when there is no settings file; that adds a `missing` problem for each connection reference not in the file and an `emptyConnectionId` problem for one without a non-blank `ConnectionId`, and the `settings` kind is a Block (`PlanKind.SeverityOf`). So the plan for any solution with a connection reference is blocked (exit 1, and the Action fails the job), and M10's `deploy apply` refuses a blocked plan. A new environment has no connection, so no settings file can hold a real `ConnectionId`. Most cloud-flow solutions have connection references (every connector action in a solution flow uses one), so the recipe as written works only for solutions without any (apps, tables, flows with built-in actions only), and the same holds for an environment variable with no default or current value that the settings file does not set. The sentence is wrong about what the tools do, and the README's fake `ContosoApp` must be a solution without references (M9's example has a SharePoint reference).
- Suggested fix: In Goal, Users, Data, Assumptions and the docs say: the recipe works only for solutions with no connection reference; a required environment variable needs a `Value` in a settings file built from repository variables; a reference blocks the plan. Delete "while they are off". Make the example solution reference-free and show the blocked message the reader will see. If binding connections in a new environment is wanted, it is a separate `powerops` task with a test (for example, a way to plan an unbound reference as a warning; what pac then does on import is not documented, so it needs a live check), as the BUILD-PLAN row already says; do not promise it in the docs.
- Resolution: fixed (Goal, Users, Data and Assumptions say the recipe works only for solutions without connection references; the wrong sentence is gone; a required variable needs a value from repository variables; the README shows the blocked message; the example solution is reference-free)

#### R2. The sweep and the lookup by name can delete an environment the recipe did not create
- Area: 5. Dev to Test to Prod route (what is deleted, and by whom); 9. Testability
- Finding: (a) The sweep keeps names "whose display name starts with the prefix", reads the PR number from the name and asks `gh pr view <n>` in the repository it runs in. The default prefix is the same for every repository that copies the example, and the name holds a PR number but no repository. In a tenant used by two repositories, repository A's sweep reads repository B's `<prefix>-pr7-...` and deletes it as soon as A's PR 7 is closed (or does not exist), while B's PR 7 is open and its run is in progress. Any environment an admin names with the prefix also matches, and the plan has no rule for a name that does not parse. (b) "Not open" is the delete condition: if `gh pr view` fails (no repository context, a token without `pull-requests: read`, a rate limit, PR not found), the state is empty, which reads as not open; the plan does not say a failure means keep. (c) Step 3 and the by-name lookup in step 8 use `pac admin list --name`, which the plan itself says is a contains match, but only the sweep is said to filter the JSON. The name of attempt 1 is a substring of the name of attempt 10, and any name that contains it matches. Nothing says the match is exact on the display name, what zero or two matches do, or that the id is checked before `pac admin delete` (an empty or `null` id from a misspelled field is not caught). (d) A display name is not unique and any admin can rename an environment; it is the only identity the delete uses. (e) The offline test in Done when asserts "the sweep deletes only names that start with the prefix", which is exactly the weak rule in (a).
- Suggested fix: Put the repository's numeric id (`github.repository_id`) into the name and select with an anchored full-match pattern (`^<prefix>-<repo id>-pr[0-9]+-[0-9]+-[0-9]+$`, the prefix itself checked against a short safe pattern), exact equality on the display name in the JSON, and exactly one match or no deletion. The sweep deletes only when `gh run view <run id>` finds the run in this repository and it is completed, and `gh pr view` returns `CLOSED` or `MERGED`; any error, or a name that does not parse, keeps the environment and prints a notice with the name. Immediately before `pac admin delete`, re-read the list, require one environment with that id and exactly the expected name, and require the id to look like a GUID. Make `workflow_dispatch` a dry run by default (an input that lists what would be deleted), and let the schedule delete only when a repository variable says so, so a reader sees the matches before the first deletion. Put the selection in a script (R9).
- Resolution: fixed (the repository id in the name; an anchored full match; exact display-name lookups, exactly one or nothing; the id re-read and checked before each delete; the sweep deletes only leftovers of runs that `gh` reports completed, a `gh` failure keeps and turns the run red; a dry run by default; the selection in scripts with tests)

#### R3. The credential the recipe teaches gives every branch pusher Power Platform admin rights in the tenant
- Area: 8. Security roles; 5. Dev to Test to Prod route
- Finding: Environments and route registers one Entra app, with a federated credential for the repository's `pull_request` runs, as a Power Platform management application, and says the app "then acts like a Power Platform administrator" (Learn gives no finer role). A `pull_request` run uses the workflow file from the PR (not checked offline against GitHub's text, but it is the premise of M10 review R1), so anyone who can push a branch to the repository can add steps that sign in as that app and run `pac admin delete` or `create` against any environment in the tenant, production included, with no reviewer. That is wider than M10's R1 (Test and Dev only), and the one control the plan names is an admin question ("may the app be registered"). The parenthesis "or a GitHub environment" is not explained or recommended. For a docs-only plan, what the docs recommend is the whole control, and the example's own `pull_request` trigger reads as the safe default.
- Suggested fix: Open the README section with this risk, before the YAML. Recommend one of: a tenant, or a region, with no production environments; or a federated credential bound to a GitHub environment with required reviewers and "Prevent self-review" (each PR run then waits for an approval); and in either case a dedicated app used for nothing else, CODEOWNERS or a ruleset on `.github/workflows/`, and a private repository. Say that a fork PR gets no token (so the example skips forks) and that secrets in the PR job must be configuration, never credentials. Name the federated credential's subject forms (name-based and immutable, read from the repository as M10's README does) and add to `Questions for your admin`: may such an app exist in this tenant, and in which tenant should it run.
- Resolution: fixed (the README opens with the risk; recommended: a tenant or region without production, the approval gate on the `ephemeral` environment with Prevent self-review and the credential bound to it, a dedicated app, a private repository, CODEOWNERS or a ruleset, configuration-only secrets; the subject forms; the admin question on the tenant)

### Medium

#### R4. Cleanup does not cover a cancel during creation, the sweep waits for the PR to close, and the delete step trusts a sign-in made hours earlier
- Area: 5. route; 9. Testability
- Finding: Step 2 can run for up to 60 minutes. A cancel (a new push under the concurrency rule, or a person) ends the `pac` process while the service goes on provisioning. The `always()` step then has at most the 5 minutes the plan's own source gives to find and delete an environment that is still provisioning; nothing the plan cites says it can be listed or deleted in that state (not checked offline). The BUILD-PLAN done-when "A cancelled run still deletes its environment" is therefore likely false for that case, and the plan does not say so. The sweep deletes only when the PR is not open, so such a leftover keeps its capacity until the PR closes, and every push adds another (the name carries the run id, so nothing is replaced). Second, the delete step relies on step 1's `pac` profile and token: a run that created for 60 minutes and imported for more may hold an expired token, and the GitHub token behind the federated sign-in is short-lived (not checked offline; M9's live check made its calls seconds after signing in). `azure/login` also runs in step 1 but `az` is used after the create. Third, no `timeout-minutes` is set, so a hang runs to the 360-minute default, and a timed-out job is cancelled with the same 5-minute limit.
- Suggested fix: Key the sweep on the run as well as the PR: delete a matching environment when its run (the id in the name) is completed or cancelled, whatever the PR state, as well as when the PR is closed or merged. Add a first step to each PR run that removes the same PR's environments from older completed runs, which bounds leftovers per PR. The delete step signs in itself (its own `pac auth create --githubFederated`, no environment) and is short; move `azure/login` to just before step 7. Set `timeout-minutes` on the job and on the create step so at least 10 minutes remain. In the docs and the BUILD-PLAN row say that a cancel during provisioning is cleaned up by the sweep, not by the run, and that no cancelled run was tried.
- Resolution: fixed (the sweep keys on the creating run, not the PR; each PR run first removes its own PR's leftovers; the delete step signs in again; `timeout-minutes` on the job and the create step; the cancel-during-create case and its cleanup by the sweep are in the plan and the docs)

#### R5. The sweep as described cannot sign in or call `gh`, and it can stop silently
- Area: 5. route; 9. Testability
- Finding: (a) The one federated credential the plan names is for the repository's `pull_request` runs. A `schedule` or `workflow_dispatch` run presents the default branch's ref subject instead (GitHub's OIDC subject rules; not checked offline), so the sweep cannot sign in without a second credential, and the plan does not list it. A `workflow_dispatch` started from another branch presents yet another subject. (b) `gh pr view <n>` and `gh run view` in a job with no checkout have no repository: the step needs `GH_REPO` or `--repo`, and `GH_TOKEN` in `env:`. The sweep's `permissions` are not named: it needs `id-token: write`, `pull-requests: read`, `actions: read` and `contents: read`, and nothing more. (c) The plan says GitHub disables schedules in a public repository after 60 days without activity and that the docs say so; the effect is that leftovers (and their capacity) build up with nothing red anywhere. (d) With `pac admin list --json` the sweep reads every environment of the tenant, so it must say what it does with the ones that are not the recipe's (nothing, and print nothing).
- Suggested fix: List in the README the two credentials (the PR trigger's and the default branch's) and the sweep's permissions; give the sweep `GH_REPO` and `GH_TOKEN`; make it fail (red, so GitHub notifies) when it finds a matching environment it cannot classify or one older than a set number of days; and tell the reader to look at `pac admin list` for the prefix by hand now and then, because the schedule can be switched off.
- Resolution: fixed (the default-branch credential, `GH_REPO`, `GH_TOKEN` and the sweep's permissions named; the sweep turns red on what it cannot classify; the 60-day schedule rule and a manual check in the docs; nothing printed from the tenant's list)

#### R6. Identifiers can reach a public log before the masks, and the sweep handles the tenant's whole list
- Area: 2. hard-coded and tenant values; 8. Security
- Finding: Only step 1's `pac` output is kept out of the log, and the URL's masks are registered in step 6, after steps 2 to 5 have run. Learn documents no success output for `create`, and `pac` commands print environment names, ids and URLs (the reason M9 redirects `pac auth create` and masks the URL's forms). Steps 2 to 5 therefore run with their output in the log. The id and URL found in step 3 are not masked: step outputs are not masked by GitHub, and the id or URL used in a later step's `env:` or `with:` (the Action's `target`) is printed in that step's header (not checked offline, but it is why M9 masks). The masks the plan mentions cover the URL's forms, not the environment id, and the delete step gets its id the same way in the failed and cancelled cases. The sweep's JSON holds the names, ids and URLs of every environment in the tenant, including other teams'; a step that prints it, or runs under `set -x`, publishes them.
- Suggested fix: Every `pac admin` call writes stdout and stderr to a file in `$RUNNER_TEMP` and prints only `error:` text, with the debug exception M9 uses. Right after reading the id and URL from the JSON, validate their shape (a GUID; an `https` host under the documented Dataverse hosts) and register `::add-mask::` for the id in both letter cases, the URL forms, the host and its first label, and only then write them to `$GITHUB_OUTPUT`. The sweep prints counts and the recipe's own matching names, never the list, and has no `set -x`. The offline test (R9) fails on any `echo` or `cat` of a list file, and the leak scan in Step 2 covers both YAML files.
- Resolution: fixed (every `pac` and `gh` output to a file, only `error:` lines printed; the id and URL validated and masked in every form before they reach an output; the sweep prints counts and its own names only; a test that no other environment's data is printed)

Record in Assumptions and in the README's not-verified list the field names (with the pac version read), the clean `--json` stdout, and the sign-in without an environment.
- Resolution: fixed (defaults in the YAML and a README table; `jq -e` on exact fields; a bounded retry; the delete rule written out, a failed lookup deletes nothing and fails; the field names recorded as observed with pac 2.13.1 on 2026-10-23, and in the not-verified list)
