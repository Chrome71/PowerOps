# M84: Ecosystem watch

## Goal

Give the agents that develop PowerOps a light, lasting way to notice, verify, triage and record changes in Microsoft's Power Platform ecosystem, then run one real review with it and fix only what is clearly justified and small. The owner asked for this on 2026-11-10 in a private brief (`reports/ecosystem-maintenance-brief-2026-11-10.md`, git-excluded). Today the pieces exist but are not joined: `powerops-researcher` and `/verify-research` verify claims, the rule pages carry dated `Sources:` lines, FOUNDATION section 8 lists open questions, `pin-drift.yml` watches PowerOps' own pins, and Dependabot watches the NuGet packages, the Playwright example and the Action SHAs. Nothing notices when `pac`, Microsoft's agent skills, an MCP server or a Learn page that PowerOps relies on changes, and nothing records what was decided about it, so each session starts the research again.

Done when:

1. `docs/ecosystem/` holds four files: `README.md` (the procedure), `changes.md` (the change register), `compatibility.md` (the tested external versions and limits) and `sources.json` (the source inventory and the collector's last-seen values in one file). No `sources.md`.
2. `.github/scripts/ecosystem-watch.sh` validates `sources.json` and refuses a bad one, asks each automated source's public endpoint once, and prints a Markdown report in four parts: new, not checked (with the reason; never counted as "no change"), unchanged, and checked by hand (with the ones due). It writes nothing unless `--update` is given; `--update` records the values it read for every source it could read and changes nothing else. Two runs with no upstream change print the same report apart from the date line.
3. `.github/workflows/ecosystem-watch.yml` runs it every Monday and on `workflow_dispatch`, puts the report in the job summary, and keeps at most one open issue titled `Ecosystem watch`: with something new, not checked or due by hand it edits the open one or opens one; with nothing new, nothing failed and nothing due it edits the open one and closes it, and opens none. It holds no AI or other credential beyond `github.token`, writes no file to the repository and calls no tenant.
4. `AGENTS.md` has a section of at most ten lines saying when to run the procedure and pointing to `docs/ecosystem/README.md`.
5. Tests: `EcosystemWatchTests` runs the script against a `curl` stub (new, unchanged, moved back, failed, empty, malformed, rerun, `--update`, token hygiene, untrusted text, refused inventories, the real inventory); `WorkflowTests` holds the new workflow to its triggers, permissions, pins and token scope, and runs its issue step against a `gh` stub with the runner's shell flags; `EcosystemDocsTests` holds `changes.md` and `compatibility.md` to their format and the hand-moved pins to the repo's files.
6. One real review has run with the finished process (steps 5a to 5c): the automated sources' values are recorded with `--update`, every manual source was read, each finding in the areas of the brief's section 8 is verified against an authoritative source, compared with the repository, classified and entered in `changes.md`, and `compatibility.md` is current.
7. The "implement now" findings that qualify (step 6's rule) are built, each with its acceptance criterion and test; every other finding is recorded as plan for later, monitor or no action.
8. `dotnet build` (0 warnings), `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status docs/plans/m84-ecosystem-watch` (showing `done`) and the leak scan are clean; the collector run twice after the review gives the same report apart from line 1, every source unchanged or named as moved upstream since 5c's `--update`; and the Log holds step 7's five records.

### Won't build

- A `powerops` command, MCP tool or anything in `src/`. The owner's rule: the customer-facing CLI gets no command for this. The collector is a development script beside `pin-drift.sh`.
- Anything in `skills/`, `plugins/` or `.claude/agents/`, in any step. `skills/` and `plugins/` are customer-facing and copied into both plugins, and the specialists are generated into the Claude plugin; the procedure is for the people and agents who develop PowerOps. A finding that needs such a change is recorded as `plan for later`.
- A new agent role, skill or saved workflow. `powerops-researcher` verifies a claim with sources and `/verify-research` adds two independent refuters; the procedure routes to them. A seventh specialist would duplicate both.
- AI triage in CI, model credentials, or an optional agent job. The collector is deterministic; judging relevance is a session's job, by the procedure.
- Scraping. Learn changes come from the commit history of the public MicrosoftDocs repositories; sources without a structured feed (Copilot Studio and Power BI docs, the release plans, the Fabric roadmap) are read by hand on a cadence the inventory states.
- Auto-PRs, auto-merge, a write to the repository from CI, or any automatic pin bump. A tool pin moves only with a test of the new version, as decision 16(d) and decision 32 already keep it.
- A duplicate of Dependabot: the build's NuGet packages, the Playwright example's npm packages and the Action SHAs stay its job, and `compatibility.md` points to it instead of repeating versions.
- A watch on the .NET SDK. `global.json` rolls forward to the latest feature band, so a patch release drives no decision; `compatibility.md` keeps the .NET row.
- Automated watches that would report "new" nearly every week without touching what PowerOps uses (decision Q12): whole-repository heads where PowerOps cites folders, docs folders where it cites pages, the `pac` reference folder (a `pac` release is the signal), the Microsoft 365 roadmap feed (58 new Power Platform items in the four weeks to 2026-11-10), and the Claude Code and Codex registries (several releases a week). The roadmap and the two agent clients are manual sources instead, read every 30 days.
- A mapping of every Learn page PowerOps cites to its docs-repository file. The first version watches the pages listed in Data; the first review records whether finer watching is worth a milestone.
- A second validator of `sources.json`. The script is its one home, because `target` goes into URLs; the tests run the real file through the script.
- A `shellcheck` job in CI. CI runs none today; this milestone adds no job and installs nothing.
- Any change to the kept roles (`powerops-verify`, `powerops-review-security`), their plugin copies, `tests/eval`, the schemas, the version files or the changelog.

## Users

- The main development agent: before it plans or changes anything that calls or describes a Microsoft service, CLI, API, skill or MCP server (mode B), and when an integration breaks (mode C).
- The session that triages the weekly report (mode A), and any later session that must resume without repeating the research or re-proposing a rejected change.
- The owner, who sees the weekly issue and reads `changes.md` for what was decided and why.
