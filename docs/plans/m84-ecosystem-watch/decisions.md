# Decisions: m84-ecosystem-watch

The owner's brief of 2026-11-10 (private, `reports/ecosystem-maintenance-brief-2026-11-10.md`) and the orchestrating session's design direction are the base. Each decision below was made by the planner within that brief; none needed the owner. The orchestrating session's direction is called "the direction".

## Round 1 (planning)

### Q1. Where does the procedure live?
1. `docs/ecosystem/README.md`, for the people and agents who develop PowerOps, with a short pointer in `AGENTS.md` (recommended)
2. A development skill under `.claude/skills/`
3. A skill under `skills/`

Decided: 1. `skills/` is customer-facing and copied into both plugins, so 3 would ship a maintainer's procedure to every user. A skill (2) is loaded by description and only by Claude Code; a page that `AGENTS.md` points to reaches Codex and any other agent too, and costs no context until a trigger in `AGENTS.md` fires. This follows the direction.

### Q2. One inventory file or two?
1. `sources.json` holds the inventory and the last-seen values, manual sources included with `kind: manual` and a cadence; no `sources.md` (recommended)
2. `sources.md` for people and `state.json` for the collector

Decided: 1. Two files would hold the same list twice and drift. People read the inventory through the collector's report, which lists every source, its value and the manual ones due; the README explains the fields. The direction left `sources.md` open; this drops it.

### Q3. How does the collector see Learn changes?
1. The commit history of the public MicrosoftDocs repositories, for a short list of folders and pages PowerOps depends on (recommended)
2. Map every Learn URL PowerOps cites to its repository file and check each one against its `verified:` date
3. Fetch the Learn pages and compare their text

Decided: 1. Option 3 is scraping, which the brief rules out. Option 2 is the finer signal, but about a hundred cited URLs, redirects and index pages make it a milestone of its own; the first review records whether it is worth one. Copilot Studio and Power BI have no public docs repository (searched 2026-11-10), so their pages are manual sources with a 30-day cadence.

### Q4. What does the workflow write?
1. The job summary always, and at most one open tracking issue, `Ecosystem watch`: edited when something is new, not checked or due by hand, opened then if none is open, and edited then closed by a run that finds none of the three (recommended)
2. The job summary only
3. A pull request that updates the inventory

Decided: 1. A summary alone (2) is seen only by someone who opens the run, so a weekly report would go unread. A pull request (3) would write to the repository from CI and record values nobody triaged. One issue found by its exact title and author never piles up, and an open issue means "something to triage", which is the signal `AGENTS.md` gives the main agent. A manual source that falls due counts as something, like a new or failed one, because reading it is triage too; otherwise the 30- and 90-day reads would wait for some other source to move (review R8). The session whose review reaches `main` closes the issue; the workflow closes it itself on a clean run, which the expected rate makes rare (Q12). Every one of the four cases is stated and tested against a `gh` stub run with the runner's shell flags (Fable's round-1 finding 1, review R7). It needs `issues: write` on the job only. If the owner prefers no issue, deleting the one step leaves a working summary-only watch.

### Q5. Which token does the collector use in CI?
1. `github.token` with the job's permissions, given to the collect step through a curl config on stdin, and sent only to `api.github.com` (recommended)
2. No token

Decided: 1. Unauthenticated GitHub API calls are limited per address, and shared runners often run out. A second job with read-only permissions would keep `issues: write` away from the step that parses responses, but it needs a way to pass the report between jobs (an artifact action or a multi-line output), which is more moving parts than the risk warrants: the collect step only feeds responses to `jq` and prints values that pass a pattern.

### Q6. What does the watch cover besides Microsoft?
1. Claude Code, Codex and the MCP specification, because the plugins, the hooks and `powerops mcp` depend on them; not the build's NuGet packages or the Action SHAs, which Dependabot already watches (recommended)
2. Microsoft sources only

Decided: 1. The brief asks to discover sources from PowerOps' own dependencies; the agent clients and the protocol are among them, and Dependabot doesn't cover them (`skills-smoke.yml` pins them by hand). Repeating Dependabot's packages would report every update twice. After review R1, Claude Code and Codex are manual sources read every 30 days at their changelog and releases page, not registry watches (Q12); the MCP specification stays automated.

### Q7. How is a finding verified?
1. One `powerops-researcher` answer with sources for P2 and P3; `/verify-research` (two independent refuters) for P0 and P1 (recommended)
2. `/verify-research` for every finding

Decided: 1. A refutation pass costs about three agents a question; spending it on a minor improvement is waste, and the P0 and P1 findings are the ones that would change code under time pressure.

### Q8. How old may evidence be before mode B re-verifies it?
1. 90 days, or any open entry in `changes.md` that touches it (recommended)
2. 30 days

Decided: 1. The weekly watch already flags a change in the sources PowerOps depends on, so the age rule only catches what the watch can't see; 30 days would send most plans into research.

### Q9. How far does the first review's fix step go?
1. Only findings that pass a stated rule, at most five, each at most 40 lines outside `docs/ecosystem/`, none touching a public command, schema, kept role, `tests/eval`, version file or tenant (recommended)
2. Whatever the review finds

Decided: 1. The review's findings can't be known before it runs, so the step needs a rule instead of a list. Anything larger is recorded as `plan for later` and gets its own milestone, as the brief asks.

### Q10. Does the collector watch the .NET SDK?
1. No; `compatibility.md` keeps the .NET row (recommended)
2. Yes, through the release-metadata index

Decided: 1 (Fable's round-1 finding 4). `global.json` rolls forward to the latest feature band, so a patch release drives no decision, and a weekly "new SDK" line would be noise.

### Q11. What if `/verify-research` can't run in step 5b?
1. Two independent `powerops-researcher` refuters per P0 or P1 claim, spawned by the orchestrator, at most three claims; beyond that the entry is `unverified` and reported to the owner (recommended)
2. Wait for the person's approval of `/verify-research`

Decided: 1 (Fable's round-1 finding 5d). `/verify-research` asks for approval before it runs, and the review must not stall on it; the fallback keeps its idea, independent refutation, at a capped cost.

### Q12. How noisy may the automated sources be?
1. Each automated source watches only a file, page or release whose change would alter a PowerOps rule, doc claim or pin; a whole repository only where PowerOps cites it as a whole; the rest are manual or left to mode B (recommended)
2. Keep the broad watches and accept a weekly review of each

Decided: 1 (review R1, and the orchestrator's direction to cut the noise at the source). Measured on 2026-11-10 over the four weeks from 2026-10-13: the power-platform-skills head saw 65 commits and its plugin list (`.claude-plugin/marketplace.json`) 1; the power-cat-skills head 30, its two cited plugins 0; skills-for-fabric 3 releases, its cited plugin 2 commits; the `alm` folder 4 commits, the three pages PowerOps leans on 0 to 1; the `pac` reference folder 2 (a `pac` release is the better signal, and its triage reads the reference); the code-apps folder 2, the `pa` CLI page 0; the Microsoft 365 roadmap 58 new Power Platform items; Claude Code 10 npm releases in two weeks and Codex 5 in four. So power-platform-skills watches its plugin list, power-cat-skills becomes two folder sources, skills-for-fabric watches its cited plugin, the `alm` and code-apps folders become pages, the `pac` reference folder goes, and the roadmap, Claude Code, Codex and the programmability changelog become manual sources (the `m365-roadmap` kind, with its title and status handling, leaves the collector). skills-for-copilot-studio, copilot-studio-plugin and Dataverse-skills stay whole because PowerOps cites them whole. What remains saw 17 changes in those four weeks, about four a week, five on the deprecations page, which is kept because a deprecation is exactly what the watch is for. The procedure's cheap path closes a change that touches nothing PowerOps uses with one review-log line, and step 7 logs the first measured rate.
