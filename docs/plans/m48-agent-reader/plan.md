# M48: Agent reader and rules

## Goal

Read Copilot Studio agents from a solution (`bots/`, `botcomponents/`) in `analyze`, and add five rules for agents on the standard harness. This is M48 of Phase 7 ([plan](../phase7-power-platform/plan.md), stage two, build-order item 83, release label v0.31.0), with its "Stops if" rule, D7 (the fixture), F6 and D10 (decision 49) for inputs an export doesn't hold. Stage one (M40 to M47) is built, so stage two may start.

F6 was read on 2026-11-03 with `pac` 2.14.1, the latest on NuGet, in a scratch folder with no sign-in and no auth profile visible to it. `pac copilot pack` refuses the MIT workspace fixture D7 names ("not a valid agent workspace": its `connectionreferences.mcs.yml`, `actions/`, `agents/`, `knowledge/` and seven other entries are unsupported) and writes nothing. So F6's own test, whether that fixture packs into the sample's layout, has no answer, and D7's fixture can't be made. What was compared instead: a workspace that `pac copilot init` scaffolds locally (topics and a Custom GPT component, no tool) packs into `bots/<schema>/{bot.xml,configuration.json}` and `botcomponents/<schema>/{botcomponent.xml,data}`, the paths the M48 section and the public order-management sample have, and `pac solution unpack` keeps those paths and `Assets/botcomponent_connectionreferenceset.xml` unchanged in a folder. The tool shapes (`TaskDialog`, MCP, Maker mode) rest on the public exports in Assumptions alone. The stop rule needs a mismatch shown and no fixture; no mismatch was shown, so it doesn't apply. The person chose option 1 of the Phase 7 decisions' Q7 on 2026-11-02, on the condition that `pack` accepts the fixture. It doesn't, so this plan takes that question's option 3 under the delegation of 2026-10-22: no committed fixture, with the layout built by hand in tests (decisions Q1). The PR body names this departure so the person can overrule it at the merge.

`pac copilot init --environment` writes to a tenant: Learn's `pac copilot` reference says the bootstrap mode "imports that solution into the environment" and "creates server-side objects", and that the presence of `--environment` decides the mode. The flag's own description, on Learn and in `pac copilot init help`, says the active auth profile's organization is used when the flag isn't given, so `init` without it may write too when a profile is active; F6 ran it only with no profile visible. M49 adds the gate route, and should route `init` whenever an auth profile is active, with or without the flag, unless a live observation shows otherwise (decisions Q11).

Done when:

1. `Solution.Agents` holds each agent of `bots/<schema>/bot.xml` with its authentication mode, its configuration (recognizer kind and generative orchestration), the instructions of its Custom GPT component and its tools, read the same way from an unpacked folder and an exported zip. Malformed XML, JSON or YAML in those files is refused with an `InvalidDataException` naming the path, as every file the parser opens is; well-formed text of a shape the reader doesn't know, including YAML keys that the layout converter can't map, gives null fields, or a skipped component with a `note:` line, and never stops a command.
2. **PO027 (Error):** an MCP server tool on an agent whose configuration has generative orchestration off.
3. **PO028 (Warning):** an agent's instructions are over 8,000 characters, or empty when generative orchestration is on (decisions Q12).
4. **PO029 (Warning):** an agent's authentication is None.
5. **PO030 (Warning):** a tool's connection is in Maker mode.
6. **PO031 (Warning):** an agent has more than 30 tools; with 30 or fewer and an MCP server, a `note:` says the count is not checked.
7. The five rules read only agents placed in the standard harness (decisions Q4); any other agent gets one `note:` line naming PO027 to PO031, which changes no exit code (D10).
8. `references/copilot-studio.md` in `powerops-plan`, the route line and the pointer that lead to it, and the plugin copies regenerated.
9. Firing and quiet tests for each rule, reader tests for both layouts, one CLI-level test per layout, all built by hand. A page per rule with a dated Learn Sources line, and rows in `docs/rules/README.md`.
10. No eval case or fixture holds an agent, so the goldens change only in the rule lists (Data row 11). `RoleEvalTests` passes with no eval file changed, and `powerops-verify` and `powerops-review-security` keep their blob ids (`69208a2ed044a346bbae9877c8cd74d9e4794df9` and `6a6a6a1fdb71eb16d09cf3ed99406d04a0982a1f`).
11. `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status .` and the leak scan are clean, and one `feat:` PR is open.

### Won't build

- A transport rule, a 128-tool Error, the `.` in a topic name, knowledge-source counts and description checks, judging instruction quality, schema or language-server validation, running evaluations, generating widgets (the M48 section's "Deliberately doesn't"). The transport check, knowledge counts and descriptions are review items in `references/copilot-studio.md`.
- A committed agent fixture: D7's fixture can't be packed (Goal), the public samples hold tenant-shaped values (a dev-tunnel host, default publishers) and would need a scrub that D7 rules out, and a workspace from `pac copilot init` is template text under `pac`'s licence terms (decisions Q1).
- Agents on the GitHub Copilot or Customer Conversation harness: the rules say "not checked" for them (decisions Q4).
- A per-agent split of child agents' tools: every component, a child agent's tools included, names the root agent in `parentbotid`, and a child (`AgentDialog`) names its tools only in its instructions text, so PO031 counts them with the root agent's (decisions Q5). Tools of component collections (`botcomponentcollections/`): a collection's components have no `parentbotid`.
- `TaskDialog.triggerCondition` and an MCP server's `knownTools`, `UseSpecificTools` and `UseAllTools`: documented in vscode-copilotstudio's schema, seen in no export, not read.
- D10's second case for agents: no check that the solution holds a tool's `connectionReference`, and no read of a component whose agent is in another solution (it is skipped, since the agent can live elsewhere).
- A change to `powerops-review-plan`'s per-product list: the agent items in `copilot-studio.md` are read when a plan is written, not when it is reviewed.
- Topics, knowledge sources, triggers, variables and entities, beyond what the five rules read.
- The YAML layout (`solutions/<name>/`): its reader doesn't go through `SolutionParser`, and no agent in that layout was seen.
- A second read of `Assets/botcomponent_connectionreferenceset.xml`: M40 already parses it into `AgentConnectionReferences` for PO005, and no new rule needs more of it.
- An agent kind in `diff`, a gate route and the hand-off row: M49.
- A `--json` or SARIF field for the notes, or any schema change.

## Users

- A maker or agent who runs `analyze` on an exported or unpacked solution that holds a Copilot Studio agent, before it goes to Test or Production.
- CI: the Action runs `analyze` with `--fail-on error` by default, so PO027 fails a job on a solution with that fault; the four warnings fail only a job set to `fail-on: warning`. A `note:` on stderr changes no exit code.
- An agent through the MCP `analyze` tool, which passes stderr `note:` lines on.
- Every command that loads a solution through the two XML readers (folder and zip) now reads `bots/` and `botcomponents/`. Malformed XML, JSON or YAML there is refused as in any other file of the solution (decisions Q6).
- A maker who plans an agent with `powerops-plan`, which now reads `references/copilot-studio.md`.
