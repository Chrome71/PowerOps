# M94: The build runs on its own after sign-off

## Goal

Owner finding D of trial 3 (`reports/trial-3/fix-plan.md`, section M94, the authority for this plan): the build asked before each of 166 tenant writes (124 consent rows) because rule 7 of `powerops-implement` says "Ask each time". The owner wants execution to start without lag after planning and to be called only when they are genuinely needed. Their answer to Q1 (2026-11-11): "One yes per deployment".

Done when:

1. `powerops-implement` writes to a tenant only under one of two authorities and stops for everything else (rule 7, rows 2 to 4):
   - **The sign-off**, for the plan's `signed-off-hash` and the Dev environment the person named (section 3 step 3, unchanged): every write in Dev that a Step names, through the route and in the solution the plan names, with the test rows and runs that Step's check names; an environment-wide Dev setting a Step names (auditing, search), which the sign-off question lists by name (the preferred solution is not one: its ban stays); a retry of the same write after its cause is fixed; exports from Dev; local files in the repo.
   - **One yes per target environment per deployment**, covering the import (the agent line of the plan, the dry run or the form quoted in full, word for word), `settings apply --apply` and the plan's named steps in that environment. It ends on a refusal, a declined, cancelled or failed form, a changed `signed-off-hash` or a blocked report, and a new one is asked.
   - **The stop list**, each with one concrete question, holding back only what depends on the answer: (1) a sign-in, MFA, consent, terms or credential prompt the session can't complete, or a connection the person must create; (2) anything outside the signed plan: a write no Step names, another route or target, a plan line that must change, and the effect of a slip (journal it, tell the person, undo only after their yes); (3) any delete; (4) buying, assigning or starting a licence, trial or capacity; (5) any tenant-level or admin write, even one a Step names; (6) a write outside Dev that no deployment yes covers; (7) a write that reaches a person the plan doesn't name; (8) a finding only a person may accept. Anything no authority covers stops, whether or not the list names it.
2. Amendments stay person-signed. While one waits, the build goes on with steps that don't depend on it, and no tenant write runs while `powerops plan status` shows the plan changed since sign-off, or its status is not `signed-off` or `implementing` (rule 6).
3. `powerops-implement` starts right after the sign-off with one preflight (sign-in probes, the `### Licences` table re-checked, test accounts, person-made connections) that asks once for everything missing, then builds with status lines and no questions.
4. Each `writes.md` row carries its Authority: `plan <first 12 characters of signed-off-hash>, step <n>` for a sign-off write, `person: yes to <what>` for a deployment or a stop-list item, `none: slip` for a slip; `powerops plan status` warns about a row whose Authority cell is empty, and an older journal's `person: yes to step 3` row, a table with no Authority column and a file with no rows read as before.
5. The sign-off question of `powerops-plan` says in two lines what the sign-off lets the build do, lists the Dev settings it changes and says what still stops.
6. Every other text that says a Dev write needs a yes each time says the new model: the plan references, `AGENTS.md`, `CLAUDE.md`'s specialist section, five specialists, `docs/HANDOFF.md`, `docs/USE-WITH-AGENTS.md`, `docs/PLANNING-SKILLS.md`, `docs/COMMANDS.md` ("Agents" of `deploy apply`), with decision 65 (numbered at merge) in `docs/BUILD-PLAN.md`.
7. The fix plan's Done grep prints only the allowed lines of the Constraints section, and `dotnet test --filter "SkillsCommandTests|PlanCheckerTests|PluginManifestTests"` passes.
8. One Claude smoke run passes: a Step-named Dev write and a Step-named Dev setting go ahead with no question, and five stop classes (an unnamed write, a delete, a tenant-level write, a licence start, an import) stop.
9. `dotnet build` (0 warnings), `dotnet test`, `dotnet format --verify-no-changes`, `powerops plan status docs/plans/m94-build-autonomy` with no violation, and the leak scan are clean; the plugin copies are regenerated and their diff read.
