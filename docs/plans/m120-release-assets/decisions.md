## Choices

### C1. How the binaries get locked packages

Options: (a) add `RuntimeIdentifiers` to both projects and regenerate the lock files; (b) per-runtime lock files committed beside the current ones; (c) an unlocked publish that writes its lock under `obj/`, held to the committed lock by `jq`. Chosen (c). (a) makes every restore, the Action's source build in consumers' jobs included, fetch four runtime packs and two apphost packs. (b) adds four lock files that Dependabot does not update, so every package bump would break CI until regenerated by hand. (c) changes no project file and holds the application packages to the committed content hashes. It does not hold the .NET runtime and apphost packs, which no lock records under any option (NuGet treats them as download dependencies); the script prints the runtime version it bundled. Corrected after the Fable plan review, round 1, which found the first wording claimed more.

### C2. Where the Windows run goes

A new job, `windows-binary` in `ci.yml` and `windows` in `release.yml`, after the job that builds the assets. The `build (windows-latest)` job runs before `package` (`needs: build`), so it can't run a binary `package` builds; a matrix on `package` would rename a required check.

### C3. The write token

In `release.yml` only `publish` gets `contents: write`, and it runs no checkout and no build. Building moves to `assets` (`contents: read`), and the files reach `publish` as a workflow artifact, checked against `SHA256SUMS` before they are attested and attached.

### C4. One attestation for all four files

`subject-checksums: artifacts/SHA256SUMS` attests exactly the files the checksum file names, so the attested set and the checked set can't drift apart.
