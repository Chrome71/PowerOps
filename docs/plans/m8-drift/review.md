### Medium

#### R1. The token is sent to a URL taken from `pac org who` text, and the URL is never checked
- Area: 8. Security, 9. Testability
- Finding: Read 1 yields the `Org URL:` line, and the plan then builds `<environment URL>/api/data/v9.2/...` from it and sends the bearer token there (and passes it to `az` as `--resource`). Nothing says what a valid value is. A scheme other than `https` would send the token in clear text; a value with user info, a port, a path or a query would send it somewhere other than the environment's Dataverse host; a trailing `/` (the `pac` text shows one) gives a double slash in the request path; `HttpClient` follows redirects by default, and a 3xx answer from the host would carry the request on. A malformed value also raises `UriFormatException`, whose message quotes the URL (see R2). The plan's "Org URL is held in memory only and never printed" covers the output, not the destination.
- Suggested fix: In Data, say the URL must be absolute, `https`, with no user info, path, query or fragment (a trailing `/` is removed), else exit 3 naming `pac org who` and not quoting the value; the handler does not follow redirects and a 3xx is a failed read; a test for `http`, a path, user info, an empty value and a trailing `/`. Do not add a host allow-list (sovereign clouds use other hosts), but say so.
- Resolution: fixed (Data: the Org URL check before any token request, no redirects, no host allow-list; Step 4 tests)

#### R2. Transport and parse exceptions are not mapped, so the environment host can reach stderr and the token can reach a message
- Area: 8. Security, 9. Testability
- Finding: `WebResult` carries a status, a body and a timeout flag. A DNS, TLS, proxy or connection failure is none of these: `HttpClient` throws `HttpRequestException` (its message and inner `SocketException` name the host), and nothing in the plan catches it. The built command only catches `DriftReadException`; anything else goes to `SettingsCommand.Guard`, which prints `error: {ex.Message}` (the whole exception with `POWEROPS_DEBUG=1`). That breaks the rule the plan sets in Step 4 ("neither the value nor the URL appears in powerops' own stderr lines") on the most common failure of an offline or VPN-less laptop. Separately, the `az` runner is a `PacRunner`, so the token sits in a `PacResult` record, and a record's generated `ToString` prints every property, `Stdout` included; one interpolated result in a debug line or an exception message would print the token.
- Suggested fix: Say the web function turns every exception, a non-JSON body and an oversized body into a failed `WebResult` or a `DriftReadException` with fixed text (the read's name and `transport error`), never `ex.Message`; the reader catches `HttpRequestException`, `TaskCanceledException`, `UriFormatException` and `InvalidDataException`. Say the token is kept in a type with no printing `ToString` (or the reader never formats a `PacResult`). Add tests: a throwing fake web function gives exit 3 with no host in stderr, and a sweep test that runs the whole command with a recognizable token and URL through every failure path and asserts neither appears in stdout, stderr, the report or a saved file.
- Resolution: fixed (Data: every exception and bad body becomes fixed text; the reader never formats a PacResult; Step 4's sweep test)

#### R3. The built live seam has no way to forward `pac`, `az` or Web API text, and `Failed` cannot be reused for `az`
- Area: 9. Testability
- Finding: Automation says `pac`'s stdout and stderr, `az`'s stderr and the Web API `error.message` go to powerops' stderr, "as in `settings apply`". Three mismatches. (1) `settings apply` forwards that text only for `solution import` (it writes the import's stdout and stderr); for `pac org who` it prints a one-line message and nothing of the output. (2) The committed seam is `Func<string, string, Snapshot>` and `DriftReadException(string message)`; the command prints `error: --env N: {message}` and has no stderr writer for the reader, so forwarded text has to travel inside the exception message (and then sits behind the `error: --env N:` prefix, not "unchanged") or the seam changes. The plan says the reader takes a runner, a second runner and a web function, and no writer. (3) `SettingsCommand.Failed` returns pac-specific text ("pac was not found on PATH. Install pac (dotnet tool install ...)") and a hard-coded command name; the plan lists it among helpers to make `internal` and reuse, but for `az` and Web API failures it cannot be used as it stands.
- Suggested fix: In Automation, decide the carrier: `DriftReadException` gets a second property (`Forwarded`, text for stderr, kept apart from the message) and `DriftCommand` writes it after the `error:` line, or the reader gets the error writer. Say `Failed` is generalized (the tool name and the not-found text become parameters, with `SettingsCommandTests` unchanged) or that drift has its own small failure function and only `Field` and `Guard` are reused. Add the carrier to Step 4's first test list so a test pins "forwarded text goes to stderr only, never the report".
- Resolution: fixed (Automation: DriftReadException.Forwarded carries text for stderr; Failed is not reused, only Field and Guard)

#### R4. Step 4's token and header tests need a seam that the plan does not give `Program.Run`
- Area: 9. Testability
- Finding: The Step 4 list "CLI tests with fakes, through `Program.Run`" includes `az` not found, `az` failing, a 401 from the Web API, `morerecords`, timeouts, "the token never appears in stdout, stderr, the report or a saved file", and "every request carries it only in the `Authorization` header". The committed `Program.Run` takes a `pac` runner and `driftLive` (solution and `--env` to a snapshot); there is no place for a fake `az` runner or web function. Automation puts those fakes in the reader's constructor, so these end-to-end properties (exit 3 and no files saved, no token in the report) can only be tested if a test builds the reader with its fakes and passes it as `driftLive`. The plan never says so, and the first commit's `DriftCommandTests` fake `driftLive` directly, which cannot see a token at all.
- Suggested fix: In Automation and Step 4, say production wiring creates `DriftLiveReader` inside `Program.Run`'s default and tests pass `new DriftLiveReader(pac, az, web).Read` as `driftLive` (so `DriftLiveReader` and its constructor are `internal` with `InternalsVisibleTo`, or public). Keep the 3-argument `Program.Run` from building a real `HttpClient` or `az` runner unless `drift` has a live `--env`. State which tests are reader-level (header, request URL, status mapping) and which are command-level (exit codes, no files, no token anywhere).
- Resolution: fixed (Automation: Program.Run builds the reader only for a live --env; tests pass new DriftLiveReader(...).Read; reader-level and command-level tests named)

#### R5. The Step 1 capture can put a token, an environment URL or environment-only ids into fixtures, and the scrub check would not see it
- Area: 2. Environment variables and tenant values, 9. Testability
- Finding: Step 1 has the user run Web API reads with `curl`, "the token passed in a header and never printed", and saves stdout and stderr apart. A header on the `curl` command line shows in the process list and the shell history; `curl -v` or `-i` (the usual way to record "the HTTP status and error body") puts the `Authorization` header and response headers (service request ids, host names, cookies) into the saved files. The scrub then greps for URLs, emails and GUIDs only; a bearer token is none of these, and the allow-list does not cover it. Web API JSON also adds fields the old text grid did not: an `@odata.context` with the environment URL (caught by the URL grep), the primary key of each row (`solutioncomponentid` and similar, environment-specific GUIDs that are not the seed's ids and must go through the single real-to-fake mapping), and lookup columns that appear as `_<name>_value`. Read 3 as stored also selects `rootsolutioncomponentid`, which is not in Data's column list (see R9).
- Suggested fix: In Step 1, have `curl` read the header from a file or standard input (`-H @file`, mode 600, outside the repo) and forbid `-v`, `--trace` and saved response headers except a hand-copied status line; add `eyJ`, `Bearer ` and `Authorization` to the grep; say the primary-key columns and `@odata.*` properties are scrubbed or dropped (the parser ignores them) and that each fixture carries the status code apart from the body. State that the made-up variable value must not look like a token.
- Resolution: fixed (Step 1: header on stdin, no -v/-i/--trace, status apart; @odata.* dropped, keys and lookups mapped; grep for eyJ, Bearer, Authorization)

#### R8. `az` may not start on Windows through `PacRunner`
- Area: 9. Testability
- Finding: `PacRunner` starts the executable with `UseShellExecute = false`. On Windows the Azure CLI is installed as `az.cmd`, and starting a bare `az` that way is not found (a `Win32Exception`), which `PacRunner` reports as "not started", so powerops would say "az was not found on PATH" on a machine where `az` works. This is .NET behavior the plan does not mention, and `pac` is not affected. The product is cross-platform (the plan takes care that file names are the same on every operating system), the done-when runs on Linux, and CI for the Action uses Windows runners as an option. Starting `az.cmd` through `cmd.exe` would put the resource URL in a shell command line, which the plan's own constraint (arguments as a list, never a shell string) and R1 make unsafe.
- Suggested fix: Say in Data or Constraints how Windows is handled: start `az.cmd` directly on Windows (the validated URL from R1 is then an argument of a batch file, so state the quoting risk and that the URL is validated first), or state Windows is not tested in M8 and the README says so. Add a test of the runner's executable name selection if it is chosen by platform.
- Resolution: fixed (Data: az.cmd on Windows with only the checked URL as outside input; Linux only in M8, the README says so; a test pins the executable name)

#### R12. Forwarded and received text is passed on without limits
- Area: 8. Security
- Finding: Forwarded `pac`, `az` and Web API text goes to stderr unchanged. `pac org who` prints a banner with the signed-in account's email before the failure; in a CI log this is more than the environment value the README already warns about. Control characters in the text (or a line that begins with `::`, which GitHub Actions reads as a workflow command) are passed through. A 200 response with a non-JSON body (a proxy or sign-in page), a 404 for a missing table, a 429 from the service-protection limits and a 5xx are covered only by the general "any status other than 200" and are not in the Step 2 and Step 4 test lists (400, 401 and 403 are). The response body has no size limit before parsing.
- Suggested fix: Cap the forwarded text (a few KB) and replace control characters; say whether the `pac` banner lines are dropped; add the 200-with-HTML, 404, 429 and 5xx cases to the tests (no retry in M8) and a body-size cap to Data.
