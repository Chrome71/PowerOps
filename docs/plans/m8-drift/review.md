### Medium

#### R1. Step 1 leaves an unmanaged layer on the Test flow, and Step 6 item 1 expects a clean Test
- Area: 5. Dev to Test to Prod route, 9. Testability
- Finding: Step 1 has the user read the layer table in Test "again after editing the seed flow there". That edit puts an unmanaged layer on the managed seed flow in Test. Nothing removes it before Step 6. Step 6 then runs item 1 (no drift, exit 0) and item 2 (offline, same result) before item 3 asks for the edit again. With the layer still there, item 1 reports `unmanaged-layer` and exits 1, so the done-when fails for a reason unrelated to the code. The third review's R12 asked for exactly this cleanup, but the fix covered only the edit of item 3.
- Suggested fix: Add to Step 1 that after the post-edit capture the user removes the unmanaged layer on the Test flow (or imports the managed seed again), and that a read 7 capture of that clean state is taken (it also serves Assumption 3). Or move the edit capture to Step 6 and drop it from Step 1 if the fixture is not needed.
- Resolution: fixed (Step 1 removes the layer after the edit capture and captures read 7 clean again)

#### R2. How the binding, the variable value and the flow state get into Test is left open, and it decides Assumption 3 and live item 1
- Area: 5. Dev to Test to Prod route, 9. Testability
- Finding: Assumption 3 and Step 1 need a "clean" managed Test: "right after the import that binds the connection reference and with the flow on". Environments and route says only that "both imports are the user's, with or without `settings apply`". If the connection is chosen in the portal after a plain import, or the flow is switched on by hand, or the variable value is typed into Test (Step 1: "the user's edit"), each of those is a change in a managed environment, and whether it leaves an unmanaged layer is not documented. That would refute Assumption 3 by how the setup was done, not by what `drift` does, and the two fallbacks then either exempt the connection reference or variable component types (which blinds `drift` to the most useful drift) or record live item 1 as not supported (which empties the done-when). Step 1 also contradicts itself on order: it sets the variable value "before the capture", but takes read 7 "right after the import and binding (before any edit)", so the value edit comes first and the capture is not clean of edits.
- Suggested fix: In Environments and route, say the Test import uses a settings file that carries the made-up variable value and the connection reference's connection, and that the import turns the flow on (as in M7), so nothing is edited in Test before the clean capture. Reword "before any edit" in Step 1 to "before the flow edit". If the capture still shows a layer, say the setup is redone through the settings file before an exemption or "not supported" is recorded.
- Resolution: fixed (Test is set up only through a settings apply import carrying the value and the connection; 'before the flow edit')

### Low

#### R3. Read 7's query and component-name map are specified in two places that disagree
- Area: 9. Testability
- Finding: Data (read 7) says the component name for each `componenttype` is a small map in Core "if a filter needs it", which applies to the batched mode as well as the per-component mode (a batched query still filters by table and takes ids in an `in` condition). Step 2 tests the map "only for the per-component mode". Data also says `{solutionId}` is the placeholder of reads 3 to 7, and Step 2 builds queries "from a solution name or a parsed solution id", but a batched or per-component read 7 needs component ids and a component name, so the stored Step 1 template and the "equals the stored query with the placeholder filled" test have no way to express them.
- Suggested fix: In Step 2, test the map in every mode that uses a filter (batched and per-component), and name the extra placeholders of read 7 (type name, id list or id) in Data, with the query test filling them.
- Resolution: fixed (read 7 placeholders named; the map is tested in every filtering mode)

#### R4. The solution-name pattern can pass a trailing line break
- Area: 9. Testability
- Finding: The name is checked against `^[A-Za-z0-9_]+$`. In .NET, `$` also matches before a final `\n`, so a value such as the name plus a line break passes, is written into the FetchXML and the file name, and reads as "not installed" (exit 2) or, in a later reuse of the pattern, slips through a trust-boundary check. The plan makes this check the only guard before the name enters a query, so the exact test matters.
- Suggested fix: Say the check is a full match (`\z` or `Regex.IsMatch` on an anchored `\A...\z` pattern), and add a test with a trailing line break to the "a name outside the pattern is refused" case in Step 2.
- Resolution: fixed (full-match pattern with \A and \z; trailing line break test)

#### R5. The subject of an unmanaged-layer item on a flow is undefined, and live item 3 says "on that flow"
- Area: 9. Testability
- Finding: The subject is "the name for flows, variables and references, and `<type> <id>` for other components". The unmanaged layer is a property of a component row (type and id), and a cloud flow's row is type 29, which the plan treats as "other" for the layer check and as a flow for `component-missing`. So the item can read `29 <id>` instead of the flow's name, and the user cannot tell from the output that it is the seed flow, which is what item 3 asks the report to show. Two builders would write two outputs, and the golden would follow whichever one is built.
- Suggested fix: Say in Automation that an `unmanaged-layer` item takes the name when the component's id is in the cloud-flow, variable or reference lists, else `<type> <id>`, with a Step 3 test.
- Resolution: fixed (unmanaged-layer items take the flow, variable or reference name; test)

#### R6. Snapshot-file input handling is thinner than the rest of the plan
- Area: 9. Testability, 2. Environment variables (values in output)
- Finding: Three gaps. (1) A snapshot is checked only for `schemaVersion` and the solution name. Nothing says what happens to a file with a missing list, a duplicate key (two components with one type and id, which would throw in a dictionary and may quote the file in the message), an unknown `state` or a `valueHash` that is not hex, or a very large file (the snapshots are meant to travel as CI artifacts, and the readers elsewhere cap reads with `ReadBudget`). (2) The plan lists `NotFound` among the helpers to reuse, but `NotFound` prints `error: path not found: <path>`, which is the `--env` value the plan says powerops never prints; the missing `.json` case (exit 2) would print it. (3) Errors for a bad snapshot are said to name the `--env` by position for `pac` reads, but not for snapshot files, and AGENTS.md says reader errors start with the path.
- Suggested fix: Add to Step 2 a snapshot-load test for a missing list, a duplicate key and an unknown state, each giving `InvalidDataException` without quoting the file, and a size cap. In Step 4, say the missing-`.json` and bad-snapshot messages name the `--env` by position (not through `NotFound`) and add that to the "value appears nowhere" test.
- Resolution: fixed (snapshot load rejects a missing list, a duplicate key, an unknown state, a bad hash and a file over 1 MB; NotFound not reused; --env named by position)

#### R7. The scrub does not require the same fake id for the same real id in the Dev and Test captures
- Area: 2. Environment variables (tenant values), 9. Testability
- Finding: Step 1 turns "other" component ids into fake values and keeps only the seed's own. The Dev and Test captures are compared by the golden `drift-seed.*` and by the tests, which match components by type and id. If a component that exists in both environments is scrubbed to two different fake ids, or to a fake id that collides with one already used for another component (the existing captures use the all-zero GUID style with a short number), the goldens show `component-missing` and `component-extra` pairs that are scrub artifacts. The grep rule cannot see this.
- Suggested fix: Say the scrub keeps one mapping from real to fake id for all captures in the folder, and add a check that the Dev and Test component lists, after scrubbing, differ only where Step 1 recorded a real difference.
- Resolution: fixed (one real-to-fake id mapping across the folder, and a check of the Dev and Test lists)

#### R8. Step 5's README line takes the needed privilege "from the admin answer", but no step gets the answer

The first admin question (which role can run the reads without write rights) has no step that answers it. The maintainer runs Step 1 with their own, probably administrator, account, so what was observed is not a minimum, and a README line written from it would overstate or understate the need. The plan reaches sign-off with this question open.

- Resolution: fixed (README names the capture's role and says the minimum was not tested)

#### R9. The order of the usage and snapshot checks contradicts itself for mixed errors
- Area: 9. Testability
- Finding: Automation step 1 lists the exit-2 usage errors first, then loads every snapshot file, and then says "the first problem found, in `--env` order, decides the exit code". For `--env a.json --env missing.json`, where the first is an unreadable snapshot (exit 3) and the second is a `.json` path naming no file (exit 2), the list order gives 2 and the `--env` order gives 3. Step 4's tests cover each case alone, so the build can pick either reading.
- Suggested fix: Say that all usage errors are checked first (exit 2), then the snapshots in `--env` order, and add one mixed case to Step 4. Drop "in `--env` order" from the first clause.
- Resolution: fixed (usage errors first, then snapshots in --env order; mixed test)

#### R10. Parser edge cases that Step 2 leaves open
- Area: 9. Testability
- Finding: (1) `FlowState.Export` maps every code except 1 and 2 to `off`, and the plan says states are "mapped to the same names as `FlowState`"; reusing it would turn an unknown `statecode` into `off` and make a flow-state item from a read powerops cannot understand. (2) `org who` with no `Friendly Name:` line: `settings apply` treats it as exit 3, drift says only "output powerops cannot read". (3) An empty variable value and no value at all: `pac` may print both as an empty cell, and the plan says `valueHash` is null "when there is no current value", so whether an empty string hashes to the empty-string hash or to null is open, and the two give a false `variable-value`.
- Suggested fix: In Step 2, say an unknown `statecode` raises `InvalidDataException` (not `FlowState.Export`), a missing friendly name is exit 3, and an empty value is treated as no value, with a test for each.
- Resolution: fixed (unknown statecode unreadable, missing friendly name exit 3, empty value is no value; tests)
