# M8: drift

## Goal

`powerops drift` compares one solution across two or more Dataverse environments and reports where they differ: the version, the components, unmanaged layers on a managed solution's components, environment variable values, connection reference bindings and cloud flow states. It only reads: the environment's name and URL through `pac org who`, and the solution's rows through the Dataverse Web API, with a token from the Azure CLI (`az`) (Q6). It can save what it read as snapshot files, and a later run can compare those files offline. This is the BUILD-PLAN M8 row (release v0.9.0, build-order tasks 22 to 24), and the folded `settings diff` (BUILD-PLAN decision 12). M9's `deploy plan` reuses its snapshot model.

Done when:

- Offline: the tests under Steps pass on the recorded Step 1 captures with fake `pac`, `az` and web functions (no tenant, no network). Equal snapshots exit 0. Each of these exits 1 and is named in the output: a version change, an extra component, an unmanaged layer (on a recorded capture if Step 1 shows layers can be read, else on a hand-written snapshot), a changed environment variable value, an unbound connection reference and a flow that is off. A failed or timed-out read exits 3. The JSON goldens validate against `docs/schemas/drift.schema.json` and `docs/schemas/snapshot.schema.json`. `dotnet build`, `dotnet test` and `dotnet format --verify-no-changes` are clean.
- Live (BUILD-PLAN M8 done-when), in the user's Dev and Test (BUILD-PLAN decision 9), each run read-only and with the user's yes:
  1. With the seed installed in both (unmanaged in Dev, managed in Test, the same environment variable value, its connection reference bound, its flow on), `drift --solution PowerOpsSeed --env <Dev> --env <Test> --save <dir>` reports no drift and exits 0. The managed difference is shown as information (Q3).
  2. `drift --solution PowerOpsSeed --env <dir>/<Dev file> --env <dir>/<Test file>`, offline, gives the same items, the same text output and the same exit code (0). Only the JSON `source` fields differ.
  3. After the user edits the seed flow in Test (in the maker portal; powerops writes nothing), a live run reports the unmanaged layer on that flow and exits 1. The edit must leave the flow on, so no `flow-state` item is expected. If Step 1 shows that layers cannot be read, that the flow cannot be edited in Test, or that the edit leaves no unmanaged layer, this item is recorded as not supported in the PR instead (Q4).

## Users

- Agents in the user's Claude Code or Codex that run `powerops drift ... --format json` to answer "does Test still match Dev?" before a deployment, and `--save` the snapshots for M9's plan.
- Makers and CI jobs that want a Markdown drift report in a PR or a job summary.

## Data

**Inputs.** `--solution <unique name>` and two or more `--env` values. Each `--env` is either a path to a snapshot file (when a file exists at that path) or an environment, passed unchanged to `pac` as `--environment` (an environment id or URL, as `pac` takes them). A value is a snapshot path when it ends in `.json` (ignoring case) or names an existing file; one that ends in `.json` and names no file is a usage error, so a mistyped snapshot path is never sent to `pac`. Anything else, an environment URL with its `/` included, is an environment. powerops never prints the value of an `--env`, because it may be a URL. Output names each environment by its position (`1`, `2`, ...) and its friendly name, because friendly names are not unique.

**Reads per live environment** (all read-only). Read 1 runs `pac` with `--environment <value>` through the existing `PacRunner`, with the 30-second read timeout. Reads 2 to 7 are Web API requests (below), each with a 30-second timeout, after one token request:

1. `pac org who`: the friendly name (the `Friendly Name:` line) and the environment URL (the `Org URL:` line), both read as `settings apply` reads its lines. Nothing else of its output is kept. The URL is held in memory only and never printed, like the `--env` value. It is checked before any token is asked for: an absolute `https` URL whose host has only letters, digits, `-` and `.`, with no user info, port, path (a trailing `/` is removed), query or fragment; anything else exits 3 naming `pac org who`, without quoting the value. There is no host allow-list, because sovereign clouds use other hosts.

   Token: `az account get-access-token --resource <environment URL> --query accessToken -o tsv`, run like `pac` (a subprocess with an argument list, 30-second timeout). The token is held in memory, sent only as the `Authorization: Bearer` header of reads 2 to 7, and never printed, logged, saved or put in a message. On success `az`'s stdout is the token, so it is never forwarded.

2. On `solution`, filtered on `uniquename`: `solutionid`, `version`, `ismanaged`. No row means the solution is not installed; the other reads are skipped.
3. On `solutioncomponent`, filtered on that `solutionid`: `componenttype`, `objectid`, and `rootsolutioncomponentid` (only for Step 1's count of root components; the snapshot does not keep it).
4. On `workflow`, the solution's workflows with `category` 5 (cloud flows): `workflowid`, `name`, `statecode` (0 off, 1 on, 2 suspended, mapped to the same `on`, `off`, `suspended` names as `FlowState`; any other value is unreadable output, not `off`, so `FlowState.Export` is not reused).
5. On `environmentvariabledefinition` with an outer link to `environmentvariablevalue`, for the solution's definitions: `schemaname` and the current `value`.
6. On `connectionreference`, for the solution's references: `connectionreferencelogicalname`, `connectorid`, and `connectionid` (only whether it is set is kept; the id itself is never stored or printed).

Reads 4 to 6 select "the solution's" rows by a link to `solutioncomponent` (`objectid` equal to the row's id, `solutionid` equal to the solution's id), the relation read 3 already uses, not by a `solutionid` column on the row.
7. On `msdyn_componentlayer`, only where the solution is managed (Q3): which of the solution's components have an unmanaged layer. It selects only `msdyn_componentid`, `msdyn_solutionname` and `msdyn_order`, never `msdyn_changes` or `msdyn_componentjson`, which can hold the component's data. If Step 1 shows the table cannot be read through the Web API with FetchXML, this read is dropped and the snapshot says `layersRead: false` (Q4). If the table needs a filter per component, the read is batched (one query per component type, with an `in` condition on the ids) when the table accepts that. If it accepts only one component per query, at most 50 component reads are made; a managed solution with more components gets `layersRead: false`, as under Q4, and the README says so. The table's component name for each `componenttype` number (if a filter needs it) is a small map in Core, taken from Step 1's capture, with a test. Read 7's stored template then also has the placeholders `{componentName}` and `{componentIds}` (one id per query in the per-component mode).

**Web API requests** (reads 2 to 7). Each is `GET <environment URL>/api/data/v9.2/<entity set>?fetchXml=<the FetchXML, URL-encoded>` with the headers `Accept: application/json`, `OData-MaxVersion: 4.0`, `OData-Version: 4.0` and `Prefer: odata.include-annotations="Microsoft.Dynamics.CRM.morerecords"`. The entity sets are `solutions`, `solutioncomponents`, `workflows`, `environmentvariabledefinitions`, `connectionreferences` and `msdyn_componentlayers`. The response is OData JSON, a `value` array with one object per row. Columns come as raw values (a choice is its number, a yes/no column `true` or `false`); no formatted-value annotation is asked for, so no label in the user's language is read. A column with no value has no property in the row (Learn: FetchXML through the Web API does not return null properties), so a missing property is read as null. A linked table's column is named `<link alias>.<column>` (read 5: `v.value`). A result with `@Microsoft.Dynamics.CRM.morerecords` true is more than one page (5,000 rows) and exits 3 with "more than one page of results is not supported"; one solution's rows stay far below a page, so paging is not built. Any status other than 200 is a failed read. Requests go through one `HttpClient`, with no new package, whose handler does not follow redirects: a 3xx is a failed read. The web function reads at most 16 MB of a body; a longer body, a body that is not JSON, and every exception (`HttpRequestException`, `TaskCanceledException`, `UriFormatException`, `JsonException`, `InvalidDataException`) become a failed read with fixed text (the read's name and `transport error`, `unreadable response` or `timed out`), never an exception's own message, which can name the host.

On Windows the Azure CLI is `az.cmd`, which the runner starts directly; the only argument from outside is the URL checked above, which holds no character `cmd` treats specially. M8 runs and tests on Linux only, and the README says Windows is not tested. A test pins the executable name per platform.

Step 1's FetchXML is written by hand and stored with the capture, in `tests/fixtures/pac/drift/queries/`, with `{solutionId}` as the placeholder in reads 3 to 7. Step 2 copies the exact text into Core (`src/PowerOps.Core/Drift/DriftQueries.cs`), and a test compares the built queries with the stored ones. The solution name goes into FetchXML only after it fully matches `\A[A-Za-z0-9_]+\z` (no trailing line break) (unique names allow only letters, digits and underscores); anything else is a usage error. The solution id goes in as a parsed GUID.

Changes from the BUILD-PLAN row's read list: flow states come from the `workflow` table (read 4), not from `pac power-automate list-cloud-flows`. One FetchXML read gives every cloud flow's name and state, with the same parser and filter as the other reads and no Preview command. `pac solution list` is not read: reads 3 to 7 need the solution id, so read 2 replaces it. `environmentvariabledefinition` and `pac org who` are added.

Amendment of 2026-10-21 (Q6): reads 2 to 7 move from `pac env fetch` to the Dataverse Web API. Learn documents only `--environment`, `--xml` and `--xmlFile` for `pac env fetch`, and no output format or `--json` for it, so its text output cannot be parsed against documented behaviour; it is rejected. An undocumented `pac` mode is not used. The Web API's JSON, raw values, missing null properties, error body and paging are documented. `pac` stays the tool for what it documents: `pac org who` turns `--env` into the environment's name and URL, so `--env` still takes what `pac` takes. AGENTS.md's rule "Call `pac` as a subprocess. Do not reimplement it." holds: powerops reimplements no `pac` command; it reads rows that `pac` prints in no documented format. Step 5 adds one clause to that rule.

**Snapshot** (a Core record, and the snapshot file, Q1): `schemaVersion` (the snapshot file's own constant, starting at 1, which moves only when the snapshot format changes, not with `JsonOutput.SchemaVersion`; `docs/schemas/README.md` says so), the environment's friendly name, the solution's unique name, `installed`, `version`, `managed`, `layersRead`, and four lists. `layersRead` is false only when the layer read was dropped for a managed solution (Q4 or the 50-read cap). It is true when layers were read, and also when the solution is unmanaged or not installed, because no read was needed. The lists are sorted by their match key, ordinal:

- components: `type` (the `componenttype` number), `id` (`objectid`), `unmanagedLayer` (true, false, or null when layers were not read or the solution is unmanaged); matched by type and id;
- environment variables: `schemaName`, `valueHash` (the SHA-256 of the current value's UTF-8 bytes after `\r\n` is turned into `\n`, in lowercase hex, or null when there is no current value) (Q2); matched by schema name, ignoring case;
- connection references: `logicalName`, `connectorId`, `bound`; matched by logical name, ignoring case;
- cloud flows: `id`, `name`, `state` (`on`, `off`, `suspended`); matched by id (the same across imports, Learn), shown by name.

A snapshot never holds an environment id or URL, a connection id, a value, a user name or `pac`'s own text. The ids it holds are the solution's own component ids, which are in every export of the solution anyway.

**Snapshot files** (Q1). `--save <dir>` creates the folder if needed and writes one file per live `--env`, `<dir>/<solution>.<environment name>.json`. Every character outside letters, digits, `-`, `_`, `.` and space becomes `-`, so the name is the same on every operating system. An existing file is overwritten. Snapshot-file inputs are not written again, and `--save` with no live `--env` is a usage error. Files are written only after every read succeeded. A snapshot file passed as `--env` must parse, have the current `schemaVersion` and name the same solution (compared ignoring case, as Dataverse compares unique names). Otherwise it is unreadable input (exit 3), or a usage error (exit 2) for another solution.

## Automation

`powerops drift --solution <name> --env <env or file> --env <env or file> [--env ...] [--save <dir>] [--format text|json|markdown] [--out <file>]`

1. **Usage and snapshot files** (before any `pac` or `az` call or request): a missing `--solution` or one that fails the name pattern, fewer than two `--env`, an `--env` that ends in `.json` but names no file, `--save` naming an existing file or used with no live `--env`: exit 2. All of these are checked first. Then every snapshot-file `--env` is loaded and checked in `--env` order: unreadable or a wrong `schemaVersion` is exit 3, another solution is exit 2, and the first problem stops the run.
2. **Read**: the live `--env` values in order, each with reads 1 to 7. The first failed, timed-out or unreadable read stops the run with exit 3. The message names the `--env` by its position (`--env 2`) and the read (`pac org who`, `az account get-access-token`, or the Web API read of a table, such as `solutioncomponent`), never the `--env` value, the URL or the token. A failed `pac org who` adds the hint "Sign in with pac auth create, and check that the account can read that environment." (not `PlanFacts.SignInFix`, which points to `pac org select`), and `pac`'s stdout and then its stderr go unchanged to powerops' stderr, as in `settings apply`. A failed `az` call adds "Sign in with az login, and check that the account can read that environment.", and only `az`'s stderr is forwarded. `az` not found exits 3 with "az was not found on PATH. Install the Azure CLI and sign in with az login." A failed Web API read gives the HTTP status code, and the `error.message` of the documented error body (`{"error":{"code","message"}}`) goes to stderr; a 401 or 403 adds the `az login` hint. A timeout forwards nothing. Forwarded text travels in `DriftReadException.Forwarded`, a second property apart from the message; `DriftCommand` writes it to stderr after the `error: --env N: <message>` line, and never to the report or a file. Forwarded text may repeat the `--env` value or the URL; the README says so. The reader takes the token out of the `az` result at once and never formats a `PacResult` (a record's `ToString` prints every property). Nothing is saved and no report is written. A failed layer read (read 7, for example for lack of access to the table) is exit 3 like any other. A read with more than one page (`morerecords` true, see Data) also exits 3. A solution that is installed in none of the environments exits 2 ("solution `<name>` is not installed in any environment"): it is almost always a mistyped name, and "no drift" would read as a pass. With `--save`, two live environments whose file names collide (compared ignoring case) exit 2 after the reads and before anything is written.
3. **Compare** each environment with the first (BUILD-PLAN row). The result is a list of items, each with the environment, a kind, a subject and whether it is drift:

| Kind | Drift | When |
|---|---|---|
| `solution-missing` | yes | the solution is installed in the first environment and not in this one, or the other way round; nothing else is compared for this pair |
| `version` | yes | the versions differ (the item shows both) |
| `managed` | no | the managed flags differ (Q3); shown as information |
| `component-missing` / `component-extra` | yes | a component (matched by type and id) is in the first environment and not this one, or in this one only. Type 29 rows whose id is in the cloud-flow list, environment variable definitions and values (types 380 and 381) and connection references have their own kinds below, so they are left out here and one difference is reported once. Other workflows (business rules, classic workflows, desktop flows) stay in |
| `unmanaged-layer` | yes | a component of a managed solution has an unmanaged layer; checked in every environment, the first included |
| `layers-not-read` | no | the layer read was dropped (Q4) and the solution is managed there |
| `variable-missing` | yes | the definition is in the first environment and not this one, or the other way round |
| `variable-value` | yes | the current values differ, including a current value on one side only; the output says `differs` and never shows a value or a hash (Q2) |
| `reference-missing` | yes | as for variables |
| `reference-connector` | yes | the connector differs |
| `reference-unbound` | yes | the reference has no connection; checked in every environment, the first included |
| `flow-missing` | yes | as for variables |
| `flow-state` | yes | the states differ (the item shows both) |

A flow that is off in every environment is not drift (Dev flows are often off on purpose); the done-when case "a flow that is off" means off in one environment and on in the first. The checks of a single environment (`unmanaged-layer`, `reference-unbound`) run for every environment where the solution is installed, whatever the pair comparison found. Connection ids are never compared: connections belong to one environment, so a reference bound in both is bound to different ids by design. Default values of environment variables are not compared: they ship in the solution, so a version match covers them.

4. **Report**: items sorted by environment position, then by the kind order of the table, then by subject (ordinal). The subject is the name for flows, variables and references, and `<type> <id>` for other components (powerops reads no display names for them). An `unmanaged-layer` item takes the flow's name when its component's id is in the flow list; the snapshot keeps no ids for variables and references, so their layers are named `<type> <id>`. With `--save`, the files are written now. Exit 0 when no item is drift, 1 when any is.

Exit codes: `0` no drift, `1` drift, `2` usage error (including a solution installed nowhere), `3` a `pac` or `az` call or a Web API read failed, timed out or returned output powerops cannot read, `pac` or `az` not found, or an unreadable snapshot file.

`--format json` follows the M4 contract: `schemaVersion` first, `docs/schemas/drift.schema.json`, its row in `docs/schemas/README.md`, a `Map` entry in `OutputSchemaTests` and goldens. The report holds `solution`, `drift` (true or false), `environments` (position, name, `source` `live` or `snapshot`, `installed`, `version`, `managed`, `layersRead`) and `items` (environment position and name, kind, subject, `drift`, and `expected`/`actual` for `version`, `managed`, `reference-connector` and `flow-state`, else null). The snapshot file has its own schema, `docs/schemas/snapshot.schema.json` (prefix `snapshot`, so it does not clash with the `drift` prefix in `Map`).

The model, the parsers of the Web API's JSON, the comparison and the reports live in Core (`src/PowerOps.Core/Drift/` and `src/PowerOps.Core/Output/DriftReport.cs`). `src/PowerOps.Cli/DriftCommand.cs` parses the options, loads and writes files and writes the report; the live read of one environment is a function passed to it (`Program.Run`'s `driftLive`, so command tests use a fake). The live reader, `src/PowerOps.Cli/DriftLiveReader.cs`, runs `pac org who`, `az` and the requests. It takes the existing `Func<IReadOnlyList<string>, TimeSpan, PacResult>` runner that `Program.Run` passes to `settings` (for `pac`), a second runner of the same shape for `az` (a `PacRunner` with the executable `az`), and a web function `Func<Uri, string, TimeSpan, WebResult>` (URL, token, timeout to status code, body and timed out) over one `HttpClient`; reader tests fake all three and never use the network. `Program.Run`'s default `driftLive` builds the reader (with a `PacRunner` for `az` and the `HttpClient`) only when a run has a live `--env`. Tests pass `new DriftLiveReader(pac, az, web).Read` as `driftLive`: reader-level tests check the request URL, the headers, the token only in `Authorization`, and the status and exception mapping; command-level tests through `Program.Run` check exit codes, no report and no files after a failure, and no token, `--env` value or URL in stdout, stderr, the report or a saved file. `DriftLiveReader` and `WebResult` are `internal`, with `InternalsVisibleTo` for the CLI tests. The private helpers of `SettingsCommand` that drift needs become `internal` and are reused, not copied: `Field` (the `Friendly Name:` and `Org URL:` reader) and `Guard` (exceptions to exit 3). `Failed` is not reused: its text is `pac`-specific, and drift has its own small failure function for `pac`, `az` and the requests. `NotFound` is not reused: it prints the path, and drift's messages name an `--env` by its position only, for snapshot files too; `PlanFacts.SignInFix` is already `internal`. `SettingsCommandTests` stay unchanged.

Out of scope (not asked for): a mode that prints positions only, without friendly names (names are printed and saved; the README says the reports and files are for private places), an option to accept environment variables whose values differ by design (such a variable always exits 1; JSON users can filter `items` by `kind`, and the README says so), `--show-values` (Q2), display names of components other than flows, variables and references, comparing default values, comparing each environment with every other one, reading more than one solution per run, paging past 5,000 rows, the Dataverse SDK, any Web API request other than the GETs of reads 2 to 7 (Q4, Q6), a token from anything but `az`, and any write to an environment.

## Screens

None. Command-line only. Text output: one line per environment (`<position> <name>: <version>, managed|unmanaged[, layers not read]` or `<position> <name>: not installed`; `layers not read` appears only for a managed solution with `layersRead: false`), one line per item (`<position> <name>: <kind> <subject>[: <expected> -> <actual>]`, information items marked `(info)`), and a summary line (`no drift` or `<n> drift items`). Markdown: an environments table and an items table, for a PR comment.

## Environments and route

- Environments: the user's Dev (a managed developer environment) and Test (a sandbox), set up by the user before Step 1 (BUILD-PLAN decision 9). The plan names neither; `environment` stays null because `powerops plan facts` was not run (planning must not contact the tenant). Their ids and URLs live only in the user's shell or gitignored files.
- The seed moves into Dev before Step 1. The user imports the seed (unmanaged) into Dev and sets the variable's current value there to the made-up test value of Step 1. Dev is unmanaged, so edits there leave no layer that counts. The user then exports the seed as managed from Dev and imports it into Test with `powerops settings apply --apply`, using a settings file kept outside the repo. That file carries the same value and the connection for the reference, so the import binds the reference and brings the flow back on (as M7 showed). Nothing is edited in Test before the clean capture.
- Auth: the user's pac profile for `pac org who`, and the user's Azure CLI sign-in for the token. The user installs the Azure CLI (on Arch-based systems such as CachyOS the `azure-cli` package, else Microsoft's documented install) and runs `az login` themselves. powerops signs in to nothing and stores no token; `--environment` picks the environment per call, so no `pac org select` is needed. The reading account needs a security role in each environment that lets it read the tables (admin question).
- Two identities: `pac org who` runs as the pac profile and the rows are read as the `az` account; they can differ, and the report does not claim they are one. Step 1 records whether they were the same account. `az` uses its signed-in tenant; an environment in another tenant is not supported in M8 unless Step 1 shows otherwise, and the README says so.
- CI (for M9 and M10): a workflow that runs `drift` needs an `az` sign-in beside `pac`'s, for example an OIDC `az login` as the same application user, with read privileges in each environment. M8 builds nothing for CI; the README says what CI needs.
- Agents run `drift` only against environments the user named in the session. It reads only, so it needs no `--apply`-style flag.
- Route of the code: the normal PR to main and the v0.9.0 release.

## Constraints

- Read-only: every `pac` and `az` call reads, and every Web API request is a GET. The only file writes are `--save` and `--out`, both explicit. `pac` and `az` are subprocesses with arguments as a list; the FetchXML is one URL-encoded query parameter (`Uri.EscapeDataString`).
- No new package. SHA-256 and `HttpClient` come from the base library. The Azure CLI (MIT licence) is a new prerequisite on the user's machine, as `pac` is; the README says so.
- Tests never call a real `pac` or `az`, or the network.
- Fixtures and goldens hold fake values only (environment names such as `Contoso Dev`, fake ids for anything outside the seed, no connection ids, no URLs). Step 1's captures are scrubbed before commit and described in `tests/fixtures/NOTICE.md`.
- A SHA-256 hides a value from a reader, not from someone who guesses short values (a flag, a known URL). Snapshot files are for the user's own folders and private CI artifacts, not public places. The README and the snapshot schema's description say so and do not call the files "safe" (this narrows the wording of Q2's answer).
- Run time: one `pac` call, one `az` call and five Web API reads per environment, plus the layer reads, each up to 30 seconds. Layer reads are one per component type when batched, or up to 50 when the table takes one component per query (Data, read 7). Step 1 records which, and the time per read, and the README gives the cost.
- Licensing: reading needs no licence beyond access to the environments. In Managed Environments, every user who runs an app or flow needs a premium licence (BUILD-PLAN research basis); the seed flow runs in both, which the user's tenant covers (admin question below).
- Sources, checked on Microsoft Learn on 2026-10-21 (local `pac` 2.13.1 usage text read; no tenant contacted):
  - "pac env" (learn.microsoft.com/power-platform/developer/cli/reference/env): `fetch` takes `--xml`, `--xmlFile` and `--environment` (an id or URL); no output format, paging or virtual-table support is documented; `pac org` is the old name of `pac env`, and `who` takes `--environment`.

  - "Solution layers" (learn.microsoft.com/power-apps/maker/data-platform/solution-layers and learn.microsoft.com/power-platform/alm/solution-layers-alm): all unmanaged changes share one unmanaged layer on top of the managed layers, typically shown as the Active layer.
  - "Work with cloud flows using code" (learn.microsoft.com/power-automate/manage-flows-with-code): category 5 is a cloud flow; `workflowid` is the same across imports.
  - "Use environment variables for Azure Key Vault secrets" (learn.microsoft.com/power-apps/maker/data-platform/environmentvariables-azure-key-vault-secrets): a secret variable holds a reference to the vault, not the secret.
  - "Use a connection reference in a solution" (learn.microsoft.com/power-apps/maker/data-platform/create-connection-reference): a connection is chosen per reference at import.

## Assumptions

The first five are go-back Assumptions: if Step 1 refutes one, the plan goes back to planning before Step 2, with the fallback named.

- The Web API returns FetchXML results as Learn documents them: a `value` array, raw values as plain properties (`componenttype`, `statecode` as numbers, `ismanaged` as a boolean), no property for a null column, `v.value` for read 5's linked column, a value with a space, a comma and a line break whole in a JSON string, and the `error` body with a non-200 status for a malformed query. Step 1 checks each. Fallback: none within this plan (the Web API was chosen because it is documented); M8 stops and the BUILD-PLAN row is revised (a new decision).
- `az account get-access-token --resource <environment URL>` gives a token that the environment's Web API accepts for the signed-in user. Learn documents the Az PowerShell equivalent for Dataverse, not `az`; Step 1 checks it. Fallback: none within this plan; M8 stops for a new decision on the token source.
- Component types and ids (`componenttype`, `objectid`) are the same in Dev and Test after an import, for every root component of the seed (the table, the flow and the canvas app) and their subcomponents. Learn states it only for flows; Step 1 compares them. If only some types differ, the fallback is to leave those types out of `component-missing` and `component-extra` and say so in the README. An unmanaged and a managed solution may also list different rows (subcomponents); Step 1 counts the rows per type in each. If they differ, the fallback is to compare only root components (by the column Step 1 shows marks them), or, if none does, to compare components only between environments with the same managed flag and report a `components-not-compared` information item for the other pairs.
- A clean managed Test, right after the import that binds the connection reference and with the flow on, shows no unmanaged layer. If Step 1 shows one although Test was set up only through the settings-file import, the fallback is to name the component types exempt from `unmanaged-layer` (for example the connection reference), or to record live item 1 as not supported.
- `pac org who --environment <id or URL>` reads the named environment, not the profile's current one, and prints its `Org URL:` (Learn and the 2.13.1 usage text; the M7 capture shows the line). Fallback: none within this plan; `pac org select` before each environment writes pac's settings and needs a new decision, so M8 stops and the BUILD-PLAN row is revised.
- The Web API can read `msdyn_componentlayers` with FetchXML, and its rows show which layer is the unmanaged one. Not documented; Step 1 checks it. If not, Q4 applies (not a go-back).
- The connection reference's component type number is taken from Step 1's capture: Learn does not list it.
- A connection reference with an empty `connectionid` is unbound.
- Environment facts were not available: `powerops plan facts` was not run during planning.
