# PO023: Power Pages table permission lets anonymous users create, write or delete

Severity: warning

## What it finds

An active table permission (component type 18) with `create`, `write` or `delete` set to true whose roles include an active web role (component type 11) with `anonymoususersrole` true. There is one finding per anonymous role, named by the permission's name, listing the privileges in the order create, write, delete. A role is named by its web role's name, or by its id when the solution doesn't hold it.

A child permission with no roles of its own takes its parent's roles, so it is a finding when its parent's roles include an anonymous role. A grant that reaches a child only through an inactive parent doesn't count, because Learn says the child isn't in effect then; PO022 reports that child. Read, append and append to are not checked, and neither is an authenticated role with create, write or delete.

In two cases the rule can't tell whether a permission that grants create, write or delete reaches an anonymous role. It gives no finding, `analyze` prints one `note:` line on stderr, and the exit code doesn't change:

- A role id on the permission is not in the solution: `PO023 not checked for table permission '<name>': web role '<id>' is not in the solution.` The input it needs is that web role, in the same solution.
- The permission takes its roles from its parent, and a parent or a permission above it is not found in the solution (a `parententitypermission` value that is not a GUID string counts as not found), so the inherited roles can't be read: `PO023 not checked for table permission '<name>': its parent, or a permission above it, is not found in the solution.` The input it needs is the parent table permission, and the permissions above it, in the same solution.

The rule reads the `powerpagecomponents/` folder of the enhanced data model in a solution, unpacked or in a zip. It does not read the `.powerpages-site/` layout. Learn doesn't document the export layout; the `anonymoususersrole` flag was observed in the web roles of the core-portal solution of microsoft/gov-apptemplates, and the `create`, `write` and `delete` flags in the table permissions of the Contoso Real Estate sample.

## Why it matters

Learn says anonymous users get access to a site through the Anonymous Users web role, and that this role respects only table permissions. Its security advice is to treat anonymous table permissions as public data access, and not to grant anonymous users create, read, update or delete access unless the business requirement explicitly calls for public access.

This rule checks only the privileges that change data. Learn's advice names update where the export's key is `write`, and it covers read too; leaving read out is the rule's own choice.

## How to fix

Remove create, write and delete from the table permission of the anonymous role, or move them to a role that requires sign-in. If the site needs public writes, confirm it and baseline the finding as Suppress says.

Microsoft's own sample sites trip some of the Power Pages rules, so the message says "before Production", not "now".

## Suppress

To accept the finding for now, run `powerops baseline` and use `powerops analyze --baseline powerops-baseline.json`. A baselined finding is matched on solution, rule, component and message.

Two permissions with the same name and table give findings that differ only in their file, so one baseline entry covers both.
