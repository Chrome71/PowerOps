# PO035: Flow names a navigation property in the wrong case

Severity: warning

## What it finds

A cloud flow with an action of the Microsoft Dataverse connector that names a navigation property in `$expand`, or in a lookup input `item/<name>@odata.bind`, where the name matches one of the action's table's exported navigation properties only when case is ignored. There is one finding per action and distinct name, named by the action, and the message gives both spellings:

- `Flow '<flow>' action '<action>' names '<name used>' on '<entity set>', but the navigation property of table '<table>' is '<exported name>'; the Web API matches navigation property names by case.`

The rule reads the navigation properties of the solution's one-to-many relationships: each `EntityRelationship` of type `OneToMany`, from `Other/Relationships/*.xml` of an unpacked folder, from the `EntityRelationships` of a zip's `customizations.xml` and from `entityrelationships/<name>/entityrelationship.yml` of the YAML layout. Each of its two `EntityRelationshipRole` elements with a `NavigationPropertyName` gives one: role type `1` belongs to the referencing table (`ReferencingEntityName`, the table that holds the lookup) and role type `0` to the referenced table (`ReferencedEntityName`). Each table's entity set is its `EntitySetName` in the solution's tables (`Entities/<table>/Entity.xml`, the `Entities` of a zip's `customizations.xml`, or `entities/<table>/entity.yml`), matched ignoring case. The action's `entityName` must equal the entity set of a table that has such a navigation property, ignoring case, and be a literal; the rule checks only that table's properties. The names it checks are `$expand` when it is a comma list of plain names (letters, digits and `_`), spaces around the commas allowed, and the `<name>` of each `item/<name>@odata.bind` key. A name that matches an exported name exactly is fine. When two exported names match ignoring case, the first one read is named. If two properties of one table differed only by case the rule could name the wrong one; names derived from schema names are unique ignoring case, so none is expected.

Not read, so the rule says nothing about it:

- Many-to-many relationships. No export read so far has one, so how their navigation properties are exported is not known. Learn names their properties (`Entity1NavigationPropertyName`, `Entity2NavigationPropertyName`) but not how they are exported.
- A `$expand` that is more than a comma list of plain names, such as `demo_CostCentre($select=demo_name)` or a nested expand. The whole value is skipped.
- An expression or an interpolation (a value with `@`) in `entityName` or `$expand`.
- A table, or a relationship, that the solution doesn't hold. A name that matches no exported navigation property even ignoring case is never reported, because the relationship may be outside the export.
- Navigation property names in `$filter`, `$orderby` and `$select`, and in the relationship parameter of the Relate rows and Unrelate rows actions.
- Relationships exported without `EntityRelationshipRoles`, such as the system relationships (in the `alm-makers` fixture the relationships in `BusinessUnit.xml`, `Owner.xml`, `SystemUser.xml` and `Team.xml` have no roles), and a role of any other type.
- The legacy Common Data Service connector (`shared_commondataservice`) and `ApiConnection` actions, which use other parameters.
- The YAML layout with roles: its reader follows the XML element names, which the converter keeps, but the two YAML fixtures hold only system relationships, so a YAML export with roles has not been observed.

A malformed relationship file is refused with its path (exit `3`), as any malformed solution file is; so is a malformed table file once a relationship has roles.

Learn's part: that the Web API matches navigation property names by case ("Web API navigation properties" and "Use multi-table lookup columns", for the name in `@odata.bind`), that a one-to-many relationship's single-valued navigation property is its `ReferencingEntityNavigationPropertyName` and its collection-valued one its `ReferencedEntityNavigationPropertyName`, and that the connector's Expand Query takes navigation property names ("Use lists of rows in flows"). Observed in exports, not documented: that a flow's lookup input is the parameter key `item/<navigation property>@odata.bind` (Learn shows only the value, `entityset(id)`); that `RelationshipRoleType` `1` holds the referencing table's navigation property and `0` the referenced table's (in all 8 relationships with roles in the `alm-makers` fixture the role `1` name equals `ReferencingAttributeName`; in the 3 of `polymorphiclookupexamplesolution.zip`, a multi-table lookup, it is `<attribute>_<referenced table>`); and that the connector passes the name on unchanged: Learn doesn't say it, and the 1.0 trial saw a wrong-case name fail through the connector. The fixture `flow-navigation` has the action shapes and the exported case.

## Why it matters

The Web API matches navigation property names by case. A flow that names `demo_costcentre` where the table's navigation property is `demo_CostCentre` fails in the environment, while a flow test passes, because a test's mock echoes whatever name the flow sends.

## How to fix

Write the navigation property name exactly as the table's relationship defines it, in the same case.
