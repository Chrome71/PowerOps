# PO034: Security role can create or write a table that no component in the solution uses

Severity: warning

## What it finds

A security role in the solution with Create or Write on a table that no component in the solution uses. There is one finding per role and table, named by the role's name, and the message names Create, Write, or Create and Write:

- `Role '<role>' has <Create, Write or Create and Write> on '<table>', which no component in the solution uses, so it may grant more than the solution needs.`

A table is used when, ignoring case, it is the schema name of a table root component, or of a table that the manifest lists as required in its missing dependencies, or one of a canvas or code app's `CdsDependencies` tables, or when its name appears in a workflow's definition text (a cloud flow names a table by its entity set name or its logical name, which both hold the table name). Matching text can only make the rule quieter. `UserEntityUISettings` is never reported: "Create or edit a security role to manage access" lists Create, Read and Write on User Entity UI Settings among the minimum privileges, and the privilege names (`prvCreateUserEntityUISettings` and the others) follow the `prv<verb><table>` pattern that "Verifying access in code" gives; Learn doesn't print them. Roles whose id is a documented role template are skipped, as in [PO033](PO033.md). Read, Delete and the other verbs are not reported. The message says "may": Create and Write on `SharePointData`, the role editor's defaults, is expected on most roles made in the editor, and whether a role's users need it is for the maker to say. App Opener's privileges were not read, so a role copied from it may still give findings on system tables.

PowerOps doesn't read plugin code, classic workflows, agents or canvas apps without readable `CdsDependencies` for the tables they use. When the role has tables left over and the solution holds a plugin assembly, a canvas app with no readable `CdsDependencies`, a workflow with no readable definition, or a Copilot Studio agent (the first of these, in that order), the findings are replaced by one `note:` line per role on stderr, and the exit code doesn't change: `PO034 not checked for role '<role>': <n> of the tables it can create or write are used by no component PowerOps reads, and the solution holds <a plugin assembly | a canvas app with no readable CdsDependencies | a workflow with no readable definition | a Copilot Studio agent>, whose table use isn't read.` A role file with no `RolePrivileges` element gives PO033's note, which names both rules.

The rule reads `Roles/<name>.xml` in an unpacked folder, and the `Role` elements of a zip's `customizations.xml`; it does not read the YAML layout. Where a system table's privilege name differs from its logical name (`prvReadUser` for `systemuser`), the rule can give a false finding on that table if the solution carries it as a root component. No export read so far does.

Learn's part: that a security role holds privileges on tables, the minimum privileges it lists for common tasks, and that a table privilege's name is `prv` plus verb plus the table's schema name ("Verifying access in code"). Observed in exports, not documented: that a role made in the role editor can carry Create and Write on `SharePointData` with no component that uses it (the fixture `equipment-checkout`).

## Why it matters

Learn lists the minimum privileges a role needs for common tasks, and Create or Write on a table that nothing in the solution uses is not among them. Such a role may grant more than the solution needs.

## How to fix

Check whether the role's users need to create or write that table, and remove those privileges from the role if they don't.

## Suppress

To accept the finding for now, run `powerops baseline` and use `powerops analyze --baseline powerops-baseline.json`. A baselined finding is matched on solution, rule, component and message.
