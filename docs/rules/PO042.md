# PO042: Flow reads or sends a secret without secure inputs or outputs

Severity: warning

## What it finds

An action of a cloud flow, at any depth, in one of two cases. There is one finding per action, naming the flow and the action.

- The action reads a secret and its secure outputs are off. A secret read is a Microsoft Dataverse action (`apiId` ending in `/shared_commondataserviceforapps`) whose operation is `PerformUnboundAction` or `PerformUnboundActionWithOrganization` with the literal `actionName` `RetrieveEnvironmentVariableSecretValue`, or an Azure Key Vault action (`apiId` ending in `/shared_keyvault`) whose operation is `GetSecret` or `GetSecretVersion`. Everything is compared ignoring case.
- The action is of type `Http` or `HttpWebhook`, it has an `authentication` block (an object or an expression string; for `HttpWebhook`, in `subscribe` or `unsubscribe`) and its secure inputs are off. The rule states only that the block exists and secure inputs are off: it does not read the block's type or values.

Secure inputs and outputs are the strings `inputs` and `outputs` in `runtimeConfiguration.secureData.properties`. The key is documented for Azure Logic Apps and observed in exported cloud flows; no Power Automate page shows the JSON.

What it leaves alone, as not checked: other ways to read a secret (the Key Vault `DecryptData` actions, custom connectors, legacy `ApiConnection` Key Vault actions that have no `operationId`, the output of a child flow); an `authentication` property on any other action type, such as a connector action; and triggers, because an `Http` or `HttpWebhook` trigger is not read. A Key Vault action's `apiId` is inferred: the connector id `shared_keyvault` is not on Learn, it is observed as the connector id of a connection reference in a public export (`pnp/powerplatform-samples`, `samples/varify-bot/sourcecode/VARify/src/Other/Customizations.xml`), and an action's `apiId` equals its connector's id in every connector of the `alm-makers` fixture. A wrong inference costs a missed finding, never a false one.

An `Http` action whose `authentication` block uses a managed identity holds no secret, and the rule still reports it, because it does not read the authentication type.

## Why it matters

Secure inputs and outputs keep an action's data out of the run history. Microsoft's walkthrough for Key Vault secrets in environment variables turns on secure outputs on the action that reads the secret and secure inputs on the HTTP action that sends it (steps 9 and 15). The Key Vault connector reference says the outputs of Get secret and Get secret version can be visible in the run history.

The Azure Logic Apps page on secure data records two statements: an `Authorization` header is not shown by default, and an action that uses secured outputs as its inputs has its inputs hidden. Learn does not state whether Power Automate's run history shows the fields of an `authentication` object, so the second message says only what the export shows.

That is also why the rule has a known false-positive class: an `Http` action whose credentials come only from a secret read with secure outputs on may already have its inputs hidden, and the rule still fires there, because the walkthrough turns on the HTTP action's secure inputs as well and the rule cannot tell what an expression reads. Accept such a finding with `powerops baseline`.

## How to fix

Turn on secure outputs on every action that reads a secret, and secure inputs on every action that sends one.

## Suppress

To accept the finding for now, run `powerops baseline` and use `powerops analyze --baseline powerops-baseline.json`. A baselined finding is matched on solution, rule, component and message.
