# Command reference

Every `powerops` command with its options, output and exit codes. Install PowerOps first: [Install](../README.md#install).

## Usage

```sh
powerops analyze                      # find solutions under . (unpacked XML folders and exported .zip files)
powerops analyze path/to/solution.zip path/to/unpacked --format json --out report.json
powerops rules                        # list every rule with its severity, title and fix (add --json for machine output)
powerops diff old.zip new.zip         # compare two versions component by component (zip or unpacked folder; --format text|json|markdown, --out <file>)
powerops test path/to/solution --tests tests/flows   # run offline flow tests (*.flowtest.json) against the cloud flows, with mocked connector actions (--format text|json|markdown, --out <file>)
powerops settings generate path/to/solution --out deploymentsettings.json   # pac deployment settings with empty values to fill in
powerops settings validate path/to/solution --settings deploymentsettings.json   # missing or extra entries, empty connection ids and values
powerops settings apply solution.zip --settings deploymentsettings.json   # dry run: the target, the pac command, each cloud flow new or existing
powerops settings apply solution.zip --settings deploymentsettings.json --apply --target "Contoso Dev"   # import through pac, then check the flows are on
powerops drift --solution MySolution --env <dev> --env <test>   # compare one solution across environments or saved snapshot files (--save <dir>, --format text|json|markdown, --out <file>)
powerops drift --solution MySolution --env <dev> --env <test> --save snapshots/   # the same, and write snapshots/MySolution.<environment name>.json for each environment
powerops drift --solution MySolution --env "snapshots/MySolution.Contoso Dev.json" --env "snapshots/MySolution.Contoso Test.json"   # compare saved snapshots, offline
powerops deploy plan exports/ --target <test>   # what importing the solution zips in exports/ would do to the target: order, install, upgrade or skip, deletions, layers, settings, flow states (reads the target only)
powerops deploy plan exports/ --target <test> --save exports/powerops-plan.json --format markdown --out plan.md   # the same, with the Markdown for a PR and the plan file from one read
powerops deploy apply exports/powerops-plan.json --target <test>   # dry run: plan again against the target, refuse if it differs from the reviewed plan, say what would be imported
powerops deploy apply exports/powerops-plan.json --target <test> --apply   # import the reviewed plan through pac, then check each cloud flow
powerops deploy gate exports/powerops-plan.json   # a PreToolUse hook: reads the hook's JSON on stdin; exit 0 allows the call, exit 2 blocks it and says why on stderr
powerops baseline                     # accept today's findings: writes powerops-baseline.json
powerops analyze --baseline powerops-baseline.json   # report only findings that are not in the baseline
powerops mcp                          # run an MCP server over stdio for agents: its tools run the commands above and return their JSON
```

### Writing files

Every file PowerOps writes (`--out`, `--save`, the baseline file, the plan that `plan sign-off` edits, the skill files of `skills install`) goes through one rule. A target that is a symbolic link is refused with exit `2` and an `error:` line, before the command does its work, and the file behind the link is not touched; for `skills install` that includes a link at a skill file or at a folder on the way down from the repo folder (the repo folder itself may be a link), so `.agents/skills` as a link to `.claude/skills` is refused too. A target that is a file the command was given as an input is refused the same way: an `analyze` or `baseline` zip, `--baseline`, the two solutions of `diff`, the path of `test`, the solution of `settings generate`, an `--env` snapshot file of `drift`, the plan file of `deploy apply`. The files a scan found count too: the zips and `solution.yml` files that `analyze`, `baseline`, `diff` and `test` found under a folder, the `*.flowtest.json` files `test` found, and the zips and settings files in the folder of `deploy plan` or beside the plan file of `deploy apply`; each command lists them before the refusal, which stays before its work and before any read of a tenant. The files a reader opens inside an unpacked solution folder do not count, so a report can still be written into the folder it scanned, as the Action does with `powerops-plan.json`. `plan sign-off` through a linked `plan.md` exits `3`, as it does for a linked plan it reads. A target is taken as .NET takes every path on every OS: `..` is collapsed first, so `--out dl/../x.json` with `dl` a link to `sub/deep` names the `x.json` beside `dl` (a shell would name `sub/x.json`), which is also the file the commands' readers open for that spelling; then it is resolved once through every link on the way, one name at a time as `realpath` does (a `..` inside a link's target is taken in the link's target), and that one path is checked and written. Each input is taken the same way and the results are compared, with case ignored on Windows and macOS. A link loop, or more than 40 links on the way, at the target or at a named input is refused with exit `2`. So `--out /proc/self/cwd/in.zip` and `--out self/in.zip` with `self` a link to `.` are refused when `in.zip` is an input. It does not see 8.3 names, `\\?\` paths or Unicode normalization, and a link swapped in after the check needs write access to the folder. An empty name or an existing folder as the target is refused with exit `2` too, and `deploy apply --out` checks before any import that a file can be created in its folder (a device such as `/dev/null` is written in place, so it skips that check), so the report of imports that ran is not lost to a read-only folder. A regular file is written to a temp file in its folder (`.powerops-<hex>.tmp`) and moved over the target, so a crash leaves the old file whole, and an existing file keeps its Unix mode (its owner, ACL, extended attributes and hard-link count are not kept). A regular file whose length cannot be set (a filesystem that refuses it) is not written in place: the write exits `3`. A killed process can leave the temp file behind. `/dev/null`, `/dev/stdout`, `/dev/stderr`, `NUL` on Windows and a pipe (FIFO) named by its own path are written in place, as before; a link to a device or a pipe is refused like any link, so name the device itself. Known limits, each now exit `3` where an in-place write worked: a single file bind-mounted into a container as `--out`, a folder that allows writing the file but not creating a file, and a sticky world-writable folder such as `/tmp` where a rename over another user's file is refused. The MCP `deploy_plan` `save` is the exception: it refuses a file or a link that exists.

## analyze and baseline

`analyze` is offline and read-only. Options: `--format text|json|sarif|markdown` (default `text`), `--out <file>` (write the report to a file instead of stdout), `--fail-on error|warning|none` (default `error`), `--baseline <file>` (drop findings listed in a baseline file before reporting and before the exit code; the summary counts them as `baselined`). It reads unpacked XML folders (`Other/Solution.xml`), exported zips and the YAML layout that Dataverse Git integration commits: point it at the folder that holds `solutions/`, and each `solutions/<name>/solution.yml` is reported as its own solution, with its components picked by its `solutioncomponents.yml`. Canvas app `.pa.yaml` formulas are read only in the YAML layout (PO014). In a scanned folder, a `*.zip` that starts with the zip signature but can't be opened, or that can't be read at all, exits `3` and names the file; a readable `*.zip` without the signature (a Git LFS pointer, an empty placeholder) or with no `solution.xml` is skipped, and so is a file that vanishes during the scan. A zip with two entries of the same name, and a flow file with a duplicate JSON key, are refused (exit `3`). Every finding carries a one-line `fix` and a `helpUri` to its docs page in JSON and Markdown output, and SARIF rules carry the fix as `help`. Every JSON output carries a `schemaVersion`; the schemas are in [docs/schemas/](schemas/).

`baseline [path...] [--out <file>]` runs the same analysis and writes the findings it found to a JSON file (default `powerops-baseline.json`). A finding matches the baseline on solution unique name, rule id, component and message, not on file, so a baseline made from an exported zip also works for the unpacked folder. An unreadable or invalid baseline file is a usage error (exit `2`).

Exit codes: `0` no findings at or above `--fail-on`, `1` findings at or above it, `2` usage error (bad option, missing path, no solutions found), `3` unreadable solution or internal error (set `POWEROPS_DEBUG=1` for a stack trace).

## diff

`diff <old> <new>` is offline and read-only. It loads both solutions and compares the solution unique name, version, managed flag and publisher, root components, missing dependencies, connection references, environment variables, flows and canvas apps. File paths, ordering, flow JSON key order and whitespace, and XML whitespace in canvas app metadata are not differences, so a folder and its exported zip compare equal. Classic workflows and business rules are compared by name, category and state only (their XAML is not read), and components it does not read yet (tables, views, forms and so on) are not compared. Environment variable current values are reported as changed, added or removed but never printed. A canvas app whose `AppVersion` timestamp changed is reported as republished, since an edit changes the app package and the timestamp. Some changes carry a risk label: `removed-component` (a managed upgrade deletes components that are no longer in the new version, [per Microsoft Learn](https://learn.microsoft.com/en-us/power-platform/alm/solution-concepts-alm)), `flow-state` (a cloud flow was turned on or off), `connection-reference` and `environment-variable` (added or removed). Options: `--format text|json|markdown` (default `text`) and `--out <file>`. Markdown is cut at a whole row below 60,000 characters, with a note on how many changes were left out, so it fits in a pull request comment. JSON follows [docs/schemas/diff.schema.json](schemas/diff.schema.json). Exit codes: `0` no differences, `1` differences found, `2` usage error (bad option, missing path, or a folder that holds several solutions: pass one of them), `3` unreadable solution or internal error (set `POWEROPS_DEBUG=1` for a stack trace).

## settings generate and settings validate

`settings generate <solution> [--out <file>]` prints a `deploymentsettings.json` with the solution's environment variables and connection references, sorted by name, with empty `Value` and `ConnectionId` to fill in (stdout, or a file with `--out`). `settings validate <solution> --settings <file> [--format text|json]` reports entries missing from the file, entries not in the solution, names listed more than once, connection references without a `ConnectionId`, environment variables with no value in the file and no default or current value in the solution, and any `"Value": ""`, which `pac solution import` rejects. To keep a variable's default or current value, leave its entry out of the file (observed with `pac` 2.13.1); `settings generate` writes every variable with an empty value, so fill each one in or remove it. Fields the solution does not need (the extras `pac` writes) are ignored. Exit codes: `0` clean, `1` problems, `2` usage error, `3` unreadable solution or invalid settings file.

## settings apply

`settings apply <zip> --settings <file> [--apply --target <name>] [--format text|json]` deploys an exported solution zip with a deployment settings file through `pac`. Without `--apply` it is a dry run that writes nothing: it runs `settings validate`, reads pac's current environment with `pac org who`, reads each cloud flow's state there with `pac power-automate list-cloud-flows`, and prints the target environment name, whether the zip is managed, the `pac solution import` arguments (the environment id shows as `<environment id>`) and each flow as `new` (with the state the import should give it) or `exists` (with its state, which the import keeps). `--apply --target <name>` imports into the pac profile's current environment, and only when `<name>` equals that environment's friendly name; every later `pac` call is pinned to that environment's id, which is never printed. Friendly names are not unique, so check the profile with `pac auth list` before saying yes to a target. The import is `pac solution import --environment <id> --path <zip> --settings-file <file>` with pac's defaults: unmanaged customisations are not overwritten, changes are not published and there is no upgrade, so components removed from the solution stay in the target. Afterwards each flow is reported `on`, `off`, `suspended` (for example, a data policy blocks it) or `missing`. `pac` cannot turn a flow on, so powerops does not either: a new flow comes back in its export state (on only if it was on at export and its connection references get connections), an existing flow keeps its state, and a flow stays off when the importing user does not own or have access to every connection it uses (`ConnectionAuthorizationFailed`). A solution with a flow that was off at export therefore always exits `1`; that is by design, because the command checks that the flows are on. A user who cannot list flows sees every flow as `new` before and `missing` after. The import turns the solution's flows off and on again while it runs, so a running flow is briefly interrupted. It can take up to an hour (powerops waits 60 minutes): run it in the background or with a long command timeout; stopping powerops does not stop an import already running in the environment. The flow check makes two `pac` reads per flow, and a read slower than 30 seconds ends the run with exit `3`. There is no rollback: on a failure, fix the cause and run again. When the import fails, the report holds pac's exit code and pac's own output goes to stderr. In text mode with `--apply`, the first line is the target environment, printed before the import starts; with `--format json` that line goes to stderr and the report ([docs/schemas/settings-apply.schema.json](schemas/settings-apply.schema.json)) is written at the end. Exit codes: `0` dry run done or every flow on, `1` validate problems or a flow not on, `2` usage error (bad option, path not found, a folder instead of a zip, `--apply` without `--target` or the reverse, or a `--target` that does not match), `3` `pac` not found, not signed in, a failed or timed-out import, `pac` output it cannot read, or an unreadable solution or settings file.

Agents: run the dry run first and show the user the target line; run `--apply --target <name>` only after the user says yes to that environment, and never against an environment the user did not name.

## drift

`drift --solution <name> --env <env or file> --env <env or file> [--env ...] [--save <dir>] [--format text|json|markdown] [--out <file>]` compares one solution across two or more environments and reports where they differ. It compares the version, the components, unmanaged layers on a managed solution's components, environment variable values, connection reference connectors and bindings, and cloud flow states. Each environment is compared with the first. Output names an environment by its position (`1`, `2`, ...) and its friendly name, because friendly names are not unique. An `--env` is an environment (an id or URL, as `pac` takes it) or a snapshot file (a path that ends in `.json`, or an existing file), so live and saved environments can be mixed. A value with a `/` or `\` that is neither a URL nor an existing file is refused, because it would reach `pac` as an environment name; give the environment's id or URL. `--save <dir>` writes `<solution>.<environment name>.json` for each live environment, after every read has succeeded. It creates the folder, overwrites a file of the same name, and replaces every character outside letters, digits, `-`, `_`, `.` and space in the name with `-`. Snapshot files you pass in are not written again. A later run can compare the saved files offline.

Each difference is an item with a kind. These kinds are drift and make the exit code `1`: `solution-missing` (installed in one environment of a pair and not the other; nothing else is compared for that pair), `version`, `component-missing`, `component-extra`, `unmanaged-layer`, `variable-missing`, `variable-value`, `reference-missing`, `reference-connector`, `reference-unbound`, `flow-missing` and `flow-state`. Two kinds are information only and are marked `(info)`: `managed` (the managed flags differ; Dev unmanaged and Test managed is the normal route) and `layers-not-read`. A flow that is off in every environment is not drift. A flow, variable or reference that is missing is reported once under its own kind, not again as a component. Tables (type 1), canvas apps (300), model-driven apps (80) with their sitemaps (62) and app settings (10087), environment variables (380 and 381) and connection references get new ids when they are imported, so they are compared by name through their own kinds or not at all, and only other components are compared by id. `unmanaged-layer` and `reference-unbound` are checked in every environment, the first one included. Connection ids are not compared, because a connection belongs to one environment. Default values of environment variables are not compared either. A variable whose value differs by design makes every run exit `1`, and there is no option to accept it; with JSON output, filter `items` by `kind`.

Values are never printed. A snapshot file holds a SHA-256 of each variable's current value, never the value. A hash hides a value from a reader, but not from someone who guesses a short or known value, so keep reports and snapshot files in private folders and private CI artifacts. Friendly names are printed and saved, which is another reason. `layers not read` appears for a managed solution whose layer reads were skipped (see the cost below).

`drift` only reads. For each live environment it runs `pac org who --environment <env>` for the friendly name and the environment URL, asks `az account get-access-token` for a token for that URL, then sends Web API GET requests with FetchXML. It does not parse `pac env fetch`, because Microsoft Learn documents no output format for it. The token is held in memory and sent only in the `Authorization` header. It is never printed or saved, and neither is the URL. powerops sends the token only to documented Dataverse hosts (`*.dynamics.com`, `*.crm.microsoftdynamics.us`, `*.crm.appsplatform.us`, `*.crm.dynamics.cn`); an environment URL on any other host exits `2` before a token is requested. Prerequisites: `pac` signed in (`pac auth create`), and the Azure CLI on `PATH` and signed in with `az login`. If `az` is installed elsewhere, add its folder to `PATH`, for example `fish_add_path <folder>` or your shell's equivalent. The two sign-ins can be different accounts: `pac org who` runs as the pac profile, and the rows are read as the `az` account. An environment in a different tenant from the `az` sign-in is not supported. The reading account needs to be able to read the solution, solution component, workflow, environment variable and connection reference tables; the minimum security role was not tested. In CI, `drift` needs an `az` sign-in beside `pac`'s.

Each live environment costs one `pac` call, one `az` call and five Web API reads, each with a 30 second limit. For a managed solution it also makes one layer read per component that is a table, flow, canvas app, environment variable definition or connection reference (the layer table takes one component per query; about 0.4 s each in the capture), to find unmanaged layers; other component types are not checked for layers. More than 50 such components skip the layer reads, and the report says `layers-not-read`. A read returns one page of at most 5,000 rows; more than that exits `3`. When a call fails, the message names the `--env` by position and the read. Text forwarded from `pac`, `az` or the Web API goes to stderr only, never to the report or a file, and may repeat an `--env` value or the environment URL. Tested with `pac` 2.13.1 and Azure CLI 2.90.0 on Linux, live on 2026-10-22 against an unmanaged developer environment and a managed install in a trial environment, with an account that holds the System Administrator role there; the minimum role for the reads was not tested, and Windows is not tested. JSON follows [docs/schemas/drift.schema.json](schemas/drift.schema.json), and snapshot files follow [docs/schemas/snapshot.schema.json](schemas/snapshot.schema.json). Exit codes: `0` no drift, `1` drift, `2` usage error (no `--solution` or a name that is not a solution unique name, fewer than two `--env`, an `--env` ending in `.json` with no file, an `--env` with a path separator that is neither a URL nor an existing file, `--save` naming a file or used with no live environment, a snapshot for another solution, two environments that would be saved to the same file name, a solution installed in none of the environments, or an environment URL on a host that is not a documented Dataverse host), `3` a `pac` or `az` call or a Web API read failed, timed out or returned output it cannot read, `pac` or `az` not found, or an unreadable snapshot file.

Agents: run `drift` only against environments the user named in the session.

## deploy plan

`deploy plan <folder> --target <environment> [--save <plan file>] [--format text|json|markdown] [--out <file>]` says, before anything is imported, what importing the exported solution zips in `<folder>` into the target would do. It reads the target and writes nothing to it; its only file writes are `--out` and `--save`. Every file directly in the folder (not in subfolders) whose name ends in `.zip`, in any case, is one solution. Beside a zip, `<zip name without .zip>.settings.json` (the exact name, at most 1 MB) is its deployment settings file in `pac`'s format, as in `settings validate`. A zip or settings file name may hold only letters, digits, `.`, `_` and `-`. `--target` is an environment (an id or URL, as `pac` takes it and as `drift`'s `--env`); it is never printed, and the report names the target by its friendly name. The target is read the way `drift` reads it (one `pac org who`, one `az` token and the same Web API reads for each solution in the folder; for each other solution a zip depends on, only whether it is installed and its version), so the same limits apply: documented Dataverse hosts only, 5,000 rows per read, and text forwarded from `pac`, `az` and the Web API goes to stderr only.

The plan lists the solutions in import order: a topological sort on each zip's dependencies on the other zips in the folder (from its `<MissingDependencies>`; ties in name order). Each solution gets an action: `install` (not installed in the target), `upgrade` (the zip's version is higher) or `skip` (the same or a lower version, as `pac solution import --skip-lower-version`). Versions must have four numeric parts. For an install or upgrade it checks the settings file with `settings validate`; a zip with no settings file is checked as if the file were `{}`, so a connection reference, or a variable with no default or current value, is a problem, because `pac solution import` binds references only from a settings file. It also checks the dependencies and gives each cloud flow's expected state after the import (`settings apply`'s prediction, against the flow's state in the target). Every finding is an item with a kind and a severity. These block the plan (exit `1`): `cycle` (a dependency cycle among the zips), `missing-dependency` (a required solution that is neither installed in the target nor earlier in the order), `managed-conflict` (a managed zip over an unmanaged install, or the other way round, for any action) and `settings`. These are warnings: `dependency-not-checked` (a `<Required>` that names no solution), `deletes` and `unmanaged-layer`. These are information: `layers-not-read` and `components-not-checked`. The deletion check applies to the upgrade of a managed zip. It names the cloud flows, environment variables and connection references of the target's solution that the zip no longer has, which the upgrade deletes. Tables and canvas apps are compared by count only, because the target names them by id: when the target's solution holds more of them than the zip's root components, one item says the upgrade deletes at least that many (a deleted table loses its data). Other component types are counted and listed as not checked, so their deletion is not checked. `unmanaged-layer` names components of a managed target solution that have an unmanaged layer, which the import does not override; layers appear only when the target snapshot holds them, and the live read does not read them yet, so a live plan says `layers-not-read`. A block is a rule of the plan, not of `pac`: when one is wrong for your case, fix the input, or import with `pac` directly, outside PowerOps. The plan has no waiver.

The plan has a hash (SHA-256, lowercase hex) over its inputs: the target's environment id, each zip's bytes, each settings file's bytes (a change of line ending is a change), the target snapshot of each solution in the folder, and the installed version of each dependency read from the target. The same inputs give the same hash. The hash covers the inputs, not the findings. `--save <file>` writes the JSON report to a file whatever `--format` is, so one run gives the Markdown for the PR and the plan file. The plan file holds the tool version (`tool`), the hash, the target's friendly name, and `inputs`: for each zip the SHA-256 of the zip, of its settings file and of the target snapshot, and the dependency versions, so a later step can say which input changed. It holds no environment id or URL, no folder path, no connection id and no variable value. The Markdown report stops at whole rows before 60,000 characters and says how many rows it left out. JSON follows [docs/schemas/deploy-plan.schema.json](schemas/deploy-plan.schema.json). Exit codes: `0` plan ok, `1` blocked (the report and the plan file are still written), `2` usage error (no folder, no zip, a file name outside the rule, a symbolic link, two zips with the same unique name, a settings file with no zip of that exact name, no `--target`, an `--out` or `--save` that names a folder, or a URL on a host that is not a documented Dataverse host), `3` an unreadable zip, settings file, version or flow id, a failed, timed-out or unreadable `pac`, `az` or Web API read, or `pac` or `az` not found.

Agents: run `deploy plan` only against environments the user named in the session, and show the user the plan before asking for approval.

## deploy apply

`deploy apply <plan file> --target <environment> [--apply] [--format text|json] [--out <file>]` imports a reviewed plan. The plan file is the one `deploy plan --save` wrote; its folder is the deploy folder, so the zips and settings files are read from there. Without `--apply` it is a dry run that writes nothing. It refuses before reading the target when the plan file is blocked or was made by another powerops version (exit `1`). Then it plans again against the target with `deploy plan`'s code, and exits `2` when the target's friendly name is not the plan's, and refuses (exit `1`, nothing imported) when the new plan's hash differs from the file's, naming the first input that changed, or when the new plan is blocked. Otherwise the dry run lists what it would import, and with `--apply` it runs `pac solution import` for each `install` or `upgrade` in plan order (`--settings-file` when the zip has one, `--stage-and-upgrade` for the upgrade of a managed zip), hashing each file again just before its import. It stops at the first failed import and names the solutions already imported: there is no rollback. An import that times out leaves its row `unknown` (it may have finished or still be running, so check the solution's import history in the environment) and still exits `3`. Afterwards it reads the target again and reports each planned cloud flow's state; exit `1` when a flow is not in the state the plan expected. The target's id, its URL, connection ids, setting values and `pac`'s own text never reach the report; `pac`'s output goes to stderr with every line prefixed `  | `. JSON follows [docs/schemas/deploy-apply.schema.json](schemas/deploy-apply.schema.json). Exit codes: `0` applied (or a dry run that would apply), `1` refused or a flow not as expected, `2` usage error or a `--target` mismatch, `3` an unreadable plan file, zip or settings file, a failed `pac`, `az` or Web API call, a file changed before its import, or a failed import.

Agents: run `deploy apply` without `--apply` freely against an environment the user named; run `deploy apply --apply`, or the MCP tool `deploy_apply` with `apply: true`, only after the user said yes to that environment in the session. The tool then asks the user to type the environment's name in a form and imports only after that.

## deploy gate

`deploy gate <plan file>` is the command that a `PreToolUse` hook of Claude Code or Codex runs before Microsoft's import tools. It reads the hook's JSON on stdin (UTF-8, at most 1 MB), writes nothing to stdout, and exits `0` or `2` only, because a hook blocks only on `2`. It never imports anything and never writes a file. A call that is not an import (any tool but `Bash`, `Monitor`, `PowerShell` and an MCP tool named `mcp__<server>__solution_import`, and a shell command with no import in it) exits `0` without reading the plan or the target.

For an import it allows the call only when all of these hold:

- the call is pac's MCP `solution_import`, or one plain `pac solution import` in a Bash command, with a literal absolute `--path`, an `--environment` that is an id or the https URL of a Dataverse host (no user info, port or path), and optionally `--settings-file` and `--stage-and-upgrade`. The options that change only how `pac` waits (`--async`, `--max-async-wait-time`) and `2>&1` are allowed; any other option, a variable, a wildcard, a relative path, a network path or any other redirection blocks. In the MCP form every argument is a string, `--async` is `"true"` or `"false"`, a path holds only letters, digits and `/ \ : . _ - ~`, and an unknown key blocks;
- the dry run of `deploy apply` passes with the call's `--environment` as `--target`: the plan file is readable, not blocked and made by this version, the target has the plan's friendly name, and the hash of the zips, settings files, target and dependencies is the plan's;
- the call's zip is the plan's first import (the same bytes), with the settings file of that step (the same bytes, or none when the step has none), and `--stage-and-upgrade` exactly when the step stages and upgrades. Both files must be regular files, and they are hashed again just before the gate allows the call: a file that changed during the dry run blocks.

Everything else blocks: another zip, a later or skipped zip, another environment (Dev when the plan is for Test), a plan of skips only, and the routes that cannot be checked: model-apps' `solution-settings.js import`, power-pages' `import-solution` and `deploy-pipeline`, create-site's template import, `pac package deploy`, `pac solution upgrade`, `pac pcf push`, `pac application install`, `pac code push`, `pac catalog install`, `pac app-management install-application-package`, `Import-CrmSolution`, any import in PowerShell, a command that holds an import the gate cannot read (`sh -c`, `eval`, a variable, or a mention such as `grep "pac solution import" docs`), and a Bash command with a `$'...'` word that holds an escape. A plan-file argument that starts with `-` blocks too. The gate blocks the import routes it knows: a new pac command that installs or imports passes until the gate gets a route for it. Each block writes `error: deploy gate: ...` lines on stderr and ends with one line that says what to do next. The environment value, folder paths and the command text are never printed. The check has a deadline of 300 seconds; past it the gate blocks. An exception blocks too, so a failure never lets a call through.

A pass shows that the call matches the plan file at the given path and the live target. It is not a record that anyone reviewed that file, and it is not the user's yes to the import. The exit codes are `0` allowed and `2` blocked, for every other outcome.

## plan and skills

Plans live in `docs/plans/<name>/plan.md`, with a header between `---` lines (`status`, `review`, `signed-off`, `signed-off-hash`, `environment`, `depth` and `supersedes`).

```sh
powerops plan status                  # check every docs/plans/*/plan.md under . (offline, read-only; add --json for machine output)
powerops plan sign-off docs/plans/site-visits   # write status, date and body hash into the header
powerops plan facts                   # environment and solution names as JSON; read-only, needs pac signed in, prints names only
powerops skills install               # copy the planning skills into .claude/skills/ and/or .agents/skills/ (--agent claude|codex|gemini|copilot, --force to overwrite)
```

`plan status` checks the header, that a signed-off plan still matches its recorded hash, that the review is done (with `review.md`) or skipped, and that no file in the plan folder holds a URL, GUID or email (add `<!-- plan-status: allow -->` to a line to allow it). `plan sign-off` refuses unless `status` is `approved`, the review is done or skipped, and the scan is clean; it edits only the header. Exit codes: `0` clean, `1` violations or a refused sign-off, `2` usage error or malformed header, `3` internal error.

Agents: run `plan facts` only when the environment `pac` is signed in to is one the user named in the session.

What the planning skills do, and how to install them as a plugin: [Planning skills](USE-WITH-AGENTS.md#planning-skills).

## mcp

`mcp` runs a Model Context Protocol server over stdio until the client closes stdin (exit `0`, or `3` on an internal error). A tool input is refused, with an `error:` line and nothing run, when a string holds a control character or an unpaired surrogate or is longer than 4,096 characters, or when `paths` has more than 50 entries or `envs` more than 10. Its tools, what they write, and how Claude Code and Codex start it: [Use from an agent (MCP)](USE-WITH-AGENTS.md#mcp-server).
