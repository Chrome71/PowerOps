Phase 3 is in [its own section](#phase-3-environment-aware-m8m11), and so are [Phase 3b](#phase-3b-works-with-microsofts-skills-and-mcp-servers-m12m13), [Phase 4](#phase-4-testing-m14m17), [Phase 5](#phase-5-agents-m18m20) and [Phase 6](#phase-6-hardening-m22m32). Last updated 2026-10-28.

## Where PowerOps fits

Teams that use Dataverse Git integration, or an export → unpack → commit workflow, **already have the unpacked solution in Git**. A pull-request check therefore needs no export, no sign-in and no secrets: just `checkout` plus one PowerOps step.

Today nothing fills that slot well:

- **Solution Checker** runs as an online service, and you can't add your own rules to it.
- **Pipelines** checks only for missing dependencies.
- **`pac solution create-settings`** generates a deployment settings file but never checks it.
- **Microsoft's model-apps skill** now writes one as well (`scripts/solution-settings.js template`, since model-apps 2.15.0) and imports with it (`import`). Its check that each filled entry names one of the package's variables or connection references runs only during that import, and it says "An entry left empty overrides nothing". Nothing in the files read checks the file offline or in CI (read at power-platform-skills `aed70bf`, 2026-10-24).
- **Existing diff tools** don't read the Git-integration YAML layout or canvas `.pa.yaml` files.

The first release therefore answers one question offline, in seconds: **"will this solution import and run cleanly?"**

## Product shape (applies to every milestone)

- **One command does the useful thing with zero configuration.** `powerops analyze` auto-detects every solution under the current folder, in all three layouts:
  - an exported `.zip`
  - an XML unpack (`Other/Solution.xml`)
  - the YAML layout (`solutions/*/solution.yml`)
- **Output formats:** text for people, `--format json|sarif|markdown` for machines, and `--out <file>`.
- **Exit codes:**

  | Code | Meaning |
  |---|---|
  | 0 | Clean |
  | 1 | Findings at or above `--fail-on` (default `error`) |
  | 2 | Usage error |
  | 3 | Internal error |

- **Suppression without a config file.** `powerops baseline` writes the current findings to a file. Pass it back with `--baseline <file>` and only new findings count.
- **Stable rule IDs** (`PO001`…), each with a docs page (`docs/rules/PO001.md`), which is also the SARIF `helpUri`.
- **Agents are the main users.** PowerOps runs inside the user's Claude Code or Codex, where agents call it. Every JSON output carries a `schemaVersion` and has a published schema; every finding says how to fix it; and agents can list the rules with `powerops rules --json` instead of reading docs (M4).
- **Read-only and offline.** It never changes the solution and makes no network calls, except `drift`'s Web API reads (below). The other exceptions go through `pac`: `powerops plan facts` (M3) reads and prints names only, and `powerops settings apply` (M7) reads the target and its flow states and imports a solution only with `--apply --target <name>`. From M8, `powerops drift` reads environments (read-only): `pac org who` gives the name and URL, and Dataverse Web API GET requests, with a token from `az`, give the solution's rows (decision 15). And `powerops deploy apply` (M10) imports only a reviewed plan with `--target <name>`.

## Architecture

```
src/PowerOps.Core/          library: no console, no network
  Model/                    Solution, Component(type, id, schemaName, files), Publisher, Dependency
  Readers/                  ZipReader, XmlUnpackReader, YamlReader → one normalized Solution model
  Flows/                    cloud-flow clientdata parser (connection refs, env-var parameters, state, child flows)
  Rules/                    IRule { Id, Severity, Title, Fix, Evaluate(Solution) → Finding* }, one file per rule
  Output/                   Text, Json, Sarif, Markdown writers
src/PowerOps.Cli/           System.CommandLine commands: analyze, baseline, plan, skills, rules (M4) (later: diff, settings); PacRunner (M3)
tests/PowerOps.Core.Tests/  unit + golden-file tests
tests/PowerOps.Cli.Tests/   end-to-end tests on the packed tool
tests/fixtures/             licensed sample solutions + NOTICE.md
docs/schemas/               JSON Schemas for every JSON output (M4)
action.yml                  composite GitHub Action at the repo root
```

**Dependencies:**
- the .NET base class library (zip, XML, JSON)
- System.CommandLine
- YamlDotNet, from milestone M5 only. The plan header (M3) is plain `key: value` lines read by a small fixed reader, not parsed as YAML.

SARIF is written by hand with System.Text.Json; the Sarif SDK is used only in tests to validate the output. The `powerops` CLI doesn't call `pac` or the Dataverse SDK until M3, and then only read-only: `powerops plan facts` (in `PowerOps.Cli`, through `PacRunner`) runs `pac org who` and `pac solution list` and prints names only. The first write through `pac` is M7's `powerops settings apply`, which runs `pac solution import --settings-file` only with `--apply --target <name>`.

## First rule set

Errors are reserved for things that break deployment. Everything else is a warning.

| ID | Rule | Severity | Milestone |
|---|---|---|---|
| PO001 | A flow uses a connection reference that isn't defined in the solution | error | M1 |
| PO002 | A required environment variable has no default and no value | error | M1 |
| PO003 | A missing dependency has no owning solution (the import will fail) | error | M1 |
| PO004 | A child flow isn't in the solution or its declared dependencies | error | M1 |
| PO005 | A connection reference isn't used by any flow or app | warning | M1 |
| PO006 | A flow contains a hard-coded environment or SharePoint URL | warning | M1 |
| PO007 | An environment variable's default looks environment-specific (URL, GUID, email) | warning | M1 |
| PO008 | An environment variable's current value is shipped inside the solution | warning | M1 |
| PO009 | Component names don't use the publisher prefix | warning | M1 |
| PO010 | The solution uses a default or auto-generated publisher (`new`, `cr###`) | warning | M1 |
| PO011 | A flow was exported turned off | warning | M1 |
| PO012 | A Dataverse "row updated" trigger has no filter columns | warning | M2 |
| PO013 | A component listed in `rootcomponents.yml` has no source folder (pac drops it silently) | error | M5 |
| PO014 | A canvas app formula in a `.pa.yaml` file contains a hard-coded environment or SharePoint site URL | warning | M5 |

Plugin-step and web-resource JavaScript rules are left out, because Solution Checker already covers them.

**What the server reads and writes.**
- The offline tools read only files, as the commands they run do. `plan_facts`, `drift` (for an environment, not a snapshot file) and `deploy_plan` read a tenant through `pac` and `az`, as the CLI does, and so does `deploy_apply` for its re-plan.
- It writes in two places only. `deploy_plan` writes the plan file into the deploy folder when the call names a new file in `save`. `deploy_apply` imports through `pac solution import` only when the call sets `apply` and the user types the target's name into the server's confirmation form (decision 26). `baseline` and `settings_generate` return the file's text instead of writing it, and `drift` has no `save`.
- It has no export, import, environment, auth or record tools, and its descriptions name none of Microsoft's (decision 16(b)). The descriptions of `deploy_plan` and `deploy_apply` say to promote a reviewed plan with `deploy_apply`, not with an import tool.

**Tools (decision 25).** Each tool turns its input into an argument list and runs the matching command in-process, through `Program.Run` with its own writers and `--format json` (or `--json`). So the result is the JSON the CLI prints, with `schemaVersion` and its schema in `docs/schemas/` (decision 24). `baseline` calls the command's own code (`AnalyzeCommand.Run` and `Baseline.Write`) with a string writer, because the command always writes a file. Every path input must be absolute, and a relative one is refused: an agent knows its workspace's path, and the folder each client starts the server in is not documented. So `analyze` has no default path. In `drift`'s `envs`, an entry that ends in `.json` is a snapshot file and so a path; any other entry is an environment, as for the CLI's `--env`.

"Read-only" means `readOnlyHint: true`, `destructiveHint: false` and `idempotentHint: true`, with `openWorldHint: false` unless the row says open world. Every tool sets all four hints, because the SDK's attribute defaults to destructive, and Codex asks before any call whose `destructiveHint` is true, even when `readOnlyHint` is true (research basis). `deploy_plan` and `deploy_apply` are not idempotent, so Claude Code doesn't retry them after a dropped connection.

**Results and errors (decision 24).**

| The command's exit code | The MCP result |
|---|---|
| 0 | `isError: false`, with one text block holding the JSON |
| 1: findings, drift, failed tests, a blocked plan, or a refused apply | The same. The JSON says what was found |
| 2: a usage error | `isError: true`, with the JSON when the command printed one, then powerops' own `error:` lines, as the Action logs them. `plan status` prints its JSON and then exits 2 for a malformed plan |
| 3: unreadable input, a failed `pac`, `az` or Web API call, or an internal error | The same as 2. `deploy apply` prints its report and exits 3 after a failed import, and the report names the solutions already imported (there is no rollback) |

Input the server refuses before any command runs is also a tool error (`isError: true`): a wrong type, a missing field, a relative path, or a string that starts with `-` or `@`. A leading `-` would be read as a flag. A leading `@` would be read as a response file, which System.CommandLine expands into arguments by default (observed with the built tool on 2026-10-27), so a file holding `--apply` would become that flag. An unknown tool or a malformed request is a JSON-RPC protocol error, which the SDK returns. There is no `outputSchema` and no `structuredContent`. The tools don't page their output: a result over a client's limit (25,000 tokens by default in Claude Code) is cut or saved to a file by the client, so an agent narrows `paths`.

**Left out.** `plan sign-off` (the user signs off after the review), `skills install` (it writes into the repo), `settings apply` (an import without a plan, decision 16(c)), `drift --save`, `--out`, and the Markdown and SARIF formats, which serve PR comments and code scanning from the CLI.

### Phase 5 research basis

- **MCP spec.** The current revision is 2026-07-28; the one before is 2025-11-25. 2026-07-28 drops the `initialize` handshake, and peers may support several revisions. A tool has `name`, `title`, `description`, `inputSchema`, `outputSchema` and `annotations`. A result has `content`, `structuredContent` and `isError`, and a tool that declares an `outputSchema` must return matching structured content. Annotation defaults: `readOnlyHint` false, `destructiveHint` true, `idempotentHint` false and `openWorldHint` true. Clients must treat annotations as untrusted unless the server is trusted. Input validation errors are tool execution errors (`isError`), so the model can correct itself (SEP-1303, 2025-11-25); an unknown tool is a protocol error. On stdio, stdout carries only MCP messages, stderr may carry logs, and the client closes stdin to stop the server. A human SHOULD be able to deny tool calls. Elicitation (form or URL mode; accept, decline or cancel; no passwords or tokens in a form) is optional for clients, and in 2026-07-28 it arrives as an input-required result during `tools/call`. The spec doesn't call it a confirmation step; using it for a yes/no is this plan's choice. Roots are deprecated in 2026-07-28. ## Phase 6: hardening (M22–M32)

The user asked on 2026-10-28 for a phase that refines and secures what Phases 0 to 5 built, and adds no feature. A read-only audit of `main` at `b4abce4` found the gaps. FOUNDATION Phase 6 is done when **every high and medium finding of the audit is fixed with a test that fails without the fix, or accepted in the plan with its reason, while the commands, options, JSON schemas and documented exit codes stay as they are**. The milestones are ranked by risk, cheapest high-value fixes first, and each is one PR. M24, M28 and M32 get a quick plan of their own before they are built; the others are built from the plan's rows (decision 30).

**Status (2026-10-28).** Planned, reviewed and signed off ([plan](plans/phase6-hardening/plan.md)); M22 is built, nothing else yet. M21 (`powerops deploy gate`) is planned in another session. **What Phase 6 reads and writes.** Nothing in a tenant: no milestone runs `--apply`, an import, or a `pac` or `az` call against an environment, and every test uses fakes. What changes is that hostile or broken input is refused where it was read, crashed or exhausted memory: a refusal is exit 2 or 3 in the CLI, or a tool error in `powerops mcp`. Two exit codes the audit found wrong follow AGENTS.md again (R-5, C-3), and a zip that can't be opened while scanning a folder exits 3 instead of being skipped (C-4, decision 33). The plan's Compatibility list names every change a CI user or an agent can see, by milestone.

**The top risks.**
- **S-1 (high, observed).** `pac` and `az` are started by bare name, and .NET looks in the current folder before PATH, so a clone with an executable `pac` or `az` at its root runs it with the user's sign-in when `powerops` or `powerops mcp` starts there.
- **I-1 (high).** The package ID `PowerOps` is unregistered on nuget.org (observed: 404 on 2026-10-28), yet the skills tell users to run `dotnet tool install --global PowerOps`, and the README's from-clone line uses `--add-source` with no version. Anyone who registers the ID would be installed (inferred).
- **A-4 (medium, observed).** SECURITY.md sends reporters to private vulnerability reporting, which is off.
- **S-2 (medium, inferred).** Between the user's yes in `deploy_apply`'s form and the import, a writer in the deploy folder can swap in another consistent plan and its zips.
- **Memory and time from small inputs (medium, observed).** A 192 KB flow takes `analyze` to about 2 GB (R-1); a 600 KB flow test hangs `powerops test` (C-2); `diff` is quadratic in canvas XML depth (R-2); a regex backtracks on a long value (R-3); `plan status` follows links into `/dev/zero` (R-7).
- **Unprotected `main` and unlocked restores (medium, observed).** No ruleset (A-1), no lock files in a build that runs in consumers' deploy jobs (A-2), and a new advisory would fail every consumer's build (A-3, inferred).

### Phase 6 research basis

Checked on 2026-10-28. Six read-only agents (Sonnet) audited `b4abce4`: readers and file inputs, MCP inputs and subprocesses (`powerops-reviewer`), the Action and supply chain, correctness and exit codes, docs drift, and the open research items (`powerops-researcher`). The readers and correctness agents ran the built CLI on crafted inputs in a scratch folder, under a 2 GB heap cap. The planning session re-ran S-1, R-1, R-5, C-4 and C-7. Each milestone rechecks the claims it builds on.

- **`pac` versions.** The release notes on the [Microsoft.PowerApps.CLI.Tool](https://www.nuget.org/packages/Microsoft.PowerApps.CLI.Tool) package pages date `solution import --stage-and-upgrade` (1.28, whose package page shows 2023-10-19) and `org fetch`, now `env fetch` (1.21.13). They don't date `--settings-file`, `solution list`, `org who` or `power-automate list-cloud-flows`, which the [power-automate reference](https://learn.microsoft.com/power-platform/developer/cli/reference/power-automate) marks preview and an admin command. 2.14.1 (2026-10-21) is the latest and notes only dependency updates. [Learn's introduction](https://learn.microsoft.com/power-platform/developer/cli/introduction) reads the installed version from the second line of a bare `pac` run, by example only. So no documented minimum exists (decision 32).
- **Empty settings entries.** [Pre-populate connection references and environment variables](https://learn.microsoft.com/power-platform/alm/conn-ref-env-variables-build-tools) shows `""` values in a generated file, calls them "missing" and says to fill them. The [pac solution reference](https://learn.microsoft.com/power-platform/developer/cli/reference/solution) describes `--settings-file` only as the file's purpose. [`ImportSolutionRequest.ComponentParameters`](https://learn.microsoft.com/dotnet/api/microsoft.crm.sdk.messages.importsolutionrequest.componentparameters) says it overwrites values from the solution, and says nothing about empty ones. Learn nowhere says that an empty entry overrides nothing.
- **Which skill wins.** [Claude Code's skills docs](https://code.claude.com/docs/en/skills) leave the choice to the model, by `description` and `when_to_use`; give a precedence only for skills of the same name; namespace plugin skills; cap each skill's listing text at 1,536 characters; and document no way to order two skills. [Codex's skills docs](https://developers.openai.com/codex/skills) select by `description`, state no precedence or ranking, cap the listing at 2% of the context, and let `allow_implicit_invocation: false` limit a skill to explicit calls.
- **Windows.** [`ProcessStartInfo.UseShellExecute`](https://learn.microsoft.com/dotnet/api/system.diagnostics.processstartinfo.useshellexecute) says that with `false` only executables start, and doesn't mention `.cmd` files. The `ArgumentList` docs promise escaping, but not escaping that is safe for `cmd.exe`. No .NET advisory for the batch-file quoting issue (CVE-2024-24576 in Rust) was found. Neither client documents starting a bare-name stdio server from a `dotnet tool` shim on Windows, and [pac auth](https://learn.microsoft.com/power-platform/developer/cli/reference/auth) says only that profiles are "stored on this computer".
- **Limits.** [Import solutions](https://learn.microsoft.com/power-apps/maker/data-platform/import-update-export-solutions) gives 95 MB as the maximum size of a solution file, without saying compressed or not. The pac solution reference gives `--max-async-wait-time` a 60-minute default and no maximum.
- Sources: [pac solution reference](https://learn.microsoft.com/power-platform/developer/cli/reference/solution), [Microsoft.PowerApps.CLI.Tool](https://www.nuget.org/packages/Microsoft.PowerApps.CLI.Tool), [Claude Code skills](https://code.claude.com/docs/en/skills), [Codex skills](https://developers.openai.com/codex/skills). verified: 2026-10-28

## Live testing runbook

This starts once M1 passes locally.

1. **Local check:**
   1. `dotnet build && dotnet test`
   2. Pack the tool and run it from a temp folder.
   3. Run `powerops analyze` on the fixtures.
2. **`pac` on this machine:**
   1. Put `~/.dotnet/tools` on PATH.
   2. Update `pac` to the current version.
   3. Run `pac auth create --name powerops-test --deviceCode` against the test environment only.
3. **Seed solution (once, in the in-app browser).** You sign in on make.powerapps.com, then create:
   - a publisher (prefix `pops`)
   - a solution
   - one table
   - one environment variable
   - one connection reference
   - a cloud flow that uses them
   - a small canvas app

   Bind the connection and turn the flow on. Claude can guide this and read the page state, but you enter all credentials.
4. **Export and analyze:**
   1. `pac solution export` (unmanaged and managed), then `pac solution unpack`.
   2. Run `powerops analyze` on the zip and on the unpacked folder.
   3. Compare the findings with what you know is in the solution.
5. **Break it on purpose:**
   1. In the browser, hard-code a URL in the flow and add an unused connection reference.
   2. Re-export.
   3. Confirm the new findings appear (and, from M6, that `powerops diff` shows exactly those changes).
6. **Keep the result:**
   1. Scrub the export (fake publisher name, no tenant URLs).
   2. Commit it as a new fixture so the live case becomes a permanent offline test.

**Guardrails:**
- Use a dedicated `powerops-test` profile and environment.
- Never touch a work tenant unless you say so.
- Tenant URLs and IDs live only in environment variables or gitignored files.

3. **Live environment:** a dedicated developer environment in a tenant where the maintainer has admin rights, used only for PowerOps testing (a sandbox needs spare tenant database capacity).
   - Developer environments that aren't managed are suspended from 2026-12-15. The seed solution is already exported and committed as the `powerops-seed` fixture, so offline tests don't depend on the environment.
4. **Planning skills come before the YAML layout.** They ship to PowerOps users as M3 (v0.4). Every later milestone is planned with them, which dogfoods them early.
5. **Planning-skills smoke test runs weekly, not per build.** The simulated-user smoke test is a scheduled job on the maintainer's model credentials, stored as CI secrets. A manual run before each release is still allowed.
6. **v0.4.0 supports Claude Code and Codex.** Gemini CLI and Copilot ship marked provisional, untested.
7. **No warn-only sign-off.** A sign-off written by hand without `powerops plan sign-off` fails `plan status` with the hint "run `powerops plan sign-off`".
8. **The agent base comes before the YAML layout and `diff` (2026-10-20).** The main users are agents in the user's Claude Code or Codex. Versioning the JSON output and adding fix hints is cheapest before the first NuGet release and before `diff` adds a new output; later rules and commands are then built to the same contract and recipes. Each milestone also rechecks the rule docs' sources with `/verify-research`, because the platform changes fast.

## Decisions, Phase 3 (2026-10-21)

9. **Environments: two environments in the maintainer's own tenant.** Dev is the existing unmanaged developer environment, suspended from 2026-12-15. Test is a new environment that expires 30 days after it was created. The first plan was a managed developer environment for Dev and a sandbox for Test, but the tenant had no Dataverse capacity for a sandbox and no developer environment was left, so the master session changed it on 2026-10-22. Phase 3's live checks must finish before Test expires (about 2026-11-21; it was created on 2026-10-22) and before 2026-12-15.
10. **Order: `drift`, then `deploy plan`, then `deploy apply`, then ephemeral environments.** Drift is read-only and the lowest risk. It also builds the snapshot reader that the plan needs. Ephemeral environments are an opt-in recipe, built as docs and not verified: no live run, by decision of the master session on 2026-10-23, and the tenant has no capacity for a sandbox. PowerOps' own CI never creates environments, because each PR's environment would cost at least 1 GB of database capacity and premium licences.
11. **The GitHub Action that comments `diff` on PRs is folded into M9, not dropped.** M9 needs a PR comment for the plan anyway. Without a target, the same comment shows the offline `diff` of the PR's base and head, which is the Phase 1 item. Until then, the action writes the analysis to the job summary, annotations and code scanning.
12. **`settings diff` is folded into `drift` (M8). The offline diff of two settings files is dropped.** Settings files are meant to differ between environments, and `settings validate` already checks each file against the solution. The useful question is whether an environment's env var values and connection bindings match what was deployed, and only a read of the environment answers it. Drift does that read.
13. **Import directly through `pac`, not through Pipelines.** Pipelines deploys one solution per run, with a fixed import mode. It needs a host environment and can't carry a plan into its gate (see the research basis). `pac pipeline deploy` can be added later as another way to apply a plan.
14. **`deploy apply` runs only a reviewed plan.** It plans again against the target and refuses on any hash mismatch, so what runs is what was reviewed in the PR.
15. **`drift` reads the solution's rows through the Dataverse Web API, with a token from `az`, not through `pac env fetch` (2026-10-21).** Microsoft Learn documents no output format for `pac env fetch`, so its text cannot be parsed against documented behaviour. The Web API's JSON, raw values, errors and paging are documented. `pac org who` still turns `--env` into the environment's name and URL, so `--env` takes what `pac` takes. A token for that URL comes from `az account get-access-token`, run as a subprocess like `pac`. No new package. The costs: the Azure CLI is a prerequisite beside `pac`, and the `az` account can differ from the pac profile. See Q6 of the [M8 plan](plans/m8-drift/plan.md).

## Decisions, Phase 3b (2026-10-24)

16. **Coexistence with Microsoft's skills and MCP servers.** PowerOps is the check-and-plan step between a Microsoft skill's build or export and the import. It doesn't build, and it doesn't replace their tools (FOUNDATION §2).
    - (a) PowerOps keeps calling the `pac` binary as a subprocess with an argument list. It doesn't wrap or call pac's MCP server (`pac copilot mcp --run`, which Learn calls "designed for local development and testing purposes"). The binary's flags and exit codes are what PowerOps is tested against.
    - (b) Amended by decisions 25 and 26 (2026-10-27): the tools also include `test`, and `deploy plan` saves only a new file in its deploy folder. The Phase 5 MCP server exposes only what `pac`, pac's MCP server and the Dataverse MCP server don't have: `analyze`, `rules`, `baseline`, `diff`, `settings generate` and `validate`, `plan status` and `facts`, `drift` and `deploy plan`. These are read-only, and they return their output instead of writing files, except that `deploy plan` can save the plan file that `deploy apply` reads, behind an explicit flag. It also exposes `deploy apply`, as a dry run unless an explicit flag is set. It leaves out export, import, environment, auth and record tools. Its tool descriptions say to promote a reviewed plan with `deploy apply`, not with an import tool. It needs neither Microsoft server and names none of their tools: the Dataverse server's tools have changed once already (Learn lists `describe_table`, `list_tables` and `fetch` as removed, and `search` renamed to `search_data`; read 2026-10-24).
    - (c) In a flow that PowerOps gates, `deploy apply` is the only import, and it needs a reviewed plan file. Microsoft's import paths (the Phase 3b conflict checks) aren't used for the same solutions in that flow, and `powerops-implement` step 7 names them and asks for a yes before any of them. `settings apply` stays the one-solution command without a plan (M10), for use outside such a flow.
    - (d) `pac` versions: PowerOps is tested with 2.13.1, and the example workflows pin 2.14.1. Microsoft's model-apps asks for `pac` newer than 2.10.0. Older builds are untested (FOUNDATION §8), and the pins stay.

## Decisions, Phase 4 (2026-10-25)

17. **Flow tests run offline, against the exported definition.** No documented API starts a cloud flow, reads a run's per-action inputs and outputs, or turns static results on or off, and run history is run-level only (research basis). No open library fits: PowerAutomateMockUp has had no release since 2022, its expression coverage is unverified and its package states no licence (it was not tried); LogicAppUnit and Microsoft's test SDK are for Logic Apps Standard, and the SDK's licence bars redistribution. So PowerOps simulates the definition itself, with only the action types and functions its fixtures use, written from Learn's references, and fails closed on anything else. The capture step checks the simulator against one real run. A command that reads `flowrun` after a deploy is not planned: those rows are run-level, and the flows would need a trigger that CI can call.
18. **Mocks take the static-result shape.** It is the shape Learn documents for mock outputs, a body copied from a run's raw outputs pastes in unchanged, and a flow's own static results can serve as its mocks.
19. **The merge gate needs no tenant.** `powerops test` runs in the Action, and the job is a required check. It needs no secrets and runs on fork PRs, so Phase 4's done-when doesn't depend on an environment.
20. **Copilot Studio evaluation goes through the Power Platform API, opt-in and labelled preview.** The API's JSON is documented, and pac's output, which carries the run id, is not. Decision 15 used that reason for reads; here it also covers one write, starting a run, which `pac copilot-studio run-maker-evaluation-test-set` could do. That is an exception to the AGENTS.md rule to call `pac` and not reimplement it, and the M17 plan updates that rule if it keeps this route. The token comes from `az`. Whether CI can run it as an application identity is settled by the eval capture (build-order item 36), not assumed.
21. **The Playwright starter is an example with no CI sign-in.** It follows Microsoft's samples with `@playwright/test` only (and TypeScript for the type check), uses Playwright's own saved sign-in, and doesn't copy their toolkit. A CI run would need a stored password or certificate for a user, which FOUNDATION §4 rules out.
22. **Environments for Phase 4: open, the user's choice.** The options are A (a new trial), B (the user's own managed developer environment) and C (saved data only), in the Phase 4 section. The recommendation is C with the one extension of Test. The user answers by about 2026-11-14, when the extension is first offered. Until then, M14's capture step and the live checks of M16 and M17 are planned for 2026-11-21, which works with every option. M17's is on hold since 2026-10-27 (Phase 4 status).

## Decisions, Phase 5 (2026-10-27)

23. **`powerops mcp` is a subcommand of the existing tool, stdio only, on `ModelContextProtocol.Core`.** One install gives the CLI and the server at one version, and the plugins run the command from PATH; a separate project would be a second tool package to install and keep in step. Both agents start local servers over stdio; HTTP would add a listener and its sign-in for no user. The SDK is licensed Apache-2.0 (with MIT parts), stable since 1.0.0, and its net10.0 dependencies are MIT, so hand-written JSON-RPC is not needed. The SDK also follows the spec's revisions, such as 2026-07-28, which removed the `initialize` handshake; hand-written code would have to track that itself. Core rather than the main package leaves out the Generic Host and dependency injection, with three dependencies instead of ten, if Core alone can host a stdio server; that is unverified until M18's spike, and the main package (all MIT) is the fallback. The server goes in `PowerOps.Cli`, not in `PowerOps.Core`, which stays without a console or a network. FOUNDATION §4 already calls for a thin server over the core.
24. **The tools run the CLI's commands in-process and return their JSON as text.** The output contract already exists (`schemaVersion`, the schemas in `docs/schemas/` and the goldens), so a tool's result is the CLI's `--format json` output, byte for byte, and the same tests cover both. There is no `outputSchema`: with one, the spec requires matching `structuredContent`, the schemas would go into `tools/list`, which agents load into their context, and Claude Code's handling of `structuredContent` beside text is not documented. Exit codes 0 and 1 are results, because 1 is the answer (findings, drift, a blocked plan) and the JSON says which. Exit codes 2 and 3 are tool errors (`isError`), and so is invalid input, so the model can fix its call (SEP-1303). A value that starts with `-` or `@` is refused, and so is a relative path, so tool input never becomes a flag or a response file and never depends on where a client starts the server.
25. **The tools are decision 16(b)'s list plus `test`.** `powerops test` (M14) came after decision 16(b). It is offline and read-only, neither pac nor Dataverse has anything like it, and the hand-off page's step 4 runs it. Left out: `plan sign-off` (the user signs off after the review), `skills install` (it writes into the repo), `settings apply` (an import without a plan, decision 16(c)), `drift --save`, `--out`, and the Markdown and SARIF formats, which serve PR comments and code scanning from the CLI. This amends decision 16(b) and the FOUNDATION Phase 5 row.
26. **The server writes only for an explicit input, and imports only after the user types the target's name.** `deploy_plan` writes the plan file only when `save` names a new file in the deploy folder, never over an existing one. `deploy_apply` is a dry run unless `apply` is true. Then the server asks through an elicitation form, which the client shows to the user, not to the model, and only the plan file's target name, typed exactly, imports. Annotations are hints that clients must not trust from unknown servers, so they decide only when a client asks first (the Phase 5 tools table); the form is the gate. A client without elicitation gets a refusal and the CLI command to run. This fits the AGENTS.md rule that `--apply` needs the user's yes to that environment in the session: the form asks for that yes in the call itself, an agent still asks in chat before it sets `apply`, and M19 adds `deploy_apply` with `apply: true` to the rule's wording. A user who has the form answered automatically, by a Claude Code `Elicitation` hook or by Codex's reviewer, gives that yes in advance, and the README says not to. If neither client shows the form to the user, `apply` is dropped, `deploy_apply` stays a dry run, and imports go through the CLI.
27. **Agents register the server through the M13 plugins, or by hand.** Each plugin gets a `.mcp.json` that runs `powerops mcp` from PATH, so the server is the installed CLI's version, not the plugin's. Without the plugin, `claude mcp add` and `codex mcp add` take the same command. Microsoft's plugins ship no server config (research basis), but PowerOps' server is local and has no sign-in of its own, so a plugin can start it with no setup.
28. **No live check beyond the done-when's manual run.** The tools that read a tenant run the same code as `drift` and `deploy plan`, whose live checks passed in M8 and M9, and the offline tests cover the mapping with fakes. The manual run reads Test only after the user's yes, and imports nothing, because the user declines the form. If Test is gone first, its tenant steps are marked not verified. No import runs over MCP in Phase 5.
29. **Release labels v0.17.0 to v0.19.0.** M17 keeps v0.16.0 while it is on hold. No release has been cut yet (`.release-please-manifest.json` is at 0.0.0), and release-please numbers the real releases from the commits. So these labels order the milestones; they don't fix the version numbers.

## Decisions, Phase 6 (2026-10-28)

The plan's `decisions.md` holds the question for each, with the options weighed.

30. **Phase 6 adds no feature, and is split by risk into one PR per milestone.** The cheapest high-value fixes come first: S-1, I-1 and D-2 each take under an hour and close a path to running code or importing without the user's intent, and M22 also takes the cheap fixes that touch the same files or every consumer (A-3, D-3, D-5). Only M24, M28 and M32 get a quick plan of their own, because the plan's rows already name the file, the line and the fix for the others; each milestone's PR is still reviewed. M24 changes `deploy apply`'s import path, so it is built after M21 merges, or rebased on it; M28 counts the write sites after M21 merges; the rest don't wait for M21.
31. **Hostile-input tests, not a fuzzing library.** The audit's probes become one table-driven theory per area (about 25 inputs, each with its exit code and a time limit), and M27 adds one seeded mutation test over the fixtures, with structural swaps such as `\ud800` and duplicate keys, in xunit with no dependency. About 10,600 byte mutations and 1,700 structural mutants and random expressions found nothing, while hand-written probes found every gap. CsCheck (Apache-2.0) isn't needed; FsCheck is BSD-3-Clause.
32. **No runtime check of `pac`'s version.** Learn and the NuGet notes date too few of the commands PowerOps uses to give a documented minimum, the version line is documented by one example, and reading it costs one more `pac` start per command. The tested versions stay in decision 16(d), and FOUNDATION §8 keeps the item open.
33. **A zip that can't be opened while scanning a folder exits 3 and names it.** It is unreadable input, which AGENTS.md maps to 3, and the same zip named directly already exits 3. Only a file that starts with the zip signature counts: a Git LFS pointer or an empty placeholder named `*.zip` is skipped, and so is a readable zip with no solution in it. It ships with C-3 in M27, because `diff` and `test` scan the folder outside their `try`.
34. **The import gets the hash the user approved.** Inside the process, with no new CLI option, the import refuses when the re-plan's hash differs from the one shown in the form. A zip swapped between its last hash and `pac` opening it stays possible; closing it would mean importing private copies, and the plan accepts it.
35. **Writes go through one helper.** It refuses a link to a regular file at the target (and, for `skills install`, a link at a folder on the way) and a target that is one of the command's inputs, writes a device or a pipe such as `/dev/stdout` in place, and otherwise writes a temp file that it moves over the target, keeping the file's Unix mode. Commands still replace their own output file, so `--out`, `baseline` and the CLI's `deploy plan --save` reruns work as before; only the MCP `save` refuses an existing file, as it does today.
36. **Repo settings change only after the user's yes.** Private vulnerability reporting, the rulesets, Dependabot alerts and security updates, CodeQL and required SHA pinning change how the public repo behaves for everyone. SECURITY.md can't name another private route, because the repo holds no email addresses.
37. **Windows and macOS: CI where a runner can, a runbook for the rest.** A hosted runner checks the resolver, the arguments a `.cmd` file receives, and the scripts under bash 3.2. The clients and `pac` sign-in need a person's sign-in, which CI can't hold without stored secrets (FOUNDATION §4). They are run by hand when the user has a machine, or marked not verified.
38. **Release labels v0.20.1 to v0.20.7.** Every code milestone is a `fix:`, which release-please releases as a patch, after M21's v0.20.0. M23, M29, M31 and M32 change only settings, CI and docs and get no label. As in decision 29, the labels order the milestones and don't fix version numbers.
